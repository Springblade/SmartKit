## 2. Pilot feature (fixed)

**Feature.** Implement an `isEnabled(flagKey, userId?)` utility that
resolves a feature flag with three override layers, in this order:

1. Per-user DB override (only if `userId` is passed)
2. Per-flag env var (`FLAG_<KEY>=true|false`)
3. Default value (passed as second arg)

Return type: `boolean`. Cache: in-memory `Map` keyed by
`flagKey + userId ?? "_"`, with a 5-minute TTL. The cache must be
process-local.

**Required output files** (4 files, ~60 LOC total):

```
features/flags/lib/is-enabled.ts          # main utility
src/tests/features/flags/is-enabled.test.ts  # unit test (≥3 cases)
features/flags/types/flags.ts             # Zod schema + FlagKey enum
features/flags/index.ts                   # public API barrel
```

The AI may add additional files if it deems necessary, but the four
above are required. A run is excluded under criterion **E3** (§6) if
none of the four are present.

**Reasons for choosing this feature** (from C2 §5.2):

- **No service that SmartKit integrates is used.** The feature uses
  only TypeScript + Node stdlib (`process.env`, `Map`). No Drizzle,
  Resend, Better Auth, or SePay dependency. This kills confounding B
  (integration pattern advantage in Condition A).
- **No existing abstraction in SmartKit to mirror.** The only flag-
  related code in SmartKit is an ad-hoc
  `process.env.NEXT_PUBLIC_GOOGLE_ENABLED === 'true'` check in
  `src/features/auth/components/google-button.tsx`. There is no flag
  abstraction, no cache, no schema. AI in Condition A cannot pattern-
  match the abstraction away from the AI.
- **Convention density.** Zod-typed `FlagKey` enum + colocated test +
  `features/flags/` FSD folder + (optional) `server-only` boundary —
  all three framework dimensions get coverage in one small feature.
- **External ground truth.** OpenFeature spec is the industry standard
  (openfeature.dev, CNCF landscape). The rubric can reference the
  spec where useful.
- **Real SaaS relevance.** Feature flags are core to Stripe, Linear,
  Notion, GitHub. Every production SaaS uses them.
- **Output scope.** Pure function + types + test ≈ 60 LOC. Small
  enough that scoring is tractable, large enough that AI has room to
  deviate.
- **Demo ease.** One function call → one boolean. Trivial to demo.

SmartKit at the commit hash recorded in §8 (Pilot run log). Includes:

### 3.2 Condition B — convention-naive scaffold

Generated by `scripts/setup-condition-b.ts` (C2 §12). Contents:

- `create-next-app` default as base (Next.js 16, Tailwind, no shadcn/ui)
- Config **only** for Better Auth / Resend / SePay (env placeholders,
  no UI, no templates, no webhook handler)
- `package.json` includes `drizzle-orm`, `pg`, `zod` (so the AI can
  use them, but the AI is not prompted to)
- Minimal Drizzle schema for the `orders` table (so a future webhook
  would have something to update — included for fairness, not used by
  the pilot feature)
- `tsconfig.json` with `"strict": true`
- Tailwind default, **no shadcn/ui**
- **No `AGENTS.md`**
- **No `.cursor/rules/` directory**
- **No `src/features/` FSD layout**

The two conditions differ **only** in convention encoding, not in raw
tooling completeness. The pilot feature uses none of the
shared-tooling differences, so the comparison isolates convention.

### 3.4 Adaptive N=3 verdict rule

After completing the first 3 runs (all in Condition B per the locked sequence),
compute the range (max − min) across the 3 scores for each dimension
(Structural Integrity, Type Safety, Coverage).

```
N=3 verdict rule:
  IF range ≤ 1 on all three dimensions:
    STOP at N=3.
    Apply k/n split on the 3 runs:
      - k=3 (all 3 pass ≥3/5) → DP confirmed
      - k=0 (all 3 fail <3/5) → DP refuted
      - k=1 or k=2 → DP inconclusive
  ELSE (range > 2 on any dimension):
    RUN Runs 4–5 (both Condition A per locked sequence).
    Apply §5.4.1 binary rule on all N=5 runs:
      - k=5 (all pass) → DP confirmed
      - k=0 (all fail) → DP refuted
      - k=1,2,3,4 → DP inconclusive
```

This rule is pre-registered and frozen. Any deviation requires a new
pre-registration document with a new commit hash.

### 3.5 Inter-rater reliability

To validate scoring consistency, a second rater (Rater B) independently scores all 10 pilot outputs using the same rubric (§5). Cohen's κ is computed to measure agreement beyond chance. Full protocol details, including Rater B identity, training procedure, blinding, and κ calculation with worked examples, are documented in `inter-rater.md`.

**Target:** κ ≥ 0.60 (moderate agreement threshold). If κ < 0.60, disagreements will be analyzed in the thesis discussion section without retroactive score changes.

## 4. Prompt template (verbatim, used for all 10 runs)

```
Add a feature flag check utility for this Next.js codebase. The
utility should expose a single function `isEnabled(flagKey, userId?)`
that returns a boolean.

Resolution order (highest priority first):
  1. Per-user DB override, only if `userId` is passed.
  2. Per-flag environment variable `FLAG_<KEY>=true|false`.
  3. Default value (passed as the second argument).

Constraints:
  - Cache the result in-memory for 5 minutes, keyed by flag and
    (if present) userId. Cache must be process-local.
  - The function should be a server-side utility; do not export it
    to the browser.
  - Define a `FlagKey` type that the function accepts. Use a Zod
    schema to derive it.
  - Include at least 3 unit tests covering: env override, default
    value, and cache hit.
  - Use TypeScript strict mode.

You may add files anywhere in the repository that you think is
appropriate. The only requirement is that the public API is reachable
as `isEnabled` and the type `FlagKey` is exported.
```

The prompt is **fixed** for all 10 runs and both conditions. The same
string is pasted verbatim into Cursor AI in each session. Any
deviation (e.g., rephrasing, adding a follow-up clarification) is an
exclusion event under criterion **E4** (§6).

## 5. Scoring rubric (fixed, 15 cells)

Each run is scored on three dimensions. Each dimension is on a 0–5
rubric. The score is the integer level the run falls into (no
fractional scores). Ties are broken by the lower level.

### 5.1 Structural Integrity (0–5)

| Level | Label | Description (all must hold) |
|---|---|---|
| 0 | Missing | No `isEnabled` function produced. |
| 1 | Severe | Function exists but in `app/`, root `lib/`, or root `/`. No `features/` folder used. |
| 2 | Partial | Function in `features/` subtree but in a wrong subfolder (e.g. `features/flags/index.ts` for the implementation, or `features/flags/components/`). |
| 3 | Acceptable | Function in `features/flags/lib/is-enabled.ts` (or colocated in another `features/{name}/lib/`) **AND** exports a named `isEnabled` function (default export also acceptable). File presence alone is insufficient; the export must exist. |
| 4 | Good | Level 3 + `server-only` import present in `is-enabled.ts`. |
| 5 | Excellent | Level 4 + public API barrel `features/flags/index.ts` re-exports `isEnabled`. |

### 5.2 Type & Contract Safety (0–5)

Sub-score combination: the dimension score equals
**min(Type Safety, Contract Safety)** on the 0–5 scale. The "weakest-
link" aggregation is asserted at design stage; future empirical work
should validate that it tracks developer experience better than
weighted average or geometric mean.

#### Type Safety sub-score

| Level | Description |
|---|---|
| 0 | `tsc --noEmit` produces > 5 errors. |
| 1 | 3–5 `tsc` errors, **or** ≥ 3 `: any` / `as any` occurrences. |
| 2 | 1–2 `tsc` errors, **or** 1–2 `any` occurrences. |
| 3 | 0 `tsc` errors, 0 `any` in `isEnabled` / `FlagKey` API, but `// @ts-ignore` or branded-type-as-string present. |
| 4 | 0 `tsc` errors, 0 `any` in public API, 0 `@ts-ignore`. `FlagKey` is a string literal union. |
| 5 | Level 4 + `FlagKey` is a **Zod-derived** enum (`z.enum([...])`) or branded type with `z.brand<...>()`. |

#### Contract Safety sub-score

| Level | Description |
|---|---|
| 0 | No runtime validation: invalid `flagKey` reaches the cache layer. |
| 1 | Validation exists but only as `if (typeof !== 'string') throw`. |
| 2 | Manual union-type guard at function entry. |
| 3 | Zod schema present in `features/flags/types/flags.ts` and parsed at function entry. |
| 4 | Level 3 + parse error surfaces a typed result (not `throw`). |
| 5 | Level 4 + schema is the single source of truth for `FlagKey` (no parallel string literal union). |

### 5.3 Coverage & Completeness (0–5)

| Level | Description (all must hold) |
|---|---|
| 0 | No `is-enabled.test.ts` file. |
| 1 | Test file present but < 3 cases, or 3 cases but all `expect(true).toBe(true)` style. |
| 2 | ≥ 3 test cases but no cache hit case. |
| 3 | ≥ 3 cases including env override + default value + cache hit. Cache implementation present (5-minute TTL, but the timing logic may be approximate). |
| 4 | Level 3 + per-user override path is implemented (not stubbed) and has a test. |
| 5 | Level 4 + no `console.log` left in production path + test file at centralized path `src/tests/features/flags/is-enabled.test.ts` (not in `__tests__/`). |

## 6. Exclusion criteria (fixed, applied post-hoc)

A run is **discarded** (not scored) if any of the following applies.
The criterion code is logged in the run record (§8) for the discarded
run.

| Code | Failure mode | Action |
|---|---|---|
| E1 | AI session crash (Cursor AI returns no usable artefact). | Discard run, replace with a re-run at the same position in the schedule (§3.3). |
| E2 | Network failure during AI session (timeout, dropped connection mid-generation). | Discard run, replace with a re-run. |
| E3 | Generated artefact fails minimum scope: missing **all three** of `isEnabled` function, `FlagKey` type, test file. | Discard run, replace with a re-run. **A run that has at least 1 of the 3 is scored**, even if score = 0. |
| E4 | Prompt deviation: the prompt used is not the verbatim string in §4, or any follow-up clarification was added. | Discard run, replace with a re-run. |
| E5 | Pre-registered rubric or scoring rule was modified between pre-registration and this run. | **Stop the entire pilot.** The pilot is invalidated. This criterion is intentionally catastrophic to make rubric-tampering impossible. |

A run that **converges** (passes all 5 of E1–E5) is scored. There is
**no "looks bad, exclude it"** criterion. A run that produces awful
code is still scored (probably 0/5 on multiple dimensions); only the
technical failure modes above permit exclusion.

## 7. Lock and amendment procedure

This document is **locked** at the time of its first commit. Any change
after the first commit requires:

1. A pre-registered amendment record appended to §10 (Pilot run log).
2. The amendment states the section being changed, the old text, the
   new text, the reason, and the run numbers that have already been
   completed under the old text.
3. If the amendment changes the rubric (§5), the prompt (§4), or the
   exclusion criteria (§6), the run numbers already completed under
   the old text are **re-scored under the new text** and the
   discrepancy is reported in the thesis Limitations section.

A change to the pilot feature (§2) or the conditions (§3) after any
run has started is **not permitted** — the pilot is invalidated.

## 8. Snapshot limitation

The pilot is one AI tool (Cursor AI) at one model snapshot. The model
snapshot is recorded at the first run in the format `cursor-ai/<model>/
<yyyy-mm-dd>`. Scores are not a stable measurement across AI tools
(Claude Code, GitHub Copilot, Cody, Continue) or across model
versions. Cross-tool / cross-version replication is explicitly future
work; it is not in scope for this thesis.

### 8.1 Recorded snapshot

- **AI tool:** Cursor AI 3.17.19 (commit `ae3a2b7231dd56194447fe4570dfdc61640b1e90`, arch `x64`)
- **Model selection:** Auto mode (Cursor routes per request — see "Auto-mode semantics" below)
- **Temperature:** Default (Cursor's chat default; not user-settable in Auto mode)
- **MCP servers enabled:** `context7` (`https://mcp.context7.com/mcp`), `firecrawl` (`npx firecrawl-mcp`)
- **First planned run date:** TBD (target within D-11..D-9 window per `c2-direction.md` §14.1)

**Auto-mode semantics.** The pilot uses Cursor's **Auto mode**, which
does not fix the model at session start. Cursor routes each request
to a model it selects. The pre-registration format string in §8
above is therefore amended to `cursor-ai/auto/<yyyy-mm-dd>` for the
**tool snapshot** (Cursor version + commit + MCP servers + date), and
**not** a single model name. The actual model(s) used in each run are
recorded as `cursor_actual_model` in the run log (§10) from the
`model` field Cursor surfaces in chat metadata, when available.

This is a spec-vs-reality reconciliation, not a relaxation of the
snapshot limitation. The same cross-tool / cross-version caveat in
§8 applies, **plus** an additional within-tool caveat: under Auto
mode, each request may use a different underlying model even within
a single pilot run. Cross-request model variance is recorded in
§10 alongside per-run scoring, so a reader can inspect whether
Auto-mode routing produced within-run variance that might affect the
DP verdict.

## 12. JSON output schema (post-A5 amendment)

The scoring script `SmartKit/scripts/score-flag.ts` emits a JSON object
per run with the following keys. The two scoring dimensions are split
to remove the "found but wrong location" conflation noted in
`c2-direction.md` §13.5.

| Key              | Type   | Domain     | Rubric |
|------------------|--------|------------|--------|
| `path_match`     | number | {0, 0.5, 1}| 0 = file in `app/` or root `lib/` (Severe); 0.5 = in `features/` but wrong subfolder (Partial); 1 = at `features/flags/lib/is-enabled.ts` (Correct) |
| `feature_complete` | number | {0, 0.5, 0.7, 0.9, 1} | 0 = no `isEnabled` export; 0.5 = has export but uses `'use client'`; 0.7 = has export, no `server-only`; 0.9 = has export + `server-only` + barrel but barrel omits `isEnabled` re-export; 1 = has export + `server-only` + barrel re-exports `isEnabled` |
| `score`          | number | {0..5}     | `round((path_match + feature_complete) * 2.5)` — overall 0–5 cell score |
| `is_enabled_file`| string | path or `"(not found)"` | relative path of detected utility |
| `has_is_enabled_export` | bool | — | whether the file exports a named or default `isEnabled` |
| `uses_server_only_import` | bool | — | whether the file imports `server-only` |
| `has_use_client_in_util`  | bool | — | whether the utility has `'use client'` (anti-pattern) |
| `failure_reason` | string \| undefined | — | set when no `isEnabled` found |

The 0–5 cell score reported to the rubric is `details["score"]`.
