\section{Pilot Feature}

The pilot tests how well AI assistants generate a \textbf{feature flag utility}: a function that checks whether a given feature flag is enabled for a user.

\textbf{Scope:} The utility must:
\begin{itemize}
\item Accept a flag key (string) and optional user ID
\item Return a boolean indicating whether the flag is enabled
\item Include type-safe schema validation (Zod)
\item Include a test file at the canonical by-feature path
       \filename{src/tests/features/flags/is-enabled.test.ts}
\end{itemize}

\textbf{File deliverables expected.} The AI was expected to generate the following files for the \code{isEnabled(flagKey, userId?)} utility.

\textbf{Condition~A (SmartKit)}: the implementation at \filename{features/flags/lib/is-enabled.ts}, the Zod \code{FlagKey} schema at \filename{features/flags/types/flags.ts}, the public API barrel at \filename{features/flags/index.ts}, and the unit test at \filename{src/tests/features/flags/is-enabled.test.ts}. These paths match the rubric level~5 layout defined in \S5.3.

\textbf{Condition~B (convention-naive scaffold)}: implementation at a root-level path (\filename{lib/feature-flag.ts}, \filename{lib/feature-flags.ts}, or \filename{lib/flags.ts}); \code{FlagKey} as a raw TypeScript string union (no Zod); no public API barrel; and unit test at the repository root (e.g. \texttt{feature-flag.test.ts} or \texttt{flags.test.ts}).

The Condition~A layout mirrors the SmartKit rubric level~5 checklist. Condition~B uses a single-file, root-level convention with no feature-based folder and no centralized test path.

\textbf{Reasons for choosing this feature:}
\begin{itemize}
\item Representative of common Next.js utility patterns (accepts input, validates, returns output).
\item Covers multiple evaluation dimensions: file placement (Structural), Zod schema (Type Safety), test coverage (Coverage \& Completeness).
\item Small enough to complete in one AI session (estimated 5--10 minutes).
\item No external API dependencies, reducing confounding variables.
\item Clear success criteria: function signature, schema, and test presence.
\item Demonstrates feature-based organization in Condition A versus flat structure in Condition B.
\end{itemize}

The baseline represents a typical Next.js project without explicit architectural guidance.

\subsection{Binary Verdict Rule (current)}

The verdict rule in force applies to the post-extension data (see Pilot Design v2 \S5.4.1). The original ``Adaptive N=3'' rule is superseded by \S A.11 amendment 2026-09-01 and is retained here only for audit traceability.

\textbf{Original \S A.3.4 rule (superseded):} If all three directional predictions (DP1, DP2, DP3) are supported after $N=3$ runs per condition, the pilot stops early. Otherwise, complete all $N=5$ runs. Verdict logic: for each DP, if all 3 Cond~A runs exceed all 3 Cond~B runs on the relevant dimension, the DP is supported; otherwise it is not supported.

\textbf{Current \S A.3.4 rule (in force):} 5/5 confirmed; 0/5 refuted; 1--4/5 inconclusive. The rule applies to both arms (Cond~A and Cond~B each at $N=5$ after the 2026-09-14 amendment extended Cond~B from $n=3$ to $n=5$). It raises the confirmed bar from $\geq 4/5$ to $5/5$ and aligns the refuted bar with the strict-falsification standard ($0/5$). The original ``Adaptive N=3'' rule above is superseded and retained only for audit traceability.

\subsection{Inter-Rater Reliability}

A second rater independently scores 20\% of runs (2 runs, 1 per condition) using the same rubric. Cohen's $\kappa$ is computed. If $\kappa < 0.7$, the rubric is revised and all runs are re-scored.

\section{Prompt Template}

The prompt given to the AI assistant in all runs is reproduced verbatim below.

\begin{verbatim}
Add a feature flag check utility for this Next.js codebase. The
utility should expose a single function `isEnabled(flagKey, userId?)`
that returns a boolean.

Resolution order (highest priority first):
  1. Per-user DB override, only if `userId` is passed.
  2. Per-flag environment variable `FLAG_<KEY>=true|false`.
  3. Default value (passed as the second argument).

Constraints:
  - Cache the result in-memory for 5 minutes, keyed by flag and
    (if present) userId. Cache must be process-local.
  - The function should be a server-side utility; do not export it
    to the browser.
  - Define a `FlagKey` type that the function accepts. Use a Zod
    schema to derive it.
  - Include at least 3 unit tests covering: env override, default
    value, and cache hit.
  - Use TypeScript strict mode.

You may add files anywhere in the repository that you think is
appropriate. The only requirement is that the public API is reachable
as `isEnabled` and the type `FlagKey` is exported.
\end{verbatim}

\textbf{Prompt delivery:} The prompt is pasted into Cursor AI chat in a fresh session with no prior context. The assistant has access to the full codebase via file tree and search. The prompt is identical for both conditions; the only difference is the codebase state the assistant observes (Cond A is the SmartKit repo with FSD conventions and example features; Cond B is the \texttt{create-next-app} baseline). Any deviation (e.g., rephrasing, adding a follow-up clarification) is an exclusion event under criterion \textbf{E4} (\S6).

\section{Scoring Rubric}

Each run is scored on three dimensions. Each dimension is on a 0--5
rubric. The score is the integer level the run falls into (no
fractional scores). Ties are broken by the lower level. Aggregate
score per run is 0--15 (sum of three dimensions). The primary analysis
reports median + range per condition (consistent with \S6.7 body and
with \texttt{SmartKit/scripts/aggregate-dp.ts}).

\textbf{Field provenance:}
\begin{itemize}
