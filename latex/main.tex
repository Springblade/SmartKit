\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

% --- Abstract ---
AI coding assistants generate Next.js App Router code that violates framework conventions such as Server/Client boundaries. Existing benchmarks---HumanEval and SWE-bench---measure algorithmic capability, not framework-convention adherence.

This thesis designs a three-dimensional evaluation framework for AI-generated Next.js boilerplate. The framework scores Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness on a 0--5 scale. The primary contribution is the framework design. SmartKit, an open-source Next.js boilerplate, instantiates the framework's conventions; a bounded feasibility pilot with five runs per condition demonstrates that the framework produces measurable scores on real AI-generated code.

The pilot produces three verdicts under the pre-registered binary rule. Structural placement (DP1) and centralized test path in Condition~A (DP3-A) confirm outright: Condition~A passes in all five runs and Condition~B passes in zero. Type \& Contract Safety (DP2) confirms as an instruction-following asymmetry rather than as a pure convention-encoding benefit: Condition~A produces Zod-derived \code{FlagKey} types in all five runs and Condition~B produces raw \code{string} types in all five runs, but the pilot cannot attribute this contrast to convention encoding alone. Test placement in Condition~B (DP3-B) refutes: Condition~B places test files at the repository root in all five runs, opposite of the prediction.

Findings are bounded by one tool, one feature, and a feasibility-stage sample ($N=5$ per condition). Population-level claims require a validation-stage replication with approximately 30 runs per arm.

\chapter{Introduction and Motivation}
\label{sec:introduction}

The chapter opens with the recent wave of AI coding assistants and the parallel shift in Next.js toward the App Router, then identifies the absence of an evaluation framework for framework-specific convention adherence. From that gap the chapter derives the research objectives, questions, and hypotheses that structure the rest of the thesis, and closes with the scope within which the SmartKit framework is designed and evaluated.

\section{Overview}

Controlled studies report substantial productivity gains from AI coding assistants. Peng et al. showed that developers using GitHub Copilot completed tasks 55.8\% faster than control groups \parencite{peng2023impact}, while Yetiştiren et al. reported that GitHub Copilot generated valid code for 91.5\% of HumanEval problems ($n=164$), with 28.7\% fully correct, 51.2\% partially correct, and 20.1\% incorrect \parencite{yetistiren2022assessing}. Next.js has emerged as the dominant React meta-framework for production web applications, with its App Router architecture introduced in version 13 fundamentally changing application structure through React Server Components and explicit Server/Client boundaries \parencite{nextjsdocs}. The failure mode that motivates this thesis is concrete (\autoref{fig:motivated-example}): when an AI coding assistant generates a Server Component that imports a Client Component and passes an event handler as a prop, Next.js produces the runtime error ``Event handlers cannot be passed to Client Component props''---a failure that \code{tsc --noEmit} cannot catch because it has no type-level representation. During SmartKit's development, recurring AI generation errors were observed firsthand in Next.js App Router code, including authentication security flaws, component boundary violations, and outdated API usage from older training data; these are development-time observations rather than measured prevalence figures. Without systematic evaluation, developers cannot assess whether AI-generated Next.js code adheres to framework conventions or will fail in production.

Existing benchmarks---HumanEval, SWE-bench---score algorithmic correctness and bug-fixing capability, but none of them measure framework convention adherence \parencite{chen2021evaluating,jimenez2024swebench}; a recent SLR of 395 LLM-for-SE studies confirmed that framework-convention adherence is not separately tracked as an evaluation category, with 338 of 395 studies (~86\%) relying on generation-task metrics such as BLEU-4, Pass@k, and Accuracy@k \parencite{hou2024llmse}. None of these capture the specific architectural requirements of Next.js App Router, such as Server/Client component boundaries, type-safe contracts, or file-system routing conventions. The practical consequence is that developers have no quantitative basis for comparing AI tools on these architectural tasks. This thesis proposes a three-dimensional evaluation framework---structural integrity, type \& contract safety, and coverage \& completeness---designed to fill that gap.

This overview has sketched the problem from a practitioner angle. The next section formalises the technical challenges that make convention adherence hard to measure; the formal research objectives, contribution list, and framework definition follow in \S\ref{sec:research-objectives}.

\section{The Problem: AI Convention Violations in Next.js}

This thesis addresses a concrete problem: AI coding assistants consistently generate Next.js App Router code that violates framework conventions, producing runtime errors and technical debt, yet no evaluation framework exists to measure this adherence. Three principal challenges shape the framework design.

First, framework conventions are implicit and distributed across documentation, error messages, and community patterns. Enumerating them into testable metrics is itself an open problem. Second, AI-generated code failures in Next.js manifest at runtime rather than compile time --- the Server/Client boundary error ``Event handlers cannot be passed to Client Component props'' only fires when the component is executed, so the framework needs dynamic analysis rather than static linting alone. Third, the three evaluation dimensions are designed to be orthogonal: a structural-integrity violation does not imply a type error, and a coverage gap operates independently of both. Collapsing them into a single composite score would hide which dimension is actually regressing. The orthogonality of the three dimensions is asserted at design stage and awaits empirical validation; the executed pilot's per-arm sample is far below the $n \approx 30$ required to confirm that the dimensions vary independently in practice (a Pearson correlation matrix on $n \geq 30$ per condition would distinguish genuine orthogonality from subtle coupling, and this analysis is part of the validation-stage work described at the end of this thesis).

The focus on Next.js App Router is deliberate. First, market dominance makes it the primary target: Next.js is reported at 20.8\% in the Stack Overflow 2025 Developer Survey's web-frameworks-and-technologies category, ahead of Express (19.9\%) and Angular (18.2\%) \parencite[1, Stack Overflow Developer Survey]{stackoverflow2025}. Second, training-data mismatch is a recognized failure mode of LLM-based code assistants: Wu et al.\ introduced VersiCode, a benchmark spanning 300 Python libraries and 2{,}000+ versions over 9 years, and showed that version-controllable code generation (version-specific completion and version-aware migration) is a significant challenge even for frontier models \parencite{versicode2024}. Third, practical feasibility applies: the author has existing Next.js expertise, enabling direct testing of enforcement mechanisms. The pilot targets Cursor because its AGENTS.md feature implements documentation-based guidance, an approach consistent with prior research suggesting that explicit context and structured prompts improve AI coding-assistant output quality \parencite{barke2022grounded,zhang2023practices}.

\section{Research Objectives and Questions}
\label{sec:research-objectives}

While Next.js dominates React meta-framework adoption and AI coding assistants such as GitHub Copilot and Cursor have demonstrated substantial productivity gains, there is a distinct gap at the intersection of these two areas: a systematic, operationalizable evaluation framework that measures how closely AI-generated Next.js boilerplate code adheres to framework-specific conventions. Existing benchmarks---HumanEval, SWE-bench---address algorithmic problem-solving and bug-fixing capability, but none capture the architectural requirements of Next.js App Router such as Server/Client component boundaries, type-safe contracts, or file-system routing conventions \parencite{chen2021evaluating,jimenez2024swebench}. This thesis targets precisely that gap.

The primary motivation of this thesis is to bridge this gap by designing a three-dimensional evaluation framework that turns an implicit set of framework conventions into measurable, comparable scores, and by instantiating that framework in SmartKit, a structured Next.js boilerplate that provides the necessary enforcement mechanisms and the evaluation target codebase.

The research pursues three objectives:
{\sloppy
\begin{itemize}
    \item \textbf{Design a three-dimensional evaluation framework.}
    Construct a framework that scores AI-generated Next.js boilerplate
    code along three dimensions: Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness, so that convention adherence becomes a quantitative,
    comparable property of generated code.
    \item \textbf{Implement SmartKit as a structured architecture.}
    The thesis releases SmartKit, an open-source Next.js boilerplate
    that demonstrates feature-based modularity, explicit Server/Client
    boundaries, and type-safe contracts, providing both the enforcement
    mechanisms and the target codebase for the framework.
    \item \textbf{Demonstrate framework applicability through a bounded
    feasibility run.} The thesis applies the framework to a representative
    feature generated by Cursor under the SmartKit condition to verify that
    the framework can produce scores on real AI-generated code.
\end{itemize}
}

Consequently, this research seeks to answer the following research questions:
\begin{enumerate}
    \item How can an evaluation framework be consistently designed to
    measure AI coding assistant adherence to Next.js App Router boilerplate conventions along the Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness dimensions?
    \item Can the resulting framework be operationalized into measurable
    metrics, and does it demonstrate applicability when applied to
    representative AI-generated Next.js features?
\end{enumerate}

These objectives and questions yield two classes of claims, both
documented as design-level pre-registrations to be exercised by the
pilot section.

\begin{description}
  \item[Framework properties (FP)] describe what the framework can
    measure. Each property claims that a dimension can be operationalised
    on a real artifact and produce a per-run score. The pilot can only
    support or fail to support these claims; it cannot refute them.
  \item[Directional predictions (DP)] are falsifiable hypotheses about
    Condition~A versus Condition~B. Each prediction states which
    condition is expected to score higher on a given dimension. The
    pilot assigns each prediction a binary verdict of
    \emph{confirmed}, \emph{refuted}, or \emph{inconclusive}.
\end{description}

\paragraph{Framework properties (descriptive).} The pilot demonstrates
that the framework operates on a real artifact:
\begin{itemize}
    \item \textbf{FP1 (Structural Integrity).} The framework can measure
    the dimension it targets---file placement, Server/Client boundary
    usage, and naming patterns---on AI-generated Next.js code, yielding
    a per-run score on a representative feature.
    \item \textbf{FP2 (Type \& Contract Safety).} The framework can measure
    the dimension it targets on AI-generated Next.js code, yielding a
    per-run score on a representative feature by combining Type-Safety
    and Contract-Safety sub-scores under the framework's weakest-link
    combination rule.
    \item \textbf{FP3 (Coverage \& Completeness).} The framework can
enumerate AI-generated files against a feature-specific checklist
and yield a per-run score reflecting required-artifact presence,
demonstrated on the no-integration subset of the convention envelope;
the integration-using subset (e.g.\ a feature that integrates Drizzle)
is structurally excluded from this pilot and is documented in
\S\ref{sec:threats} as a future-validation target.
\end{itemize}

\paragraph{Directional predictions (falsifiable hypotheses).} Each
prediction asks whether Condition~A outperforms Condition~B on one
dimension. The pilot uses the \code{isEnabled(flagKey, userId?)}
utility as the representative feature and evaluates the prediction as
\emph{confirmed} (all runs agree with the predicted direction),
\emph{refuted} (no runs agree), or \emph{inconclusive} (mixed),
following the adaptive-$N$ pilot protocol.

\begin{itemize}
    \item \textbf{DP1 (Structural Integrity).} Condition~A is predicted to place the
    utility in the SmartKit feature-based layout in the majority of runs;
    Condition~B is predicted to use a root-level or flat structure.
    \item \textbf{DP2 (Type \& Contract).} Condition~A is predicted to
    produce Zod-typed schema definitions in the majority of runs;
    Condition~B is predicted to use raw string types.
    \item \textbf{DP3 (Coverage).} Condition~A is predicted to include a
    centralized test file in the majority of runs;
    Condition~B is predicted to omit a test file in the majority of runs.
\end{itemize}

The pilot reports each framework property as \emph{supported} or
\emph{unsupported} and each directional prediction as one of the three
binary verdicts. Full statistical validation, including larger
per-arm samples, cross-tool replication, and developer-participant
studies, remains future empirical work (see \autoref{sec:threats}
for threats to validity).

Designing an evaluation framework for AI-generated Next.js boilerplate encounters three key challenges that distinguish it from existing code generation benchmarks. First, framework conventions are implicit and distributed across documentation, error messages, and community patterns, requiring deliberate extraction into enumerable, testable rules rather than relying on predefined quality criteria. Second, convention violations in Next.js App Router manifest primarily at runtime. Server/Client boundary violations produce errors only when executed, so evaluation must go beyond static analysis to capture dynamic execution behaviour. Third, because the three dimensions are orthogonal, the evaluation demands a multi-dimensional framework rather than a single composite score: collapsing them would hide which dimension is actually regressing. The orthogonality of these dimensions is asserted at design stage and awaits empirical validation; Pearson correlation analysis across runs would test whether the three dimensions are genuinely orthogonal or merely weakly coupled, but the executed pilot's small per-arm sample precludes such analysis at this stage.

This thesis makes one primary contribution and two supporting contributions.

The primary contribution is the design of a three-dimensional evaluation framework, scored on Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness, for measuring how closely AI coding assistants adhere to Next.js App Router conventions. The framework addresses a gap left by existing benchmarks, which score algorithmic correctness rather than framework-specific quality. The framework is operationalised through an \emph{ecosystem comparison}: a SmartKit condition with AGENTS.md, sibling features, FSD layout, and Zod patterns versus a convention-naive scaffold with none of these.

The first supporting contribution is the SmartKit artifact, an open-source Next.js boilerplate demonstrating feature-based modularity, explicit Server/Client boundaries, and type-safe contracts. SmartKit supplies both the conventions the framework measures and the target codebase it measures them on. All four Better Auth tables (user, session, account, verification), the billing feature (SePay integration with HMAC signature verification and idempotent webhook handling), and the email integration (Resend and React Email) are implemented at the current snapshot.

The second supporting contribution is the bounded feasibility pilot protocol, comprising a pre-registration document, a Condition~A versus Condition~B comparison scaffold, a scoring rulebook, and a baseline-bootstrap script. These artifacts are concrete enough that another researcher can replicate the pilot without re-deriving the protocol from the thesis prose. The pilot demonstrates that the framework produces measurable contrast between conditions. It does not estimate the population-level effect size.

\section{Scope and Limitations}

To keep the empirical rigor and feasibility of this research within the resource envelope of a single-author thesis, the scope is strictly defined by the following parameters and limitations:

\begin{enumerate}
    \item \textbf{Framework scope:} Next.js App Router only. No comparison with Nuxt, Remix, or other meta-frameworks.
    \item \textbf{AI assistants:} Cursor used for the bounded feasibility demonstration. Broader AI assistant evaluation (GitHub Copilot, Claude Code) is future work.
    \item \textbf{Project type:} Single representative Next.js project demonstrating SaaS patterns.
    \item \textbf{Pilot study limitation:} The feasibility demonstration runs one representative task (\code{isEnabled(flagKey, userId?)}) with five independent runs per condition, yielding ten runs total. The demonstration uses a pre-registered rule: five passing runs confirms a prediction, zero passing runs refutes it, and one to four passing runs marks it inconclusive. Findings are bounded by the small per-arm sample; a population-level estimate would require approximately 30 runs per condition. Cross-tool replication and larger-$N$ studies remain future work.
\end{enumerate}

These four boundaries are deliberate: fixing them isolates the SmartKit effect from confounding variance.


\chapter{Background}
\label{sec:background}

Understanding the intersection of AI coding assistants and Next.js development requires grounding in three domains: AI coding tool capabilities and limitations, Next.js architectural patterns, and SaaS boilerplate design principles.

\section{AI Coding Assistants}

GitHub Copilot, Anthropic's Claude, and Cursor all use transformer-based LLMs fine-tuned for code understanding and generation. GitHub Copilot provides inline code completions and entire function generation within supported editors (using OpenAI's GPT series and Anthropic's Claude series models, with specific model versions varying over time). Anthropic's Claude offers conversational code assistance through the Claude Code CLI and IDE integrations. Cursor combines Claude with a custom codebase indexing system that enables context-aware suggestions across entire projects.

These assistants are context-aware: completions draw on surrounding code, comments, and project-wide signals such as the codebase index used by Cursor \parencite[code quality evaluation study]{yetistiren2023evaluating}.

Research documents both strengths and limitations. Dakhel et al.\ found that AI assistance benefits expert developers who can filter suboptimal suggestions but may harm novice developers who lack the expertise to identify incorrect or inefficient code \parencite{dakhel2023github}. Liu et al.\ documented that ChatGPT performs better on older problems (pre-2021) than newer ones, with a 48.14\% advantage on the Accepted rate, though it struggles with complex algorithms and domain-specific code, frequently generating solutions with security vulnerabilities and inefficient implementations \parencite{liu2024chatgpt}.

The task taxonomy for AI suitability shows that boilerplate generation represents a strength area. Zhang et al. mined Stack Overflow and GitHub Discussions and found that developers primarily use Copilot for code generation in general-purpose languages (JavaScript, Python) on VS Code, with data processing as the most common function category and difficulty of integration as the dominant limitation \parencite{zhang2023practices}. Pandey et al. documented Copilot time savings of up to 50\% in code documentation and autocompletion, and 30--40\% in repetitive coding, unit-test generation, debugging, and pair programming; the tool struggled with complex tasks, large functions, multiple files, proprietary contexts, and C/C++ code \parencite{pandey2024transforming}. These findings focus the study on boilerplate interaction as an appropriate domain for AI enhancement.

\section{Next.js Framework Architecture}

Next.js is a React meta-framework that provides server-side rendering, static site generation, and API capabilities within a unified application model. Version 13 introduced the App Router paradigm, fundamentally changing how React applications structure pages, layouts, and data fetching. Developers who learned the Pages Router encounter several App Router concepts that the older model did not surface, including Server/Client boundaries and file-system conventions for special files.

React Server Components represent a core innovation in Next.js App Router. These components execute exclusively on the server, which lets them access databases and sensitive operations directly without exposing logic to the client. The distinction between Server and Client components requires explicit marking through the \\usec directive, creating a boundary that developers must carefully manage. Incorrect placement of components across this boundary produces runtime errors and performance degradation.

The App Router organizes applications through a file-system-based routing mechanism. Each folder within the \filename{app/} directory corresponds to a route segment, with \filename{page.tsx} files defining the content for each route. Special files such as \filename{layout.tsx}, \filename{loading.tsx}, and \filename{error.tsx} provide shared UI and error handling across route hierarchies. This convention-driven structure enables rapid scaffolding but requires adherence to specific naming and placement patterns.

TypeScript integration in Next.js emphasizes type safety throughout the application. The framework provides typed interfaces for page properties, API request and response objects, and data-fetching results. Achieving full type coverage requires consistent use of TypeScript patterns including generics, utility types, and strict mode configuration. AI coding assistants may generate code that compiles but violates framework conventions, producing runtime errors or subtle bugs.

\section{SaaS Boilerplate Patterns}

SaaS applications share common requirements that boilerplate frameworks address: user authentication, database access patterns, multi-tenancy support, and deployment configurations. The economics of SaaS development favor approaches that reduce per-project initialization effort while maintaining code quality and consistency.

Krüger et al.\ established that platform reuse reduces maintenance effort but involves upfront investment in framework adoption and learning curve \parencite{kruger2020empirical}. The trade-off explains the appeal of well-designed boilerplate templates that amortize initialization cost across multiple projects. Aleem et al.\ identified customization, scalability, multi-tenancy, security, integration, and fault tolerance as key factors in SaaS architecture decisions \parencite{aleem2019maturity}.

Modern scaffolding approaches build on model-driven architecture principles. Inayatullah and Azam presented a UML-based DSML that automatically generates scaffolding CRUD code for cross-platform (web + mobile) applications from class diagrams, reducing repetitive implementation effort \parencite{inayatullah2019model}. Liu and Sra recently showed that LLMs have potential to automatically generate scaffolded user interfaces, reducing complexity for users in professional creative software \parencite{liu2025auggen}.

Meta-framework evaluation identifies architectural trade-offs across options. The framework-adoption literature identifies learnability, extensibility, and ease of migration as primary drivers of adoption, while framework lock-in and high configurability are commonly cited as adoption risks \parencite{storey2016frameworkadoption}. Next.js App Router emphasizes React Server Components as a first-class primitive while maintaining full compatibility with Client Components for interactive UI. This hybrid model creates specific conventions that boilerplate frameworks should encode.

\chapter{Related Work}
\label{sec:relatedwork}

This section surveys existing research on code generation benchmarks, empirical studies of AI-assisted development, and systematic literature reviews on AI for software engineering. The analysis identifies the specific gap this thesis addresses: the absence of framework-specific evaluation for AI coding assistants operating on Next.js boilerplate conventions.

\section{Code Generation Benchmarks}

The evaluation of AI coding assistants relies heavily on standardized benchmarks that measure code generation capability. Chen et al.\ introduced HumanEval as a foundational benchmark containing 164 hand-written programming problems with function signatures, docstrings, and unit tests \parencite{chen2021evaluating}. The benchmark evaluates models using Pass@1, Pass@10, and Pass@100 metrics. OpenAI's Codex achieved 28.8\% Pass@1 on this benchmark, establishing a baseline for subsequent model development.

HumanEval focuses exclusively on single-function Python code generation with algorithmic and reasoning requirements. The design prioritizes general programming capability over domain-specific or framework-aware generation. Yu et al.\ extended the benchmark concept with HumanEval Pro, adding self-invoking code generation tasks that require models to generate functions calling previously defined functions \parencite{yu2025humanevalpro}. Their work found that most LLMs exhibit a 10--15 percentage-point absolute drop on self-invoking tasks compared to standalone tasks (e.g., o1-mini falling from 96.2\% to 76.2\% Pass@1 on HumanEval Pro), indicating that current benchmarks underestimate real-world code generation complexity.

SWE-bench represents a substantial advance in benchmark realism by evaluating AI models on real GitHub issues from popular Python repositories \parencite{jimenez2024swebench}. Each task requires understanding the issue description, locating relevant code, implementing a fix, and passing unit tests. Jimenez et al.\ found that state-of-the-art models resolved only a small fraction of issues --- Claude 2 solved approximately 1.96\% with BM25 retrieval (4.8\% with oracle retrieval) and GPT-4 only 1.74\% with oracle retrieval (0\% with BM25) --- and the gap between benchmark performance and practical software engineering capability is substantial.

Language-specific benchmarks identify further evaluation limitations. Petrukha et al.\ developed SwiftEval for Swift programming, finding that general-purpose benchmarks overestimated Swift code generation capability \parencite{petrukha2025swifteval}. Their language-specific benchmark documented substantial score drops (up to roughly 60 points for the smallest open-source models, with smaller drops for frontier models) when evaluating the same models on Swift versus HumanEval-style Python problems.

No existing benchmark evaluates framework convention adherence, boilerplate structure quality, TypeScript or Next.js-specific patterns, or multi-file scaffolding tasks. The benchmarks measure whether AI assistants can solve algorithmic problems or fix bugs in existing codebases, not whether they can generate framework-compliant boilerplate from scratch.

Several extensions and alternatives warrant mention. Liu et al.\ developed HumanEval+ and MBPP+ as rigorous extensions of the original benchmarks, finding that pass rates drop by 19.3--28.9\% on average across 26 evaluated LLMs when evaluated against additional auto-generated high-quality tests per problem \parencite{liu2024correct}. Zhuo et al.\ introduced BigCodeBench, which evaluates 1,140 fine-grained tasks combining diverse function calls with complex natural-language instructions \parencite{zhuo2024bigcodebench}. Hendrycks et al.\ proposed APPS, a 10,000-problem benchmark spanning introductory, interview, and competition-level coding challenges \parencite{hendrycks2021apps}. Jain et al.\ addressed the critical contamination problem through LiveCodeBench, which sources problems from recent competitive programming contests published after model training cutoffs \parencite{jain2024livecodebench}. Li et al.\ developed CodeReviewer for code review automation, an adjacent evaluation direction that assesses code quality dimensions relevant to AI-assisted development workflows \parencite{li2022codereviewer}. Each of these benchmarks measures distinct aspects of code generation or code quality capability, yet none evaluate the framework-specific convention adherence that the SmartKit framework targets.

\section{Empirical Studies on Developer Productivity}

Several empirical studies examine how AI assistance affects real developer workflows. Peng et al.\ conducted the seminal controlled experiment on GitHub Copilot with 95 recruited developers implementing an HTTP server in JavaScript \parencite{peng2023impact}. Their methodology used a treatment-control design with matched tasks, finding the 55.8\% completion time improvement cited earlier. Heterogeneous effects showed that less experienced developers benefited most from AI assistance.

Tariq et al.\ (SSRN, 2026; pending peer review) conducted an enterprise-level
study with 60 developers and 960 task observations across eight .NET development
tasks \parencite{tariq2026enterprise}. They measured task completion time,
implementation errors, cyclomatic complexity, maintainability index, code smells,
and NASA-TLX cognitive load scores. Their findings show that AI assistance reduced
task completion time, errors, code smells, and cognitive workload while improving
maintainability, though AI also generated redundant abstractions and increased
code verbosity, with effectiveness varying by developer expertise and requiring
continued oversight. This study extends Peng et al.'s methodology to enterprise
settings and serves as an emerging methodological direction for future work in
this area. Its findings are specific to .NET development and do not directly
transfer to Next.js or JavaScript-based AI tool evaluation.

Liu et al.\ assessed ChatGPT code generation quality across multiple languages and task types \parencite{liu2024chatgpt}. ChatGPT performs better on pre-2021 problems with a 48.14-percentage-point advantage on Accepted rate (68.41\% versus 20.27\%), but its ability to directly fix erroneous code through multi-round dialogue is relatively weak. Generated code often contained security vulnerabilities and inefficient implementations requiring human verification, though ChatGPT could resolve over 89\% of identified vulnerabilities through multi-round fixing. In a separate comparison, the same authors found that across 728 LeetCode problems in five languages, AI-generated Python3 solutions had an 8 percentage-point lower share of low-cognitive-complexity submissions than human-written solutions, while cyclomatic complexity distributions closely resembled the human baseline for Python3 (with a 5 percentage-point offset in C++ for cyclomatic) \parencite{liu2024chatgpt}. Yetiştiren et al.\ separately found, in their code quality evaluation study, that ChatGPT, Copilot, and CodeWhisperer all generated code with maintainability issues --- particularly improper naming and high cognitive complexity --- at technical-debt averages of 8.9, 9.1, and 5.6 minutes respectively \parencite{yetistiren2023evaluating}.

AlOmar et al.\ examined developer-ChatGPT refactoring conversations, finding that developers frequently needed multiple iterations to achieve satisfactory refactoring \parencite{alomar2024refactoring}. AI often missed design-level improvements, and common anti-patterns emerged in developer-AI refactoring interactions. AI effectiveness therefore depends on the structure of the interaction and on the developer's ability to guide refinement, not only on the tool itself.

Hou et al.\ conducted a systematic literature review of 395 research articles on LLMs for software engineering from 2017--2024 \parencite{hou2024llmse}. Code generation (118 papers, approximately 30\% of the corpus) and program repair (35 papers, approximately 9\%) are the two most-studied application areas. The review's metric inventory groups evaluation by problem type rather than by benchmark-versus-human split: 338 generation-task studies used 19 metric families (BLEU-4 in 62 studies, Pass@k in 54, Accuracy@k in 39), 147 classification-task studies used nine metric families (Precision in 35, Recall in 34, F1-score in 33), 39 recommendation-task studies used six metric families, and 1 regression-task study used MAE \parencite{hou2024llmse}. Reported effectiveness varies widely by task type. The review identified research gaps in security, requirements engineering, and empirical studies. Framework-specific boilerplate evaluation would begin to address these gaps.

Russo et al.\ developed the Human-AI Collaboration and Adaptation Framework (HACAF), which identifies nine theoretical dimensions across individual (perceived usefulness, ease of use, behavioural intention), technological (compatibility, relative advantage, complexity), and social (social influence, environmental support, self-efficacy) levels \parencite{russo2024navigating}. Technical capability was necessary but insufficient on its own; the present thesis reads their analysis as indicating that human factors including trust, skill, and workflow integration are necessary alongside technical capability for developer-tool adoption. Evaluating framework-specific boilerplate tools therefore requires attention to how well they integrate with developer workflows and support skill development.

\section{Evaluation Methodology}

The refinement of AI-generated code has received attention as a complementary evaluation dimension. Liu et al. analyzed 4,066 ChatGPT-generated programs across 2,033 programming tasks in Java and Python \parencite{liu2024refining}. Of these programs, 2,756 were deemed correct, 1,082 produced wrong outputs, and 177 contained compilation or runtime errors; 1,930 additional programs suffered from maintainability issues identified through static analysis. Their automated refinement pipeline using static-analysis feedback improved code quality by more than 20\%. Evaluation frameworks should therefore measure both initial generation quality and the effort required for refinement.

Ouyang et al. studied the non-determinism of ChatGPT in code generation \parencite{ouyang2025nondeterminism}. Across 829 problems in three benchmarks, the ratio of coding tasks with zero equal test output across different requests ranged from 47.56\% (HumanEval) to 75.76\% (CodeContests). Setting the temperature to 0 does not guarantee determinism, despite being a common practice. Reliable assessment therefore requires multiple runs with confidence intervals rather than single-point measurements.

Beller et al. proposed the DAT framework for measuring software development productivity, developed by the Developer Insights team at Meta \parencite{beller2026dat}. The approach combines diff authoring time, survey-based metrics, and AI tool-specific productivity measures. The DAT framework models a path for evaluating AI-boilerplate interaction that balances quantitative performance metrics with qualitative developer experience assessment.

Nguyen-Duc et al. distilled a research agenda of 78 open RQs across 11 software-engineering areas --- including requirements engineering, design, construction, testing, maintenance, and education --- where the current literature is comparatively sparse \parencite{nguyenduc2025genai}. The agenda explicitly calls for standardized evaluation and longitudinal studies, requirements that framework-specific evaluation frameworks can begin to satisfy.

Sauvola et al.\ projected four primary future scenarios for generative AI in software development, ranging from legacy integration to clean-slate and networked development, with software production shifting toward higher-level design and oversight roles as routine coding tasks become increasingly automated \parencite{sauvola2024future}. Research on optimizing AI interaction patterns, including framework-specific boilerplate conventions that reduce the cognitive overhead of AI-assisted development, follows from this projection.

\section{Research Gap Summary}

The reviewed literature establishes that AI coding assistants improve developer productivity on repetitive tasks, that boilerplate generation represents an AI strength area, and that existing benchmarks measure algorithmic capability rather than framework convention adherence. To the author's knowledge---given the structured-but-non-exhaustive literature search described in the next section---we are aware of no published benchmark that systematically measures framework-convention adherence across multiple Next.js App Router conventions on a controlled corpus; a separate systematic search of framework-adjacent code-generation studies (e.g.\ on Angular/Vue/React-adjacent benchmarks) was not conducted. This gap is independently supported by Hou et al.\ (2024)'s systematic review of 395 LLM-SE articles, which does not list framework-specific convention adherence as a separately tracked evaluation category \parencite{hou2024llmse}; the review's research gaps (security, requirements engineering, empirical studies) likewise do not overlap with framework-specific boilerplate evaluation. This thesis proposes a Next.js boilerplate framework engineered for AI interaction and an evaluation methodology that measures framework-specific quality dimensions, reporting both as design-stage contributions.

\section{Alternative Approaches to AI-Codebase Alignment}

The structural approach taken by SmartKit is one of several strategies that researchers and practitioners have explored to improve AI-codebase alignment. This section reviews these alternatives and justifies why the structural approach was selected for this thesis.

Linter and formatter configurations (ESLint, Prettier, TypeScript compiler) can catch some convention violations but operate after code generation rather than before it. These tools validate style and type-correctness, not semantic feature boundaries; they cannot enforce Server/Client component conventions that require architectural awareness at the structure level. Linters operate alongside SmartKit's structural conventions rather than substituting for them: Biome 2.5.6 is included in SmartKit as a post-hoc consistency check on top of the convention envelope.

The structural approach taken by SmartKit addresses these limitations by encoding conventions at the project structure level. Conventions become discoverable by AI systems through file location and naming patterns, are enforced through project structure rather than developer vigilance, and provide reusable templates that scale across features. The structural approach works alongside prompting and documentation, not as a replacement.

\chapter{Proposed Solution}
\label{sec:solution}

This section presents the design of SmartKit, a Next.js boilerplate framework engineered to optimize interaction with AI coding assistants. The design synthesizes empirical findings from the literature with domain-specific analysis of Next.js conventions to produce a codebase structure that improves AI comprehension and output quality.

This thesis uses three related but distinct terms. \textbf{SmartKit} refers to the artefact released on GitHub: a Next.js App Router boilerplate containing six convention-encoding components (AGENTS.md, FSD directory structure, sibling feature examples, Zod schema patterns, ESLint configuration, and tsconfig path aliases). \textbf{SmartKit-style structuring condition} (abbreviated as Cond~A) is the specific experimental condition used in the pilot, comprising AGENTS.md plus one FSD-aligned sibling feature plus one colocated Zod schema. \textbf{SmartKit ecosystem} is the bundle-as-a-whole, the unit of measurement in the pilot. Findings in Chapter~6 are reported at the ecosystem level because the pilot was designed to measure the joint effect of the SmartKit convention envelope rather than isolate any single component.

\section{Design Rationale}

Zhang et al.\ surveyed developers and found that Copilot is primarily used for code generation in general-purpose languages (JavaScript, Python) on VS Code, with data processing as the most common function category and integration difficulty as the dominant limitation \parencite{zhang2023practices}. This finding motivates the focus on boilerplate interaction as an appropriate domain for AI enhancement. Barke et al.\ observed that programmers interact with Copilot in two modes: acceleration (Copilot executes a known plan) and exploration (Copilot helps discover APIs). They documented four prompting strategies in their codebook: code prompts (71.4\% in acceleration) and context prompts (15.2\% in acceleration) as unintentional strategies, comment prompts (57.2\% in exploration versus 13.1\% in acceleration), and the multi-suggestions pane as the remaining intentional strategy \parencite{barke2022grounded}. From these findings, the SmartKit design draws three architectural decisions: encode conventions explicitly, group related code narrowly, and define type-safe contracts.

\textbf{Feature-based modularity over layer-based organisation.} Many Next.js projects organise code by technical layer (\filename{components/}, \filename{lib/}, \filename{hooks/}) or by page. Layer-based organisation creates wide import graphs: a single component may transitively import from dozens of files, so an AI system generating a new component receives a large, undifferentiated context. Feature-based modularity confines all code for one feature (schemas, actions, components, emails, types) within a single directory, giving the AI a narrow, self-contained context window. The trade-off is that cross-cutting concerns (shared utilities, types, or components) require deliberate extraction to a shared layer; this overhead is acceptable for SaaS boilerplate where the feature boundary is the primary decomposition axis.

\textbf{Drizzle ORM over Prisma.} Prisma uses a schema-first DSL (\filename{.prisma} file) that generates a client; Drizzle uses a TypeScript-first schema directly in \filename{.ts} files, colocated with the application code. I considered Prisma first because the schema-first DSL is easier to onboard onto. Then I read three RealWorld-tier codebases that mixed Prisma schemas with TypeScript business code, and the boundary confused the AI in every case. Drizzle's TypeScript-first approach won out for this thesis despite the steeper SQL learning curve: with Drizzle the AI reads and extends the schema using the same language model it uses for the rest of the codebase, and schema changes propagate through TypeScript's own type inference without a separate code-generation step.

\textbf{Explicit Server/Client boundaries over tRPC-based type sharing.} tRPC provides end-to-end type inference across the Server/Client boundary by sharing a single TypeScript interface definition. This eliminates a class of type errors but requires a separate router definition and does not enforce the architectural boundary at the file level. SmartKit instead uses Next.js's native \usec directive for Client Components and the \pkg{server-only} import for server-only utilities, supplemented by Zod schemas shared across the boundary. The native mechanism is framework-default rather than library-specific, which means the conventions survive beyond the SmartKit codebase and transfer to plain Next.js projects; tRPC conventions do not. The trade-off is that the native mechanism requires explicit developer discipline; tRPC enforces the boundary automatically through its type system. Per-feature Zod schemas are colocated under \filename{features/<name>/types/} so the same definition is the source of truth for both runtime validation (server action) and TypeScript inference (client component props); this location convention is described in \S4.5 (Type-Safe API Contracts).

\textbf{Zod schemas as the single source of truth across the Server/Client boundary.} React Server Components and Client Components communicate through typed props, but there is no built-in mechanism to ensure that the type on the server matches the type on the client. SmartKit uses Zod schemas, defined once in \filename{features/<name>/types/}, parsed at the server action boundary, and reused on the client via \pkg{z.infer}. This means a single schema definition is the source of truth for both runtime validation (server action) and TypeScript type inference (client component props), and the AI can read and extend the schema using the same Zod syntax it encounters in existing features. The trade-off is that Zod adds a runtime dependency and a learning curve for developers unfamiliar with schema-first validation.

\subsection{Intended Users and Adoption Path}

SmartKit targets solo developers and small teams (two to five members) who build Next.js projects with AI coding assistants. These developers already understand React and TypeScript fundamentals. They want to reduce boilerplate setup time and keep AI-generated code consistent with project conventions.

The framework supports incremental adoption. A team can adopt the feature-based folder structure and the Server/Client boundary conventions without committing to the full SmartKit stack. This lower adoption cost lets teams validate the conventions in an existing codebase before they pick up billing, authentication, or email integrations.

\section{Feature-Based Modular Architecture}

Many Next.js projects organize code by technical layer (components/, lib/, hooks/) or by page structure. SmartKit instead uses feature-based modularity, where each feature contains everything needed for its functionality: an authentication feature, for instance, holds database schemas, API routes, React components, form validation schemas, and email templates inside one directory.

This organisation improves AI comprehension by narrowing the search space for relevant context when code is generated for one feature. The scope of any change becomes explicit, which lowers the risk of AI-generated code violating feature encapsulation. The directory boundary also serves as a natural test and deployment unit that matches developer mental models.

The feature directory structure follows a consistent pattern across all features:

\section{Server/Client Boundary Conventions}

React Server Components introduce an explicit boundary between server-only and client-accessible code, and \S4.1 motivates why SmartKit relies on Next.js's native mechanism (the `\usec` directive and the `\pkg{server-only}` import) rather than a library such as tRPC. This section therefore focuses on how those two primitives are applied in practice: where they live in the source tree, and what data-flow shape they impose on AI-generated code.

The boundary affects data-flow design. Server Components can read databases and environment variables directly, while Client Components receive data through props or invoke server actions. AI systems can therefore call type-safe server actions from a Client Component, which keeps the data path consistent as new components are generated.

\section{Database Schema Patterns}

SmartKit uses Drizzle ORM with PostgreSQL to provide type-safe database access across the application. The schema design follows conventions that AI systems can learn from existing tables and reproduce for new ones: each table declares columns with explicit types, relations through foreign keys, and indexes for query optimisation.

The Drizzle query pattern lets AI-generated code read and write the database through type-safe query builders. AI systems can examine an existing schema to infer a join or insert shape and produce code that preserves type safety end-to-end. Ad-hoc queries that bypass type checking or violate the file-level conventions are discouraged.

Better~Auth supplies the shared identity tables (\code{user}, \code{session}, \code{account}, \code{verification}) used by every signed-in feature, while \filename{features/billing/} owns its own \code{billing} and \code{payment\_transactions} tables. All four Better~Auth tables and the billing tables live in \filename{src/database/schema/}, one infrastructure directory outside the Feature-Sliced Design (FSD) hierarchy, with relations declared in \filename{src/database/schema/relations.ts}. The single-directory placement lets \pkg{drizzle-kit} scan every schema in one pass and lets any feature import shared row types (\filename{database/schema/index.ts}) without depending on a sibling feature. The placement keeps database patterns centralised while still being directly importable from any feature module.

\section{Type-Safe API Contracts}

API routes in SmartKit use Zod schemas for request and response validation. These schemas serve dual purposes: runtime validation of incoming requests and TypeScript type inference for handler code. AI systems can examine Zod schemas to understand API contracts, generating code that respects type constraints without requiring explicit type annotations.

The shared schema pattern enables consistent validation across frontend form components and backend API handlers. The same Zod schemas validate both client-submitted forms and server-handled requests. The match between frontend and backend validation reduces the gap between AI-generated client-side and server-side code, producing more coherent implementations.

\subsection{Stack Selection Rationale}
\label{sec:stack-rationale}

Each component of the SmartKit stack reinforces one of the three evaluation dimensions; the design rationale---including the comparison with alternative choices (tRPC versus native Server/Client boundary, Prisma versus Drizzle, raw types versus Zod)---is given in §4.1. The selection instantiates three guiding principles:

\begin{enumerate}
  \item \textbf{App Router-first.} Next.js~16's App Router is the architectural surface that Structural Integrity measures directly: Server/Client boundaries, file-system routing, and the \usec/\pkg{server-only} primitives are framework defaults rather than library conventions, which means the rules encoded in the rubric transfer to plain Next.js projects rather than coupling them to SmartKit.
  \item \textbf{Type-safe contracts at the boundary.} TypeScript~5.7.3 strict mode provides the compile-time signal that Type~\&~Contract Safety reads from \code{tsc --noEmit}, while Zod~4 schemas colocated in \filename{features/<name>/types/} are parsed at the Server Action boundary and reused on the client via \pkg{z.infer}. A single schema is the source of truth on both sides of the Server/Client boundary that Coverage~\&~Completeness checks for, so the AI tooling reads and extends the same Zod syntax it encounters in existing features.
  \item \textbf{Server/Client boundary as a first-class primitive.} The framework's runtime failures (event handlers crossing the boundary, server-only imports leaking to the client) are the failure mode the thesis targets, so the chosen tools must surface those failures naturally: Server Components fetch data directly through Drizzle, Server Actions in \filename{features/<name>/actions/} call \code{revalidatePath} after writes, and Client Components receive typed props without an intermediate client-side data layer. Adopting a tRPC-style shared-router alternative would have hidden the boundary inside library types and removed the very signal the Structural Integrity rubric is designed to read.
\end{enumerate}

The \filename{app/} directory is placed at \filename{src/app/} because that is the path Next.js~16's App Router reads as the routing surface. Pages and layouts live here, not feature code, so the route composition that the Structural Integrity rubric inspects (server-only imports, \usec directives, file-system routing) is read directly from this directory by the framework itself rather than from a custom layout the AI would have to learn. Each route imports feature modules from \filename{src/features/} but never the other way around, which is what keeps the page-vs-feature separation enforceable by static analysis: a feature module cannot accidentally import from a route, because that would invert the dependency direction the App Router expects.

The \filename{database/} directory is placed at \filename{src/database/} because \pkg{drizzle-kit} reads schemas from a single configured path; co-locating every table in \filename{database/schema/} means a migration scan touches one root rather than chasing feature-local schema files. Hosting the four Better Auth tables (\filename{user.ts}, \filename{session.ts}, \filename{account.ts}, \filename{verification.ts}), the relations graph in \filename{relations.ts}, and the billing tables (\filename{billing.ts} with \code{payment\_transactions}) together lets any feature module import shared row types (\filename{database/schema/index.ts}) without depending on a sibling feature's directory. The \filename{database/db.ts} client also sits here so that the \pkg{pg} pool, the \filename{env.DATABASE\_URL} read, and the schema registration live in one file --- the runtime surface that Type~\&~Contract Safety checks via \code{tsc --noEmit} stays minimal and central.

The \filename{lib/} directory is placed at \filename{src/lib/} because the utilities inside (the \code{cn} class-name helper in \filename{utils.ts}, the typed \filename{env.ts} reader, any future cross-feature helper) do not belong to a single feature. Putting \code{cn} inside \filename{src/features/auth/lib/} would force the billing feature to import from auth just to merge class names, which inverts the feature-isolation rule AGENTS.md sets and creates a spurious cross-feature dependency for a generic helper. The directory therefore functions as a third tier, sitting above \filename{src/features/<name>/} in the import graph, for code that every feature may need but no feature owns. The \code{env.ts} reader belongs here for the same reason: the database client, the auth handler, and the billing webhook all read environment variables, so the reader sits at a level that all three can import without forming a cycle.

The \filename{features/flags/} directory sits at the repository top level rather than inside \filename{src/}. This placement is deliberate: the AGENTS.md rule that new feature code should live under a feature-named directory does not enforce a \filename{src/} prefix for the pilot's representative feature, and keeping \filename{features/flags/} at the top lets the AI encounter it immediately when scanning the repo root. The pilot's baseline-bootstrap script adds this directory so that the framework has a non-trivial integration target for the Coverage dimension without requiring a hand-written feature.

Internally, \filename{features/flags/} follows the same conventions as \filename{src/features/auth/}: \filename{lib/} holds the \code{isEnabled} implementation, \filename{types/} holds the Zod-derived \code{FlagKey} schema, and \filename{index.ts} is the public API barrel. The unit test sits at \filename{src/tests/features/flags/is-enabled.test.ts}, inside \filename{src/}, in line with the centralized-test convention in AGENTS.md. Its presence is what makes the pilot executable against the framework without having to first create a feature by hand.

\label{sec:core-feature-implementation}

\subsection{Feature Flag Resolution}
\label{sec:feature-flag-resolution}

The feature flag system implements a three-tier resolution hierarchy that evaluates override sources in priority order. This design reflects the convention encoding principle: per-user overrides take precedence over environment variables, which take precedence over static defaults. The implementation is located in \filename{features/flags/lib/is-enabled.ts}, which is marked \pkg{server-only} to enforce the server-side boundary.

The Zod schema that defines the allowed \code{FlagKey} values is colocated in \filename{features/flags/types/flags.ts}:

\begin{lstlisting}[
  language=TypeScript,
  caption={Zod schema for feature flag keys.},
  label={lst:flag-key-schema},
  basicstyle=\ttfamily\scriptsize,
]
import { z } from "zod";

export const FlagKeySchema = z.enum([
  "FEATURE_NEW_DASHBOARD",
  "FEATURE_BILLING_ENABLED",
  "FEATURE_DARK_MODE",
]);

export type FlagKey = z.infer<typeof FlagKeySchema>;
\end{lstlisting}

The \code{isEnabled} function implements the three-tier resolution with in-memory caching:

\begin{lstlisting}[
  language=TypeScript,
  caption={The isEnabled utility with three-tier resolution and 5-minute TTL cache.},
  label={lst:is-enabled-impl},
  basicstyle=\ttfamily\scriptsize,
]
import "server-only";
import { FlagKeySchema, type FlagKey } from "../types/flags";

const TTL_MS = 5 * 60 * 1000;

// Two parallel maps -- values holds the resolved boolean, expirations
// holds the wall-clock timestamp at which the entry expires.
const values = new Map<string, boolean>();
const expirations = new Map<string, number>();

const buildCacheKey = (flag: FlagKey, userId?: string): string =>
  userId ? `${flag}__${userId}` : `${flag}___`;

const readUserOverride = (
  _userId: string | undefined,
  _flag: FlagKey,
): boolean | undefined => {
  // Per-user DB override is not wired in this pilot.
  return undefined; // signals "no override, fall through"
};

const readEnvOverride = (flag: FlagKey): boolean | undefined => {
  const raw = process.env[`FLAG_${flag}`];
  if (raw === "true") return true;
  if (raw === "false") return false;
  return undefined;
};

export function isEnabled(
  flag: unknown,
  fallback: boolean = false,
  userId?: string,
): boolean {
  const parsed = FlagKeySchema.safeParse(flag);
  if (!parsed.success) {
    throw new Error(
      `Invalid flag key: ${JSON.stringify(flag)}. ` +
        `Allowed: ${FlagKeySchema.options.join(", ")}`,
    );
  }
  const key = buildCacheKey(parsed.data, userId);
  const now = Date.now();

  const expires = expirations.get(key);
  if (expires !== undefined && expires > now) {
    const cached = values.get(key);
    if (cached !== undefined) return cached;
  }

  let resolved: boolean | undefined =
    readUserOverride(userId, parsed.data) ??
    readEnvOverride(parsed.data) ??
    fallback;

  values.set(key, resolved);
  expirations.set(key, now + TTL_MS);
  return resolved;
}
\end{lstlisting}

\bigskip\noindent\textbf{Design rationale.}
The tiered design mirrors the production pattern where feature flags support gradual rollouts via environment variables before per-user targeting. The 5-minute TTL prevents unbounded memory growth while keeping flag values reasonably fresh for environment-driven rollouts. The server-side boundary rationale---why the function lives behind \pkg{server-only} rather than crossing the Server/Client boundary---is given in §4.3.

\subsection{Evaluation Infrastructure}
\label{sec:eval-infrastructure}

To operationalize the three evaluation dimensions, the framework includes an automated scoring script (\filename{scripts/score-flag.ts}) that reads source files and computes a 0--5 score per dimension. The script is read-only: it does not mutate the run directory and does not call any AI/LLM for scoring.

The structural integrity scoring logic detects server/client boundary violations:

\begin{lstlisting}[
  language=TypeScript,
  caption={The structural integrity scoring logic from score-flag.ts.},
  label={lst:scoring-logic},
  basicstyle=\ttfamily\scriptsize,
]
/** Score Structural Integrity dimension (0-5) */
async function scoreStructural(runDir: string): Promise<DimScore> {
  const details: Record<string, unknown> = {};

  // Locate the main utility file (any name, look for isEnabled function)
  const tsFiles = await findTsFiles(runDir);
  let isEnabledPath: string | null = null;
  let hasServerOnly = false;
  let hasUseClient = false;
  let hasIsEnabledExport = false;

  for (const f of tsFiles) {
    const content = await readFile(f, 'utf-8');
    const hasExport =
      /export\s+(?:async\s+)?function\s+isEnabled/.test(content) ||
      /export\s+const\s+isEnabled/.test(content) ||
      /export\s+default\s+(?:async\s+)?function\s+isEnabled/.test(content) ||
      /export\s+default\s+isEnabled/.test(content);

    if (hasExport) {
      isEnabledPath = f;
      hasIsEnabledExport = true;
      hasServerOnly = /import\s+["']server-only["']/.test(content) || /from\s+["']server-only["']/.test(content);
      hasUseClient = content.includes("'use client'") || content.includes('"use client"');
    }
  }

  // Normalize path separators to forward-slash for cross-platform path detection
  // (relative() on Windows returns backslashes; downstream checks use forward-slash)
  const relPath = isEnabledPath
    ? relative(runDir, isEnabledPath).replace(/\\/g, '/')
    : '(not found)';
  details.is_enabled_file = relPath;
  details.has_is_enabled_export = hasIsEnabledExport;
  details.uses_server_only_import = hasServerOnly;
  details.has_use_client_in_util = hasUseClient;

  // Split scoring: path_match (0/0.5/1) and feature_complete (0/0.5/1)
  let pathMatch = 0;
  let featureComplete = 0;

  if (!isEnabledPath) {
    pathMatch = 0;
    featureComplete = 0;
    details.failure_reason = 'No file with isEnabled function found';
  } else {
    const inFeatures =
      relPath.includes('features/flags/lib/') ||
      (relPath.includes('src/features/') && relPath.endsWith('/lib/is-enabled.ts'));
    const inRoot = relPath.startsWith('lib/') || relPath.startsWith('src/lib/') || !relPath.includes('features/');
    const inApp = relPath.includes('app/');

    // Path matching score
    if (inApp || inRoot) {
      pathMatch = 0; // Severe: wrong location
    } else if (!inFeatures && relPath.includes('features/')) {
      pathMatch = 0.5; // Partial: in features/ but wrong subfolder
    } else if (inFeatures) {
      pathMatch = 1; // Correct: features/flags/lib/
    }

    // Feature completeness score
    if (!hasIsEnabledExport) {
      featureComplete = 0; // Missing export
    } else if (hasUseClient) {
      featureComplete = 0.5; // Has export but uses 'use client' (wrong)
    } else if (hasServerOnly) {
      featureComplete = 1; // Has export + server-only
      // Check barrel re-export for full completeness
      if (relPath.includes('features/flags/lib/')) {
        const barrel = join(dirname(isEnabledPath), '..', 'index.ts');
        if (existsSync(barrel)) {
          const barrelContent = await readFile(barrel, 'utf-8');
          if (!barrelContent.includes('isEnabled')) {
            featureComplete = 0.9; // Almost complete but missing barrel
          }
        }
      }
    } else {
      featureComplete = 0.7; // Has export but no server-only
    }
  }

  details.path_match = pathMatch;
  details.feature_complete = featureComplete;

  // Overall score (0-5) = weighted combination
  const score = Math.round((pathMatch + featureComplete) * 2.5);
  details.score = score;
  return { score, details };
}
\end{lstlisting}

\bigskip\noindent\textbf{How the rubric maps to code.}
Each scoring function returns 0 (violation), 3 (partial), or 5 (pass) per sub-criterion, which are then combined into a 0--5 dimension score. The script aggregates these per file, then averages across the project to produce the dimension score. This design mirrors the rubric's qualitative descriptors: files that expose server internals to the client boundary score 0, files that partially comply score 3, and files that follow conventions score 5.

The Type \& Contract Safety dimension runs \code{tsc --noEmit} and counts \code{: any} occurrences, while Coverage \& Completeness enumerates required files (\code{is-enabled.ts}, \code{is-enabled.test.ts}, \code{flags.ts}, \code{index.ts}) against a reference checklist. The complete rubric implementation is in \filename{smartkit/scripts/score-flag.ts}.

\section{Evaluation Framework}
\label{sec:evaluation-framework}

The remainder of this chapter reports the locked protocol used to produce the empirical data, and then reports the data itself.

\subsection{Three Dimensions}
\label{sec:dimensions}

The evaluation uses a multi-dimensional quality framework that captures different aspects of boilerplate quality. The framework extends existing benchmark methodology to address framework-specific concerns that existing evaluations overlook; the specific literature gap that motivates this framework is documented in the Related Work chapter. SmartKit's contribution is to instantiate the missing framework-specific convention-adherence measurement dimension for Next.js App Router.

The three dimensions capture distinct, non-overlapping aspects of boilerplate quality that affect real-world usability. Rather than measuring only output correctness, the framework assesses whether generated code can be integrated into production codebases without convention violations or type safety issues. Each dimension maps to an automated measurement approach and corresponds to a specific failure mode observed in AI-generated Next.js code.

\textbf{Unit of analysis.} Scoring is performed per generated file: each file receives one score per dimension, and feature-level scores are computed as the median across constituent files. The median is used rather than the mean because individual files within a feature may exhibit extreme outlier scores due to edge-case generation failures (e.g., a single malformed file), and the median is robust to such outliers.

\textbf{Structural Integrity} assesses whether generated code follows Next.js conventions for file location, naming, Server/Client component boundaries, and App Router patterns. Automated checking uses the \filename{score-flag.ts} script. The dimension captures violations such as incorrect file placement in the \filename{features/} directory, missing \usec directives on client components, and non-standard naming patterns that break routing.

\textbf{Type \& Contract Safety} combines two sub-scores on the 0--5 rubric. The Type Safety sub-score reads \code{tsc --noEmit} error counts and \pkg{@typescript-eslint/}\pkg{no-explicit-any} occurrences; these indicate whether generated code introduces type regressions. The Contract Safety sub-score reads the proportion of API route handlers that include Zod schemas for request/response validation. The two sub-scores combine under the lower-of rule: the dimension score equals the smaller of the two sub-scores.

\textbf{Coverage \& Completeness} evaluates whether generated boilerplate includes all necessary artifacts for a functional feature. \autoref{tbl:coverage-checklist} shows the reference checklist for the \code{isEnabled} feature flag utility used in the pilot. Completeness is measured by enumerating generated files against the checklist and computing a coverage ratio.

\subsubsection{Relationship between SmartKit Integrations and the Pilot Feature}
\label{sec:integrations-and-pilot}

SmartKit instantiates the framework conventions across multiple feature areas, including billing (SePay integration), authentication (Better~Auth), and email (Resend). These integrations exist because the artifact is a usable SaaS boilerplate. The pilot deliberately selects a feature---the feature-flag check utility---that uses \emph{none} of the integrated services, in order to isolate the effect of convention encoding from the effect of having integrated services available. If the pilot used a feature that integrates SePay or Resend, any observed difference between Condition~A and Condition~B would conflate convention encoding with integration availability. The integrations remain first-class in the artifact; their relation to the pilot evaluation is summarised in the scope note at the start of this chapter. This separation is what allows the framework to remain generalisable beyond SmartKit: a developer using a different stack can encode the same conventions without SePay, Resend, or Better~Auth, and the framework still measures the same three dimensions on any generated feature.

A second, related point concerns the role of the integrations during the AI session. In Condition~A, the AI sees the full SmartKit file tree, including \filename{features/billing/} (SePay HMAC, idempotency), \filename{features/auth/} (Better~Auth schemas and server actions), and the Resend email templates under \filename{features/auth/emails/}. These files belong to SmartKit's second role as a usable SaaS boilerplate (see the scope note at the start of this chapter); they encode the SmartKit convention envelope --- feature-based folder structure, colocated server actions, Zod schemas in \filename{types/}, \pkg{server-only} boundaries, and \code{revalidatePath} after mutations. The AI in Condition~A pattern-matches this envelope when generating the pilot feature, even though the pilot feature itself does not call any of the integrated services. In Condition~B, none of these pattern sources are available, so the AI must invent both the utility and its surrounding convention. The score difference between conditions therefore measures the convention envelope, not the integration surface. The convention envelope is what the framework is designed to capture; the integration surface is what makes SmartKit a usable SaaS boilerplate. Both are required for the thesis, but they play distinct roles. The integration surface contributes to the second thesis contribution---the SmartKit artifact as a working SaaS boilerplate---rather than to the pilot; the pilot is the instrument that exercises the framework on AI-generated code, while the integrations are the evidence that the framework conventions are usable in production code.

The standardised prompt's first resolution-order rule---``Per-user DB override, only if \code{userId} is passed''---is implemented in the pilot as a stubbed path: the generated \seqsplit{readUserOverride} helper returns \code{undefined} without querying any database layer, so the pilot feature genuinely touches neither Drizzle nor any external persistence. The stub keeps the resolution order observable in tests while leaving full DB-backed override as future work; this is consistent with the feature's design choice to avoid integrating any SmartKit service, including Drizzle, into the pilot scope. The relationship between this design choice and the Coverage rubric's level definitions (rubric A.5.3) is revisited in the pilot discussion, which explains the structural constraint the design imposes on the Coverage dimension. The corrected Coverage cells and their correction footnote are recorded in \autoref{tbl:pilot-actual} immediately following that table.

\subsection{Rubric interpretation: what the scores measure and what they do not}
\label{sec:rubric-interpretation}

The three rubric dimensions introduced and detailed in this chapter carry different epistemic statuses with respect to the underlying constructs they are taken to represent. This subsection makes those statuses explicit so that pilot results are read within the framework's validated scope, and not beyond it.

\paragraph{Three dimensions, three epistemic statuses.} Each dimension is grounded in a distinct form of evidence, and the strength of the inference from a score to a substantive claim differs accordingly.

Structural Integrity: \emph{directly measured}. The score counts the presence or absence of artifacts at expected paths in the SmartKit feature-sliced layout (file placement, \code{server-only} import detection, \usec{} directive checks, barrel-file verification). Differences between conditions reflect observed counts across runs (e.g.\ on the central artifact path, Cond~A confirmed with all 5 runs passing and Cond~B refuted with 0 out of 5 runs passing), not estimates or judgements, so the dimension-level score is reproducible from the run artefacts without calibration against an external construct.

For Type \& Contract Safety, the score is a \emph{justified proxy for production quality}. The sub-scores combine \code{tsc --noEmit} error counts and Zod-schema coverage at API boundaries; these signals are well-motivated indicators of compile-time and contract-level safety. The cutoffs are asserted design choices; Security review, load testing, observability, and runtime hardening remain outside this dimension's scope.

Coverage \& Completeness reads as an \emph{aspirational developer-experience proxy}. Automated scoring reaches Level 5 in all Cond A runs (file-presence enumeration: all required artifacts present at expected paths). The rubric's Levels 4--5 are designed to require a per-user DB override path, which the no-integration selection criterion excludes by design.\footnote{The Coverage \& Completeness rubric is calibrated to the full convention envelope: Levels 4--5 require a per-user DB override (non-stubbed) and centralised test path, which the no-integration pilot feature structurally cannot produce via automated file-presence detection. Cond~A's Cov $= 5$ reflects the file-presence ceiling for this feature class, not a validated developer-experience ceiling. The operationalisation gap is detailed in \autoref{sec:pilot-rubric} (Dimension 3) and revisited in the threats-to-validity discussion.} Cond~A's Cov = 5 reflects the automated file-presence ceiling for this pilot feature; the predictive claim that this score tracks developer experience awaits empirical validation (future work item 7).

\subsection{Evaluation Design: Rationale and Trade-offs}
\label{sec:design-rationale}

The evaluation framework design involves several deliberate choices that balance scope with feasibility. Prior work on tool-assisted coding includes rule-based static analysis (ESLint, TypeScript) and LLM-based code generation (GitHub Copilot, Claude Code); SmartKit takes a third path by encoding framework conventions at the project-structure level rather than relying on post-hoc validation or prompt engineering.

\textbf{Dimension selection.} The three dimensions were designed to address the gap between output-oriented benchmarks (algorithmic correctness) and the framework-specific quality dimension that existing benchmarks do not measure. Each SmartKit dimension targets a distinct failure mode observed in AI-generated Next.js code: structural violations (file placement, Server/Client boundaries), type safety gaps, and missing boilerplate artifacts.

\textbf{Automated over manual evaluation.} The framework prioritizes automated metrics to enable reproducibility and scale. Expert review provides richer qualitative assessment, but automated checking ensures consistent evaluation across the large number of code samples required for meaningful comparison. Where qualitative judgment is necessary (e.g., structure quality assessment), LLM-as-judge with majority voting is a future option that was not exercised in the executed pilot; the pilot uses single-primary-rater manual scoring (deferred IRR).

\textbf{6-level rubric across dimensions.} Each of the three~dimensions is scored on a 0--5 rubric (six integer levels). The per-dimension cell descriptions are detailed in the rubric table; the rough mapping is: $0$ = missing artefact, $1$ = severe violation, $2$ = partial (in the right neighbourhood but wrong sub-detail), $3$ = acceptable, $4$ = good (level 3 + a specific bonus criterion, e.g.\ \code{server-only} for Structural), $5$ = excellent (level 4 + a second bonus criterion, e.g.\ barrel re-export). The exact level descriptions are dimension-specific and were inferred from related literature on code quality rubrics (the 0--5 scale mirrors industry convention for code-review rubrics); per-level cutoffs have not been calibrated against developer-experience data.

\textbf{Rubric scope, not calibration gap.} The rubric's level definitions are written against the \emph{full} convention envelope that SmartKit encodes (file-system routing, Server/Client boundary primitives, type-safe contract enforcement at boundaries, and integration with the database layer via Drizzle). The executed pilot bounds the framework to a no-integration feature (\code{isEnabled(flagKey, userId?)}) for confound-control reasons, which sets the automated Coverage ceiling at level 5 (all artifact-presence criteria met) rather than at a validated developer-experience ceiling. The same rubric applied to a billing webhook handler would have a different design-stage ceiling. The pilot reports feasibility-stage ordinal scores on the rubric as written; the calibration work that would license developer-experience interpretations is itemised as future work.

\textbf{Single-framework focus.} The evaluation focuses exclusively on Next.js to maintain depth over breadth. Future work should extend the framework to Nuxt and Remix to assess generalizability of the approach.

\textbf{Confound control between conditions.} The pilot feature
(\code{isEnabled(flagKey, userId?)}) was chosen because it
exercises no SmartKit-integrated service: no Resend, Better~Auth,
SePay, or Drizzle dependency beyond the schema. Removing these
integration variables isolates the convention-encoding effect
from service-specific patterns and fixes the design-stage ceiling
for Coverage at level~3 rather than level~5. Three confounds persist:
ecosystem-level reinforcement through sibling features
(\filename{features/auth/}, \filename{features/billing/}); run-order
between the Cond~B block (Runs~1--5) and the Cond~A block
(Runs~6--10); and tool-snapshot drift across the Cond~A block.
The bundled-effect isolation (re-running DP2 with the Cond~B
prompt removing the shared Zod directive) addresses the sibling
confound; a randomized run order at validation sample size
addresses run-order and tool-snapshot drift.

The control artifact serves as the control condition, providing a baseline that isolates the effect of SmartKit's convention encoding from the effect of the underlying technology stack.

Quantitative metrics derive from automated analysis of generated code. \textit{Structural Integrity} uses Biome custom rules to check Next.js-specific file placement, naming, and Server/Client boundary conventions. \textit{Type \& Contract Safety} uses \code{tsc --noEmit} output to identify type violations and custom Biome rules for \emph{any}-type detection and Zod coverage. \textit{Coverage \& Completeness} uses file enumeration against a reference checklist per feature type.

Qualitative metrics derive from expert review of generated code. Reviewers assess whether generated code follows Next.js best practices, whether naming conventions are consistent, and whether the overall implementation aligns with framework expectations. The expert review layer follows an inter-rater reliability (IRR) protocol: two independent raters score the same generated artifacts, with a target Cohen's $\kappa$ $\geq$ 0.7. The automated scoring layer (Biome, \code{tsc --noEmit}) is deterministic and requires no IRR. Execution of the IRR pass is future work (item 3, \S\ref{sec:future-work}).

Productivity metrics such as diff authoring time and developer-reported productivity \parencite{beller2026dat} are not collected in the current pilot and remain future work; the executed pilot reports only per-run time-to-correct (ttc, in minutes) as a coarse timing signal. Task completion time, cyclomatic complexity, maintainability index, and code smell density are documented as design-stage metrics for a future developer-participant study.

\section{Pilot Methodology}
\label{sec:pilot}
\label{sec:pilot-protocol}

This section describes the pilot design: the two conditions being compared, the standardized task, the scoring rubric, and the decision rule for interpreting results.

\subsection{Pilot Design Overview}
\label{sec:pilot-overview}

The demonstration runs one task (generating a feature-flag utility) across two conditions, with five independent runs per condition. Each run produces a score on the 0--5 rubric. The verdict rule classifies the outcome:

\begin{itemize}
    \item \textbf{Confirmed}: all five runs in a condition score $\geq 3/5$.
    \item \textbf{Refuted}: none of the five runs score $\geq 3/5$.
    \item \textbf{Inconclusive}: one to four runs score $\geq 3/5$.
\end{itemize}

This binary verdict answers a feasibility question: can the framework detect a difference between the SmartKit ecosystem and the convention-naive baseline? It does \emph{not} measure how large that difference is. Population-level inference requires approximately 30 runs per condition (future work, \S{}8.2) to achieve sufficient precision for the comparative confidence interval.

The representative feature (\code{isEnabled(flagKey, userId?)}) was selected: it uses no service that SmartKit integrates (no Resend, Better~Auth, SePay, or Drizzle dependency beyond the schema). This choice keeps the comparison clean: by using a feature that touches none of SmartKit's integrated services, the comparison isolates the ecosystem effect (the bundled convention envelope) rather than conflating it with service-specific patterns. The evaluation scenario measures AI-generated boilerplate quality directly: AI systems receive task descriptions, and the generated code is measured against the framework dimensions. The demonstration focuses on Cursor as the primary case study, consistent with the scope defined in the introduction. All evaluations use multiple runs to address non-determinism concerns raised by Ouyang et al.\ \parencite{ouyang2025nondeterminism}; the Cursor tool does not expose user-settable temperature (the snapshot used in the demonstration does not surface this control), so multi-run evaluation substitutes for temperature variation as the determinism-handling mechanism. Results report per-condition medians and ranges, plus Wilson 95\% confidence intervals on the binary pass rate ($\geq 3/5$).

\label{sec:standardized-prompt}

The executed pilot applied the standardized prompt (\autoref{lst:control-prompt}) verbatim to both codebases.

\begin{lstlisting}[

  1. Per-user DB override, only if `userId` is passed.

  - Cache the result in-memory for 5 minutes, keyed by flag and

  - The function should be a server-side utility; do not export it
    to the browser.
  - Define a `FlagKey` type that the function accepts. Use a Zod
    schema to derive it.
  - Include at least 3 unit tests covering: env override, default
    value, and cache hit.
  - Use TypeScript strict mode.

\end{lstlisting}

The prompt intentionally avoids referencing SmartKit-specific conventions (\emph{do not} say ``for SmartKit'', ``follow the feature-based layout'', ``use \filename{.server} naming'', or ``refer to AGENTS.md''). The same prompt applies to both SmartKit and the convention-naive scaffold, so any difference in output quality is attributable to the convention encoding rather than the prompt content. The full pre-registration record, including the frozen prompt hash, is reproduced in the pilot protocol.

The same per-run pipeline was applied to all ten runs, with per-condition aggregates reported in \autoref{tbl:pilot-actual}:
\begin{enumerate}
    \item Initialize a fresh copy of the codebase with the pre-registered tooling verified against a run-day checklist.
    \item Invoke Cursor with the standardized prompt; start the time-to-correct clock.
    \item Collect generated files, Biome violations, \code{tsc --noEmit} output, and artifact enumeration; snapshot the run in \filename{runs/cond-<a,b>/run-<NN>/}.
    \item Score each run on the three-dimension rubric; record per-run JSON plus manual cells; commit before the next run.
\end{enumerate}

\subsection{Run Schedule and Verdict Rule}
\label{sec:pilot-schedule}

The pilot followed a pre-registered adaptive schedule: five runs in Condition~B (Runs~1--5) and five runs in Condition~A (Runs~6--10). Both arms reached adaptive-$N=5$ to satisfy the binary verdict rule and open the comparative-CI gate. The verdict rule in force: 5 out of 5 passing runs resolves as confirmed; 0 out of 5 resolves as refuted; 1 to 4 out of 5 resolves as inconclusive. The full schedule with tool snapshots, verdict counts, and timestamps is in \autoref{tbl:pilot-actual} and the pilot audit trail released in the thesis GitHub repository.

For each run treated as a binary outcome (pass = score $\geq 3/5$; fail = score $< 3/5$), the Wilson 95\% confidence interval on the proportion of passing runs is computed by:
\begin{equation}
\frac{k + \frac{z^2}{2}}{n + z^2} \pm \frac{z}{n + z^2} \sqrt{\frac{k(n-k)}{n} + \frac{z^2}{4}}
\label{eq:wilson}
\end{equation}
where $k$ is the number of passing runs, $n=5$, and $z = 1.96$ for 95\% confidence. The Wilson interval is preferred over the normal approximation (Wald interval) for small $n$ because it never produces bounds outside $[0, 1]$ and has better coverage properties when the true proportion is near 0 or 1. Results are reported as median [min, max] with Wilson 95\% confidence interval (CI) for the pass rate. The formula is in \autoref{eq:wilson}.

A second rater was scheduled to independently score 2 runs (1 per condition) using the same rubric, with Cohen's $\kappa \geq 0.7$ as the threshold for rubric revision. The IRR pass was deferred for lack of a second rater; this deferral is one of the measurement-subset limitations documented in the threats-to-validity discussion (Known Limitation (b): deferred inter-rater reliability) and is restated here as the reason the IRR pass remains a future-work item.
\label{sec:pilot-irr}

\section{Results}
\label{sec:pilot-results}

The pilot applied the three-dimensional framework to one representative task: generating the \seqsplit{isEnabled(flagKey, userId?)} utility using Cursor. The demonstration ran five runs under the SmartKit condition and five runs under the convention-naive scaffold condition. Two of three directional predictions are confirmed, one is confirmed as an instruction-following asymmetry, and one clause is refuted.

\textbf{What the reader should expect.}
The pilot's directional predictions anticipate a clear contrast on two of three dimensions. Cond~A is predicted to score at or near the rubric ceiling because its convention envelope (AGENTS.md, sibling features, FSD layout, Zod patterns) is designed to produce exactly those outputs. Cond~B is predicted to score at or near the floor because its scaffold lacks every convention-encoding signal the framework measures. The binary verdict rule classifies a 5/5 pass rate as confirmed, a 0/5 pass rate as refuted, and 1--4 out of 5 as inconclusive.

\textbf{How to read the ceiling--floor pattern.}
Cond~A's medians sit at rubric ceiling (Structural Integrity 5, Type \& Contract Safety 4, Coverage \& Completeness 5). Cond~B's medians sit near floor (Structural Integrity 2, Type \& Contract Safety 0--3, Coverage \& Completeness 0). Cond~B's Type \& Contract Safety dimension shows the widest within-condition spread (range 0--3); the other two dimensions are stable within each condition. The pattern is feasibility-stage evidence that the framework produces the predicted contrast; population-level inference remains future work.

\textbf{Scoring.} \textit{Structural Integrity} was scored by running the \filename{score-flag.ts} script against the generated files, counting violations per category. \textit{Type \& Contract Safety} was scored by running \code{tsc --noEmit} on the generated code and counting type errors and \emph{any}-type occurrences. \textit{Coverage \& Completeness} was scored by enumerating generated files against a reference checklist. Each dimension is reported on the 0--5 rubric described earlier in this chapter.

\section{Discussion}
\label{sec:discussion}

This section reads the executed scores against the rubric mechanics and issues three directional-prediction verdicts: confirmed, refuted, or inconclusive based on whether all, none, or some runs met the passing threshold.

\subsection{DP1 -- Structural Integrity Placement}
\label{sec:dp1-results}

\textbf{Confirmed.} Cond~A placed the utility at the predicted path \filename{features/flags/lib/is-enabled.ts} in all five runs. Cond~B placed it at root \filename{lib/} in all five runs. The pattern is consistent with an ecosystem-level mechanism: the SmartKit codebase exposes \filename{AGENTS.md}, sibling features under \filename{features/}, and the established placement in adjacent features; the convention-naive scaffold exposes none of these, so generated output falls back to root-level placement.

\subsection{DP2 -- Type \& Contract Safety (Zod-derived FlagKey)}
\label{sec:dp2-results}

\textbf{Confirmed as instruction-following asymmetry}: Cond~A
produced a Zod-derived \code{FlagKey} enum in all 5 runs and
Cond~B produced a raw \code{string} type alias in all 5 runs.
The standardized prompt, the dependency surface, and the explicit
Zod directive (``use a Zod schema to derive'') were identical
across conditions, so the asymmetry is not attributable to a
missing-package effect on Cond~B. The attribution question that
remains is whether the asymmetry reflects the SmartKit
convention-encoding effect or instruction-following reinforcement
that the ecosystem incidentally enables: Cond~A's prompt bundles
the directive with three ecosystem-level reinforcement signals
absent from Cond~B (AGENTS.md, colocated Zod schemas in
\filename{features/auth/} and \filename{features/billing/}, and
the Zod patterns in \filename{src/database/schema/}), and a
compliant Cond~A run cannot be attributed to the directive, the
ecosystem, or the dependency in isolation. Adjudicating between
the two explanations requires the bundled-effect isolation
experiment (future-work item~4), which re-runs DP2 with the
Cond~B prompt removing the shared Zod directive.

\textbf{What this verdict means.} The framework detected a difference between
conditions on Type \& Contract Safety: Cond A consistently produced Zod-derived
types while Cond B produced raw string types. However, the pilot design cannot
determine whether this outcome stems from convention encoding in the SmartKit
ecosystem or from instruction-following reinforcement that the ecosystem
incidentally provides. Resolving this attribution requires isolating the
Zod directive from the ecosystem effect, which is the purpose of the
bundled-effect experiment planned as Future Work item 4.

\subsection{DP3 -- Coverage \& Completeness (Centralized Test Path)}
\label{sec:dp3-results}

\textbf{DP3-A: confirmed.} The SmartKit condition placed a test file at the predicted centralized path in all five runs.
\textbf{DP3-B: refuted.} The convention-naive scaffold placed a test file at the repository root in all five runs, the opposite of the prediction.

\subsection{Synthesis}
\label{sec:discussion-synthesis}

Two findings are consistent across predictions. DP1 and DP3-A both show Cond~A placements matching the predicted FSD paths in all 5 runs, indicating that structural-convention signals (AGENTS.md, sibling features, FSD layout) orient placement when present. DP2's confirmed-asymmetry verdict and DP3-B's refutation together show that the SmartKit ecosystem's contribution is not uniform: the ecosystem reinforces directives that match its existing patterns (DP2) and produces consistent placement (DP1, DP3-A), but does not suppress default test-generation behaviour in Cond~B (DP3-B). The DP3-B refutation is read as a positive finding about the framework's discriminative capacity rather than as a contradiction of the DP1/DP2 outcomes.

\paragraph{Scope of these verdicts.} Verdicts are binary-rule outcomes, not parameter estimates. The Wilson 95\% confidence interval at five runs has a half-width of approximately 0.21, too wide to support frequentist hypothesis testing at this sample size. The comparison is an ecosystem-level demonstration (SmartKit vs convention-naive scaffold), not an isolated test of any single convention-encoding mechanism; the bundled-effect limitation, the per-arm coverage design consequence for Cond~A, and the cross-arm coverage consequence for Cond~B are consolidated in \autoref{sec:threats} together with a caveat that applies only to the Coverage \& Completeness dimension and does not affect the Structural Integrity placement verdicts in DP1 and DP3-A.

\subsubsection*{Analytical Discussion}
The four subsections below analyse the pilot results beyond the verdict descriptions in \S\ref{sec:pilot-results}. Each subsection addresses one analytical question: mechanism (which convention-encoding effect did the pilot actually exercise), alternative explanations (which the pilot cannot rule out), comparison to the AI-code-generation literature (what the results add on top of HumanEval and SWE-bench), and implications (what the framework tells practitioners and researchers to do next).

\subsection{Mechanism Interpretation}
\label{sec:mechanism-interpretation}

The ceiling--floor pattern (Cond~A medians at rubric ceiling: Str 5, T\&C 4, Cov 5; Cond~B medians near floor: Str 2, T\&C 1, Cov 0) warrants interpretation beyond the verdict descriptions. Three mechanisms are consistent with the observed pattern, and the pilot design separates which mechanisms it can and cannot test.

\textbf{Structural-convention signals orient placement when they are present.} DP1 (Structural Integrity placement) and DP3-A (Coverage \& Completeness, centralized test path) both show Cond~A placements matching the predicted FSD paths in all five runs. Cond~B places these at root-level paths. AGENTS.md, sibling features, and the FSD layout are visible in Cond~A and absent in Cond~B. The consistent 5/5 contrast on placement dimensions indicates that the visible codebase structure does orient AI-generated file placement.

\textbf{The ecosystem reinforces directives that match its existing patterns.} DP2 (Zod-derived FlagKey) produced the predicted contrast (Cond~A Zod, Cond~B raw string), but the pilot cannot attribute this to convention encoding alone. The Cond~A prompt bundles the Zod directive with three reinforcing signals: the AGENTS.md directive, the colocated Zod schemas in sibling features, and the Zod patterns in the database schema. This thesis answers the question \emph{whether} convention encoding works at the ecosystem level. It does not answer \emph{which component} drives the effect. The bundled-effect isolation experiment (Future Work item~4) is designed to answer that follow-up question.

\textbf{The ecosystem does not suppress default generation behaviour on dimensions it does not prime.} DP3-B (Cond~B test placement) was refuted: Cond~B placed tests at the repository root in all five runs, opposite of the prediction. This result is consistent with DP1 and DP2. The SmartKit ecosystem's contribution is bounded to conventions that are explicitly encoded or pattern-matched. It does not actively redirect AI default generation behaviour on dimensions where the AI has not been primed.

\subsection{Alternative Interpretations}
\label{sec:alternative-interpretations}

Three alternative explanations for the ceiling--floor pattern are worth stating explicitly so the reader can see which the pilot rules out and which it leaves open.

\textbf{Alternative A (instruction-following reinforcement):} Cond~A's advantage could reflect the explicit directive cues (AGENTS.md instruction, Zod directive in prompt, sibling Zod schemas) rather than structural convention encoding. Under this explanation, a Cond~A run with AGENTS.md removed but the directive intact would still produce the ceiling effect. The pilot cannot adjudicate this. Future Work item~4 re-runs DP2 with the Cond~B prompt removing the shared Zod directive, which is the minimum experiment that can distinguish directive reinforcement from convention encoding.

\textbf{Alternative B (tool-specific behaviour):} The ceiling--floor pattern could be specific to Cursor's context-awareness features (AGENTS.md parsing, codebase indexing) rather than a generalizable convention-encoding effect. Under this explanation, GitHub Copilot and Claude Code would not reproduce the pattern. Cross-tool replication (Future Work item~1) is the minimum experiment that can rule out tool specificity.

\textbf{Alternative C (coincidental alignment):} Cond~B's consistent floor scores could be an unlucky draw from a wider distribution rather than a systematic convention-naive scaffold effect. The binary rule (5/5 vs.\ 0/5) mitigates this concern on the two dimensions where the verdict was extreme. Population-level inference still requires the larger-$N$ replication in Future Work item~2, because the binary rule at $n=5$ cannot distinguish a true proportion of 0.50 from 0.80 within Wilson 95\% confidence intervals.

\subsection{Comparison to AI-Code-Generation Literature}
\label{sec:literature-comparison}

The pilot results map onto the broader AI-code-generation literature in two ways.

HumanEval and SWE-bench measure problem-solving and bug-fixing capability; neither assesses whether AI-generated code adheres to framework conventions. The ceiling--floor pattern in Table~\ref{tbl:pilot-actual} indicates that convention adherence is a distinct dimension from algorithmic correctness. Cond~A scored 5/5 on Structural Integrity (correct file placement) and 4/5 on Type \& Contract Safety (non-trivial Zod usage). Cond~B scored 2/5 on Structural Integrity (root-level placement) and 0/5 on Coverage \& Completeness (no test file). A benchmark that assessed only algorithmic correctness would not detect this contrast. The two conditions would both produce correctly implemented utility functions. The three-dimensional rubric captures a quality dimension that existing benchmarks do not.

Yeti\c{s}tiren et al.\ report that GitHub Copilot generated valid code for 91.5\% of HumanEval problems ($n=164$), with 28.7\% fully correct and 20.1\% incorrect~\parencite{yetistiren2022assessing}. Their failure mode concerns functional correctness on algorithmic tasks. The SmartKit framework addresses structural correctness and convention adherence on boilerplate-generation tasks. Both failure modes apply to production-ready AI-assisted development. The framework complements functional-correctness benchmarks rather than replacing them.

\subsection{Implications}
\label{sec:implications}

\textbf{For practitioners.} Developers using AI coding assistants with Next.js App Router should expect that framework conventions (Server/Client boundaries, file placement, Zod typing) are not automatically followed by AI assistants unless the conventions are explicitly encoded in the project structure. A boilerplate that encodes conventions at the file-system level (SmartKit's approach) produces measurable convention adherence in AI output. A bare scaffold does not. Teams adopting AI-assisted Next.js development should consider structural convention encoding (AGENTS.md, FSD layout, colocated type patterns) as part of their AI-tooling setup.

\textbf{For researchers.} The ceiling--floor pattern across five runs per condition provides preliminary evidence that framework-convention adherence is measurable with a rubric that operates on real generated artifacts. The bundled-effect limitation means that the mechanism (AGENTS.md, FSD layout, Zod patterns, or their combination) cannot be isolated from the current pilot design. Future research on AI-framework alignment should design experiments that isolate individual convention-encoding mechanisms. The bundled-effect isolation experiment in Future Work item~4 is the minimum next step.

\section{Threats to Validity}
\label{sec:threats}

The threats-to-validity taxonomy below organizes the limitations of the pilot under four categories.
\begin{itemize}
    \item \textbf{External Validity} covers transfer across frameworks.
    \item \textbf{Measurement Validity} covers rubric cutoffs and inter-rater reliability.
    \item \textbf{Internal Validity} covers rubric-calibration consequences and protocol deviations.
    \item \textbf{Conclusion Validity} covers alternative explanations.
\end{itemize}
This section is the analytical taxonomy, with each category discussed against the executed pilot rather than the pre-registered design.

\subsection{External Validity}
\label{sec:external-validity}

\textbf{Generalizability.} The pilot produced directional predictions about AI-generated Next.js App Router boilerplate, bounded to that framework. Whether they hold for Nuxt (Vue) or Remix is unverified. The framework's three dimensions are designed for portability, but cross-framework claims require framework-specific instantiation first; the cross-framework extension to Nuxt and Remix is future work (item~5).

\subsection{Measurement Validity}
\label{sec:measurement-validity}

\textbf{Rubric cutoffs and scoring protocol.} The pilot's three rubric dimensions produce ordinal, reproducible scores on the framework's Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness dimensions. The cutoffs (0--1: serious violations, 1--2: minor, 2--3: acceptable, 3--4: good, 4--5: excellent) are design choices; the mapping from rubric levels to developer-relevant outcomes is not empirically calibrated. IRR validation of the rubric (item 3, \S\ref{sec:future-work}) is required before rubric scores can be claimed to track developer-relevant quality grades.

\textbf{Coverage \& Completeness rubric operationalization gap.} The Coverage rubric is calibrated to the full convention envelope: levels $4$--$5$ require a non-stubbed per-user override path and centralised test path, which the no-integration pilot feature structurally cannot produce via automated file-presence detection. Automated scoring reaches Cov $= 5$ for Cond~A across all 5 runs (file-presence enumeration); the gap between the automated ceiling and the rubric's Levels 4--5 design intent (per-user DB override) is documented in \autoref{sec:pilot-rubric} and addressed as future work.

\subsection{Internal Validity}
\label{sec:internal-validity}

\textbf{Cov ceiling operationalization gap.} The Coverage \& Completeness rubric (\S\ref{sec:pilot}) defines levels $4$--$5$ as requiring the per-user override path to be ``implemented (not stubbed --- i.e.\ returns a value derived from the database)'' and the centralised test path. The pilot feature (\code{isEnabled(flagKey, userId?)}) was chosen specifically to avoid any SmartKit integration including the database layer. Automated file-presence scoring therefore reaches Cov $= 5$ for Cond~A across all 5 runs (\autoref{tbl:pilot-actual}); this is the file-presence ceiling reachable for this feature class, not the rubric's design ceiling (which requires a non-stubbed per-user DB override path that the no-integration selection criterion rules out by design). The automated ceiling and the rubric's Levels 4--5 design intent are not the same construct; reconciling them is future work.

\textbf{Bundled-effect (DP2) and design confounds.} The inability to isolate the contribution of individual SmartKit components is a deliberate scope decision. The SmartKit ecosystem was designed as a joint convention envelope: AGENTS.md, FSD structure, and Zod patterns are architecturally complementary and are adopted together in practice. Measuring them jointly tests the design hypothesis that convention encoding works through multiple reinforcing signals; measuring them in isolation would answer a different question about component-level contribution. The latter is future work (item 4); the former is the question this pilot was designed to answer. The Cond~A prompt contains both the shared Zod directive and the SmartKit ecosystem's colocated Zod configuration; the Cond~B prompt contains only the shared directive. A compliant Cond~A run cannot be attributed to either factor in isolation, and the Cond~B non-compliance does not adjudicate which factor was load-bearing. The locked run schedule executed Cond~B first (Runs~1--5), then Cond~A (Runs~6--10); time-of-day, session-memory, and experimenter-familiarity confounds cannot be ruled out across these blocks, and the Cond~A block itself spans two tool snapshots so the run-order confound and the tool-snapshot difference are partially entangled for that condition. A fully randomized run order is future work. Item 4 addresses the bundled-effect isolation by re-running DP2 with the Cond~B prompt removing the shared Zod directive.

\subsection{Conclusion Validity}
\label{sec:conclusion-validity}

\textbf{Alternative explanations.} The confirmed DP1 and DP2 verdicts cannot, by themselves, distinguish ``structural convention-encoding benefit'' from ``instruction-following asymmetry that the structural convention incidentally enables'', because Cond~A's prompt bundles both the AGENTS.md structural directives and the explicit instruction-following cues that Cond~B's prompt also contains. This bundled-effect limitation is addressed by future work item 4 (re-run DP2 with the Cond~B prompt removing the shared Zod directive to isolate the structural convention-encoding contribution from the prompting contribution). Whether the same directional verdicts would emerge under alternative solution strategies (prompting-only, linter-based enforcement, enhanced documentation) is future work.

\chapter{Conclusion and Future Work}
\label{sec:conclusion}

\section{Summary}

\textbf{Research Question 1} asks how the evaluation framework can be consistently designed to measure AI assistant adherence to Next.js App Router conventions. The framework properties (FP1--FP3) in Chapters 4 and 5 demonstrate that the three-dimensional rubric (Structural Integrity, Type \& Contract Safety, Coverage \& Completeness) can be operationalised on real AI-generated code.

\textbf{Research Question 2} asks whether the framework demonstrates applicability. The directional prediction verdicts (DP1--DP3) in \S\ref{sec:dp1-results}, \S\ref{sec:dp2-results}, and \S\ref{sec:dp3-results} show that the framework produces measurable contrast between the SmartKit and convention-naive conditions: DP1 (structural placement) and DP3-A (centralized test path) are confirmed; DP2 (Zod-derived FlagKey) is confirmed as instruction-following asymmetry; DP3-B is refuted.

The primary contribution of this thesis is the design of a three-dimensional evaluation framework for assessing AI-generated Next.js boilerplate convention adherence. Two supporting instantiations demonstrate the framework's utility. SmartKit is a working Next.js boilerplate that embodies the framework's conventions. A bounded feasibility pilot, with five runs per condition on one representative feature, demonstrates that the framework produces measurable scores on real AI-generated code. The pilot is a feasibility check, not an empirical test; the verdicts are binary-rule outcomes, not parameter estimates. Two of the three directional predictions are confirmed outright (DP1, structural placement; DP3-A, centralized test path); one is confirmed as an instruction-following asymmetry rather than as a convention-encoding benefit (DP2, Zod-derived FlagKey type); and one is refuted (DP3-B, where Cond~B produced root-level test files). The full verdicts and disclosed protocol adaptations are in the pilot discussion and the threats-to-validity section. Quantitative claims are bounded by the limitations documented in the threats-to-validity discussion, which the thesis treats as the canonical reference rather than restating them at each reporting point. The framework, artefact, and executed demonstration are intended as a foundation for larger-$N$ replication, cross-tool validation, and developer-participant studies, all documented in the future-work discussion.

\medskip\noindent\textbf{Ceiling--floor pattern.} Cond~A medians sit at or near rubric ceiling (Str $5$, T\&C $4$, Cov $5$); Cond~B medians near floor (Str $2$, T\&C $1$, Cov $0$). Cond~A Cov $= 5$ reflects automated file-presence enumeration (cf. \autoref{sec:threats}).

\section{Future Work}
\label{sec:future-work}

\textbf{(1)~Cross-tool replication.} Replicate the pilot using alternative AI coding assistants (GitHub Copilot, Claude Code) to assess whether the framework's dimensional scores are tool-specific or generalize across AI tools. The directional predictions (DP1--DP3) can be tested on each tool, producing a per-tool verdict table. This addresses the single-tool evaluation limitation disclosed in the abstract.

\textbf{(2)~Validation-stage replication at $n \approx 30$ per arm.} Increase per-arm sample size to a validation-stage quantity (effect size $h = 0.5$, $\alpha = 0.05$, power $0.8$, two-proportion chi-squared approximation) so that the comparative Bonferroni 99\% CI on the $A-B$ difference provides inferential leverage rather than collapsing to a single point at the binary-rule stage.

\textbf{(3)~Execute the IRR pass.} Re-execute the pre-registered second-rater IRR pass (Cohen's $\kappa \geq 0.7$) over a representative slice of runs once a second rater becomes available. The current pilot uses automated-only scoring; IRR validation is required before rubric scores can be claimed to track developer-relevant quality grades.

\textbf{(4)~Re-run DP2 with Cond~B prompt removing the Zod directive (bundled-effect isolation).} Instruct Cond~B to use raw \code{string} only, removing the shared Zod directive, to isolate the structural convention-encoding contribution from the prompting contribution. A compliant Cond~A run on the as-modified Cond~B would attribute DP2 to ecosystem reinforcement rather than to the directive alone, addressing the bundled-effect limitation disclosed in \autoref{sec:threats}.

\textbf{(5)~Cross-framework extension (Nuxt, Remix).} Instantiate the framework in Nuxt (Vue) and Remix environments to assess whether the directional predictions hold outside Next.js App Router. The three dimensions are designed for portability but require framework-specific instantiation (Nuxt file-based routing via \filename{/pages/}, \code{useAsyncData()}, \code{.client.vue} suffix; Remix flat routes via \filename{/routes/}, \code{loader}/\code{action} functions, \code{ErrorBoundary} components).

\textbf{(6)~Developer-participant study.} Pair SmartKit-generated and
unstructured Next.js codebases with recruited developers and measure task
completion time, code quality, and developer-reported productivity, following
the methodology of Peng et al.\ \parencite{peng2023impact} and extending the
direction established in Tariq et al.\ \parencite{tariq2026enterprise} (pending
peer review). This validates whether the structural-convention effect observed
in the pilot extends to real developer workflows.

\textbf{(7)~Rubric calibration against developer-experience evidence.} The Coverage \& Completeness dimension is interpreted as an aspirational developer-experience proxy; a developer-participant study that pairs each rubric level (0, 1, 2, 3) with developer-reported time-to-integrate and onboarding-friction ratings is needed before the Coverage score can be claimed to track a developer-relevant construct. Error handling, security review, and performance are also candidates for additional dimensions in a future revision of the rubric.
