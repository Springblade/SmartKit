\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

AI coding assistants such as GitHub Copilot and Cursor are now in daily use. By 2025, 84\% of developers reported using or planning to use AI tools (up from 76\% in 2024), and 51\% of professional developers used them daily \parencite[Figure~2]{stackoverflow2025}. For boilerplate-heavy tasks the gains are large: Peng et al.\ report a 55.8\% completion-time reduction on a controlled JavaScript HTTP-server task \parencite{peng2023impact}, and Liang et al.\ surveyed 410 developers and found that the strongest motivators for using AI programming assistants are reducing keystrokes, finishing tasks quickly, and recalling syntax; the main barrier is that suggestions often miss functional or non-functional requirements \parencite{liang2024survey}. The benchmarks that dominate the literature, including HumanEval, MBPP+, APPS, BigCodeBench, and LiveCodeBench for algorithms and SWE-bench for bug fixing, measure problem-solving and patch generation, not whether AI-generated code respects framework conventions. Server/Client boundary violations in Next.js App Router, for instance, fail at runtime in a way no static type check catches.

This thesis presents a design-stage contribution: a three-dimensional evaluation framework for AI-generated Next.js boilerplate and instantiates it in SmartKit, an open-source Next.js 16.2.12 boilerplate that acts as both the framework's target codebase and a usable SaaS scaffold. The framework scores each generated feature on Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness, each reported on a 0--5 scale. A bounded feasibility demonstration ran 10 times on one feature: $n=5$ per condition (Cond~A: SmartKit ecosystem; Cond~B: convention-naive scaffold) with both arms at adaptive-$N=5$, unlocking the comparative Bonferroni 99\% CI on the $A-B$ difference. The demonstration is an \emph{ecosystem comparison} (SmartKit vs.\ convention-naive scaffold), not an isolated test of any single convention-encoding mechanism; the asymmetry between the two conditions is how the ecosystem comparison works, not a confound. One of three directional predictions is confirmed outright under the binary rule (structural placement); one is confirmed as an instruction-following asymmetry rather than as a convention-encoding benefit (Zod-derived FlagKey type); and one is asymmetric, confirmed in Condition~A and refuted in Condition~B, reported as such rather than collapsed into a single verdict. The DP2 instruction-following asymmetry is consistent with the ecosystem-comparison framing. It confirms that the SmartKit ecosystem produces Zod-derived output even though both conditions receive the same prompt directive, while the convention-naive scaffold does not.

The pilot provides feasibility-stage evidence rather than an inferential test. Per-arm samples are too small for inferential statistics, and three protocol adaptations are disclosed: a tool substitution for runs $6$--$10$, and two-clause reporting of the asymmetric prediction introduced after data collection. Larger-$N$ replication, cross-tool validation, and developer-participant studies remain future work.

\chapter{Introduction and Motivation}
\label{sec:introduction}

The chapter opens with the recent wave of AI coding assistants and the parallel shift in Next.js toward the App Router, then identifies the absence of an evaluation framework for framework-specific convention adherence. From that gap the chapter derives the research objectives, questions, and hypotheses that structure the rest of the thesis, and closes with the scope within which the SmartKit framework is designed and evaluated.

\section{Overview}

Controlled studies report substantial productivity gains from AI coding assistants. Peng et al. showed that developers using GitHub Copilot completed tasks 55.8\% faster than control groups \parencite{peng2023impact}, while Yetiştiren et al. reported that GitHub Copilot generated valid code for 91.5\% of HumanEval problems ($n=164$), with 28.7\% fully correct, 51.2\% partially correct, and 20.1\% incorrect \parencite{yetistiren2022assessing}. Next.js has emerged as the dominant React meta-framework for production web applications, with its App Router architecture introduced in version 13 fundamentally changing application structure through React Server Components and explicit Server/Client boundaries \parencite{nextjsdocs}. The failure mode that motivates this thesis is concrete (Figure~\autoref{fig:motivated-example}): when an AI coding assistant generates a Server Component that imports a Client Component and passes an event handler as a prop, Next.js produces the runtime error ``Event handlers cannot be passed to Client Component props''---a failure that \code{tsc --noEmit} cannot catch because it has no type-level representation. During SmartKit's development, recurring AI generation errors were observed firsthand in Next.js App Router code, including authentication security flaws, component boundary violations, and outdated API usage from older training data; these are development-time observations rather than measured prevalence figures. Without systematic evaluation, developers cannot assess whether AI-generated Next.js code adheres to framework conventions or will fail in production.

Existing benchmarks address algorithmic problem-solving and bug-fixing capabilities but not framework convention adherence. HumanEval evaluates Python code generation for standalone functions \parencite{chen2021evaluating}; SWE-bench assesses AI ability to resolve GitHub issues \parencite{jimenez2024swebench}; a systematic review of 395 LLM-for-SE studies found that framework-convention adherence is not separately tracked as an evaluation category --- the SLR's metric inventory organizes evaluation by problem type (generation, classification, recommendation, regression) rather than by benchmark-versus-human-evaluation split, and 338 of 395 studies (~86\%) used generation-task metrics such as BLEU-4 (62 studies), Pass@k (54), and Accuracy@k (39) to assess code-synthesis quality \parencite{hou2024llmse}. None of these capture the specific architectural requirements of Next.js App Router, such as Server/Client component boundaries, type-safe contracts, or file-system routing conventions. The gap means developers have no framework-specific quantitative basis for comparing AI tools on these tasks.\footnote{RigorBench \parencite{rigorbench2026}, an as-yet-unreviewed preprint with a self-disclosed author conflict of interest (the authors co-developed the Agent-Rigor framework that RigorBench evaluates), addresses an adjacent concern---engineering process discipline---and is referenced here for completeness rather than as a load-bearing citation for the gap claim above.}

\textbf{Intended users.} SmartKit targets solo developers and small teams (2--5 members) working on Next.js projects with AI coding assistants. They are intermediate developers who already understand React and TypeScript fundamentals and want to reduce boilerplate setup time while enforcing consistent conventions in AI-assisted development. The framework supports incremental adoption: teams can apply the feature-based folder structure and Server/Client boundary conventions without committing to the full stack.

The thesis makes two distinct contributions. The first is the design of the three-dimensional evaluation framework and its instantiation in SmartKit. The second is a bounded feasibility demonstration that the framework can be operationalised on real AI-generated code. The demonstration evidences (2); it does not estimate (1)'s empirical effect. Inferring the latter requires a larger-$N$ replication ($n \approx 30$ per arm) and is documented as future work (\S7.2).

\section{The Problem: AI Convention Violations in Next.js}

This thesis addresses a concrete problem: AI coding assistants consistently generate Next.js App Router code that violates framework conventions, producing runtime errors and technical debt, yet no evaluation framework exists to measure this adherence. Three principal challenges shape the framework design.

First, framework conventions are implicit and distributed across documentation, error messages, and community patterns. Enumerating them into testable metrics is itself an open problem. Second, AI-generated code failures in Next.js manifest at runtime rather than compile time --- the Server/Client boundary error ``Event handlers cannot be passed to Client Component props'' only fires when the component is executed, so the framework needs dynamic analysis rather than static linting alone. Third, the three evaluation dimensions are designed to be orthogonal: a structural-integrity violation does not imply a type error, and a coverage gap operates independently of both. Collapsing them into a single composite score would hide which dimension is actually regressing. The orthogonality of the three dimensions is asserted at design stage and awaits empirical validation; the executed pilot's per-arm sample is far below the $n \approx 30$ required to confirm that the dimensions vary independently in practice (Section~\autoref{sec:future-work} documents a Pearson correlation analysis as future work).

The focus on Next.js App Router is deliberate. First, market dominance makes it the primary target: community surveys consistently place Next.js among the most widely adopted React meta-frameworks \parencite{nextjsdocs}; in the Stack Overflow 2025 Developer Survey, Next.js is reported at 20.8\% in the web-frameworks-and-technologies category, ahead of Express (19.9\%) and Angular (18.2\%) \parencite[1, Stack Overflow Developer Survey]{stackoverflow2025}. Second, training-data mismatch is a recognized failure mode of LLM-based code assistants: Wu et al.\ introduced VersiCode, a benchmark spanning 300 Python libraries and 2{,}000+ versions over 9 years, and showed that version-controllable code generation (version-specific completion and version-aware migration) is a significant challenge even for frontier models \parencite{versicode2024}. Third, practical feasibility applies: the author has existing Next.js expertise, enabling direct testing of enforcement mechanisms. The pilot targets Cursor because its AGENTS.md feature implements documentation-based guidance, an approach consistent with prior research suggesting that explicit context and structured prompts improve AI coding-assistant output quality \parencite{barke2022grounded,zhang2023practices}.

\section{Research Objectives and Questions}

While Next.js dominates React meta-framework adoption and AI coding assistants such as GitHub Copilot and Cursor have demonstrated substantial productivity gains, there is a distinct gap at the intersection of these two areas: a systematic, operationalizable evaluation framework that measures how closely AI-generated Next.js boilerplate code adheres to framework-specific conventions. Existing benchmarks---HumanEval, SWE-bench---address algorithmic problem-solving and bug-fixing capability, but none capture the architectural requirements of Next.js App Router such as Server/Client component boundaries, type-safe contracts, or file-system routing conventions \parencite{chen2021evaluating,jimenez2024swebench}. This thesis targets precisely that gap.

The primary motivation of this thesis is to bridge this gap by designing a three-dimensional evaluation framework that turns an implicit set of framework conventions into measurable, comparable scores, and by instantiating that framework in SmartKit, a structured Next.js boilerplate that provides the necessary enforcement mechanisms and the evaluation target codebase.

The research pursues three objectives:
{\sloppy
\begin{itemize}
    \item \textbf{Design a three-dimensional evaluation framework.}
    Construct a framework that scores AI-generated Next.js boilerplate
    code along three dimensions: Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness, so that convention adherence becomes a quantitative,
    comparable property of generated code.
    \item \textbf{Implement SmartKit as a structured architecture.}
    The thesis releases SmartKit, an open-source Next.js boilerplate
    that demonstrates feature-based modularity, explicit Server/Client
    boundaries, and type-safe contracts, providing both the enforcement
    mechanisms and the target codebase for the framework.
    \item \textbf{Demonstrate framework applicability through a bounded
    feasibility run.} The thesis applies the framework to a representative
    feature generated by Cursor under the SmartKit condition to verify that
    the framework can produce scores on real AI-generated code.
\end{itemize}
}

Consequently, this research seeks to answer the following research questions:
\begin{enumerate}
    \item How can an evaluation framework be consistently designed to
    measure AI coding assistant adherence to Next.js App Router boilerplate conventions along the Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness dimensions?
    \item Can the resulting framework be operationalized into measurable
    metrics, and does it demonstrate applicability when applied to
    representative AI-generated Next.js features?
\end{enumerate}

These objectives and questions give rise to two classes of claims, both
documented as design-level pre-registrations to be exercised by the pilot
(§6.2). The first class states \textbf{framework
properties}---descriptive claims about whether the framework can measure
the dimensions it targets. The second class states \textbf{directional
predictions}---falsifiable claims about the sign of the score difference
between conditions, to be reported as confirmed, refuted, or inconclusive.

\paragraph{Framework properties.} The pilot is designed to demonstrate that
the framework can be operationalised on a real artifact:
\begin{itemize}
    \item \textbf{FP1 (Structural Integrity).} The framework can measure
    the dimension it targets---file placement, Server/Client boundary
    usage, and naming patterns---on AI-generated Next.js code, yielding
    a per-run score on a representative feature.
    \item \textbf{FP2 (Type \& Contract Safety).} The framework can measure
    the dimension it targets on AI-generated Next.js code, yielding a
    per-run score on a representative feature by combining Type-Safety
    and Contract-Safety sub-scores under the framework's weakest-link
    combination rule.
    \item \textbf{FP3 (Coverage \& Completeness).} The framework can
    enumerate AI-generated files against a feature-specific checklist
    and yield a per-run score reflecting required-artifact presence.
\end{itemize}

\paragraph{Directional predictions.} Each directional prediction states
the expected sign of the difference between Condition~A (SmartKit at full
setup) and Condition~B (convention-naive scaffold) on a representative
feature---the \code{isEnabled(flagKey, userId?)} utility. Predictions are
evaluated as \emph{confirmed} (all runs in the predicted direction),
\emph{refuted} (no runs in the predicted direction), or
\emph{inconclusive} (intermediate), per the adaptive-N protocol
documented in §6.2.

\begin{itemize}
    \item \textbf{DP1 (Structural).} Condition~A is predicted to place the
    utility in the SmartKit feature-based layout in the majority of runs;
    Condition~B is predicted to use a root-level or flat structure.
    \item \textbf{DP2 (Type \& Contract).} Condition~A is predicted to
    produce Zod-typed schema definitions in the majority of runs;
    Condition~B is predicted to use raw string types.
    \item \textbf{DP3 (Coverage).} Condition~A is predicted to include a
    centralized test file in the majority of runs;
    Condition~B is predicted to omit a test file in the majority of runs.
\end{itemize}

Framework properties and directional predictions serve different
purposes. A framework property is a descriptive claim about the
framework itself; it cannot be refuted by pilot data, only supported or
unsupported. A directional prediction is a falsifiable claim about the
artifact and is the only class of claim to which the binary
\emph{confirmed/refuted/inconclusive} verdict applies. The pilot
protocol (§6.2) documents how each is reported. Full
statistical validation---including larger sample sizes, cross-tool
replication, and developer-participant studies---remains future
empirical work.

Designing an evaluation framework for AI-generated Next.js boilerplate encounters three key challenges that distinguish it from existing code generation benchmarks. First, framework conventions are implicit and distributed across documentation, error messages, and community patterns, requiring deliberate extraction into enumerable, testable rules rather than relying on predefined quality criteria. Second, convention violations in Next.js App Router manifest primarily at runtime. Server/Client boundary violations produce errors only when executed, so evaluation must go beyond static analysis to capture dynamic execution behaviour. Third, the evaluation dimensions are orthogonal: structural integrity violations do not imply type errors, and coverage gaps operate independently of both, demanding a multi-dimensional framework rather than a single composite score. Pearson correlation analysis across runs (Section~\autoref{sec:future-work}) would empirically test whether the three dimensions are genuinely orthogonal or merely weakly coupled; the executed pilot's small per-arm sample precludes such analysis.

This thesis makes three contributions. First, it proposes a three-dimensional evaluation framework (Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness) for measuring how closely AI coding assistants adhere to Next.js App Router conventions. The framework addresses a gap left by existing benchmarks, which score algorithmic correctness rather than framework-specific quality. The framework is operationalized through an \emph{ecosystem comparison}: a SmartKit condition (with AGENTS.md, sibling features, FSD layout, and Zod patterns) versus a convention-naive scaffold (with none of these), so the pilot measures the SmartKit ecosystem as a whole rather than isolating any single convention-encoding mechanism. Second, it releases SmartKit, an open-source Next.js boilerplate demonstrating feature-based modularity, explicit Server/Client boundaries, and type-safe contracts. SmartKit supplies both the conventions the framework measures and the target codebase it measures them on; all four Better Auth tables (user, session, account, verification), the billing feature (SePay integration with HMAC signature verification and idempotent webhook handling), and the email integration (Resend + React Email) are implemented at the current snapshot rather than deferred to future phases, supporting SmartKit's role as a functional SaaS boilerplate. Third, it releases the pilot protocol and the baseline comparison design as artefacts: a pre-registration document, a Condition~A vs.\ Condition~B comparison scaffold, a scoring rulebook, and a baseline-bootstrap script. These artefacts are concrete enough that another researcher can replicate the pilot without re-deriving the protocol from the thesis prose.

\section{Scope and Limitations}

To keep the empirical rigor and feasibility of this research within the resource envelope of a single-author thesis, the scope is strictly defined by the following parameters and limitations:

\begin{enumerate}
    \item \textbf{Framework scope:} Next.js App Router only. No comparison with Nuxt, Remix, or other meta-frameworks.
    \item \textbf{AI assistants:} Cursor used for the bounded feasibility demonstration. Broader AI assistant evaluation (GitHub Copilot, Claude Code) is future work.
    \item \textbf{Project type:} Single representative Next.js project demonstrating SaaS patterns.
    \item \textbf{Pilot study limitation:} The feasibility demonstration is a worked-example executed against a total of $10$ runs under a pre-registered adaptive schedule, distributed as $n=5$ Cond~A and $n=5$ Cond~B on a single representative feature, the \code{isEnabled(flagKey, userId?)} utility, which uses no service that SmartKit integrates. Both arms are at symmetric adaptive-$N=5$, so the comparative Bonferroni 99\% CI on the $A-B$ difference is now populated, but the per-arm sample is still far below the $n \approx 30$ required for inferential validation (Section~\autoref{sec:future-work}). Cross-tool replication, larger-$N$ studies, and developer-participant validation remain future empirical work.
\end{enumerate}

These boundaries are deliberate methodological choices. Fixing the framework, the AI assistant, and the project type removes confounding variance so that any measured difference between structured and unstructured conditions can be attributed to the SmartKit approach alone.


\chapter{Background}
\label{sec:background}

Understanding the intersection of AI coding assistants and Next.js development requires grounding in three domains: AI coding tool capabilities and limitations, Next.js architectural patterns, and SaaS boilerplate design principles.

\section{AI Coding Assistants}

GitHub Copilot, Anthropic's Claude, and Cursor all use transformer-based LLMs fine-tuned for code understanding and generation. GitHub Copilot provides inline code completions and entire function generation within supported editors (using OpenAI's GPT series and Anthropic's Claude series models, with specific model versions varying over time). Anthropic's Claude offers conversational code assistance through the Claude Code CLI and IDE integrations. Cursor combines Claude with a custom codebase indexing system that enables context-aware suggestions across entire projects.

These assistants share common architectural elements. They process code through transformer-based models trained on large corpora of publicly available source code, learning statistical patterns that inform code generation. When producing completions, they consider surrounding code context, natural language comments, and project-wide information to generate relevant suggestions. Their effectiveness varies with programming language, task complexity, and code structure \parencite[code quality evaluation study]{yetistiren2023evaluating}.

Research documents both strengths and limitations. Dakhel et al.\ found that AI assistance benefits expert developers who can filter suboptimal suggestions but may harm novice developers who lack the expertise to identify incorrect or inefficient code \parencite{dakhel2023github}. Liu et al.\ documented that ChatGPT performs better on older problems (pre-2021) than newer ones, with a 48.14\% advantage on the Accepted rate, though it struggles with complex algorithms and domain-specific code, frequently generating solutions with security vulnerabilities and inefficient implementations \parencite{liu2024chatgpt}.

The task taxonomy for AI suitability shows that boilerplate generation represents a strength area. Zhang et al. mined Stack Overflow and GitHub Discussions and found that developers primarily use Copilot for code generation in general-purpose languages (JavaScript, Python) on VS Code, with data processing as the most common function category and difficulty of integration as the dominant limitation \parencite{zhang2023practices}. Pandey et al. documented Copilot time savings of up to 50\% in code documentation and autocompletion, and 30--40\% in repetitive coding, unit-test generation, debugging, and pair programming; the tool struggled with complex tasks, large functions, multiple files, proprietary contexts, and C/C++ code \parencite{pandey2024transforming}. These findings focus the study on boilerplate interaction as an appropriate domain for AI enhancement.

\section{Next.js Framework Architecture}

Next.js is a React meta-framework that provides server-side rendering, static site generation, and API capabilities within a unified application model. Version 13 introduced the App Router paradigm, fundamentally changing how React applications structure pages, layouts, and data fetching. Developers who learned the Pages Router encounter several App Router concepts that the older model did not surface, including Server/Client boundaries and file-system conventions for special files.

React Server Components represent a core innovation in Next.js App Router. These components execute exclusively on the server, which lets them access databases and sensitive operations directly without exposing logic to the client. The distinction between Server and Client components requires explicit marking through the \\usec directive, creating a boundary that developers must carefully manage. Incorrect placement of components across this boundary produces runtime errors and performance degradation.

The App Router organizes applications through a file-system-based routing mechanism. Each folder within the \filename{app/} directory corresponds to a route segment, with \filename{page.tsx} files defining the content for each route. Special files such as \filename{layout.tsx}, \filename{loading.tsx}, and \filename{error.tsx} provide shared UI and error handling across route hierarchies. This convention-driven structure enables rapid scaffolding but requires adherence to specific naming and placement patterns.

TypeScript integration in Next.js emphasizes type safety throughout the application. The framework provides typed interfaces for page properties, API request and response objects, and data-fetching results. Achieving full type coverage requires consistent use of TypeScript patterns including generics, utility types, and strict mode configuration. AI coding assistants may generate code that compiles but violates framework conventions, producing runtime errors or subtle bugs.

\section{SaaS Boilerplate Patterns}

SaaS applications share common requirements that boilerplate frameworks address: user authentication, database access patterns, multi-tenancy support, and deployment configurations. The economics of SaaS development favor approaches that reduce per-project initialization effort while maintaining code quality and consistency.

Krüger et al.\ established that platform reuse reduces maintenance effort but involves upfront investment in framework adoption and learning curve \parencite{kruger2020empirical}. The trade-off explains the appeal of well-designed boilerplate templates that amortize initialization cost across multiple projects. Aleem et al.\ identified customization, scalability, multi-tenancy, security, integration, and fault tolerance as key factors in SaaS architecture decisions \parencite{aleem2019maturity}.

Modern scaffolding approaches build on model-driven architecture principles. Inayatullah and Azam presented a UML-based DSML that automatically generates scaffolding CRUD code for cross-platform (web + mobile) applications from class diagrams, reducing repetitive implementation effort \parencite{inayatullah2019model}. Liu and Sra recently showed that LLMs have potential to automatically generate scaffolded user interfaces, reducing complexity for users in professional creative software \parencite{liu2025auggen}.

Meta-framework evaluation identifies architectural trade-offs across options. The framework-adoption literature identifies learnability, extensibility, and ease of migration as primary drivers of adoption, while framework lock-in and high configurability are commonly cited as adoption risks \parencite{storey2016frameworkadoption}. Next.js App Router emphasizes React Server Components as a first-class primitive while maintaining full compatibility with Client Components for interactive UI. This hybrid model creates specific conventions that boilerplate frameworks should encode.

\chapter{Related Work}
\label{sec:relatedwork}

This section surveys existing research on code generation benchmarks, empirical studies of AI-assisted development, and systematic literature reviews on AI for software engineering. The analysis identifies the specific gap this thesis addresses: the absence of framework-specific evaluation for AI coding assistants operating on Next.js boilerplate conventions.

\section{Code Generation Benchmarks}

The evaluation of AI coding assistants relies heavily on standardized benchmarks that measure code generation capability. Chen et al.\ introduced HumanEval as a foundational benchmark containing 164 hand-written programming problems with function signatures, docstrings, and unit tests \parencite{chen2021evaluating}. The benchmark evaluates models using Pass@1, Pass@10, and Pass@100 metrics. OpenAI's Codex achieved 28.8\% Pass@1 on this benchmark, establishing a baseline for subsequent model development.

HumanEval focuses exclusively on single-function Python code generation with algorithmic and reasoning requirements. The design prioritizes general programming capability over domain-specific or framework-aware generation. Yu et al.\ extended the benchmark concept with HumanEval Pro, adding self-invoking code generation tasks that require models to generate functions calling previously defined functions \parencite{yu2025humanevalpro}. Their work found that most LLMs exhibit a 10--15 percentage-point absolute drop on self-invoking tasks compared to standalone tasks (e.g., o1-mini falling from 96.2\% to 76.2\% Pass@1 on HumanEval Pro), indicating that current benchmarks underestimate real-world code generation complexity.

SWE-bench represents a substantial advance in benchmark realism by evaluating AI models on real GitHub issues from popular Python repositories \parencite{jimenez2024swebench}. Each task requires understanding the issue description, locating relevant code, implementing a fix, and passing unit tests. Jimenez et al.\ found that state-of-the-art models resolved only a small fraction of issues --- Claude 2 solved approximately 1.96\% with BM25 retrieval (4.8\% with oracle retrieval) and GPT-4 only 1.74\% with oracle retrieval (0\% with BM25) --- and the gap between benchmark performance and practical software engineering capability is substantial.

Language-specific benchmarks identify further evaluation limitations. Petrukha et al.\ developed SwiftEval for Swift programming, finding that general-purpose benchmarks overestimated Swift code generation capability \parencite{petrukha2025swifteval}. Their language-specific benchmark documented substantial score drops (up to roughly 60 points for the smallest open-source models, with smaller drops for frontier models) when evaluating the same models on Swift versus HumanEval-style Python problems.

No existing benchmark evaluates framework convention adherence, boilerplate structure quality, TypeScript or Next.js-specific patterns, or multi-file scaffolding tasks. The benchmarks measure whether AI assistants can solve algorithmic problems or fix bugs in existing codebases, not whether they can generate framework-compliant boilerplate from scratch.

Several extensions and alternatives warrant mention. Liu et al.\ developed HumanEval+ and MBPP+ as rigorous extensions of the original benchmarks, finding that pass rates drop by 19.3--28.9\% on average across 26 evaluated LLMs when evaluated against additional auto-generated high-quality tests per problem \parencite{liu2024correct}. Zhuo et al.\ introduced BigCodeBench, which evaluates 1,140 fine-grained tasks combining diverse function calls with complex natural-language instructions \parencite{zhuo2024bigcodebench}. Hendrycks et al.\ proposed APPS, a 10,000-problem benchmark spanning introductory, interview, and competition-level coding challenges \parencite{hendrycks2021apps}. Jain et al.\ addressed the critical contamination problem through LiveCodeBench, which sources problems from recent competitive programming contests published after model training cutoffs \parencite{jain2024livecodebench}. Li et al.\ developed CodeReviewer for code review automation, an adjacent evaluation direction that assesses code quality dimensions relevant to AI-assisted development workflows \parencite{li2022codereviewer}. Each of these benchmarks measures distinct aspects of code generation or code quality capability, yet none evaluate the framework-specific convention adherence that the SmartKit framework targets.

\section{Empirical Studies on Developer Productivity}

Several empirical studies examine how AI assistance affects real developer workflows. Peng et al.\ conducted the seminal controlled experiment on GitHub Copilot with 95 recruited developers implementing an HTTP server in JavaScript \parencite{peng2023impact}. Their methodology used a treatment-control design with matched tasks, finding the 55.8\% completion time improvement cited earlier. Heterogeneous effects showed that less experienced developers benefited most from AI assistance.

The enterprise-level .NET study by Tariq et al.\ (SSRN, 2026; not peer-reviewed) extended this methodology to enterprise software development scenarios \parencite{tariq2026enterprise}. With 60 developers and 960 task observations across eight enterprise-oriented tasks, they measured task completion time, implementation errors, cyclomatic complexity, maintainability index, code smells, and NASA-TLX cognitive load scores. AI-assisted development reduced task completion time, errors, code smells, and cognitive workload while improving maintainability. The trade-off was that AI generated redundant abstractions and increased code verbosity, with effectiveness depending on developer expertise and continued oversight. Note that the Tariq et al. study focuses on .NET enterprise settings; its findings are cited as methodology precedent rather than as evidence about Next.js or AI-tool-specific effects.

Liu et al.\ assessed ChatGPT code generation quality across multiple languages and task types \parencite{liu2024chatgpt}. ChatGPT performs better on pre-2021 problems with a 48.14-percentage-point advantage on Accepted rate (68.41\% versus 20.27\%), but its ability to directly fix erroneous code through multi-round dialogue is relatively weak. Generated code often contained security vulnerabilities and inefficient implementations requiring human verification, though ChatGPT could resolve over 89\% of identified vulnerabilities through multi-round fixing. In a separate comparison, the same authors found that across 728 LeetCode problems in five languages, AI-generated Python3 solutions had an 8 percentage-point lower share of low-cognitive-complexity submissions than human-written solutions, while cyclomatic complexity distributions closely resembled the human baseline for Python3 (with a 5 percentage-point offset in C++ for cyclomatic) \parencite{liu2024chatgpt}. Yetiştiren et al.\ separately found, in their code quality evaluation study, that ChatGPT, Copilot, and CodeWhisperer all generated code with maintainability issues --- particularly improper naming and high cognitive complexity --- at technical-debt averages of 8.9, 9.1, and 5.6 minutes respectively \parencite{yetistiren2023evaluating}.

AlOmar et al.\ examined developer-ChatGPT refactoring conversations, finding that developers frequently needed multiple iterations to achieve satisfactory refactoring \parencite{alomar2024refactoring}. AI often missed design-level improvements, and common anti-patterns emerged in developer-AI refactoring interactions. AI effectiveness therefore depends on the structure of the interaction and on the developer's ability to guide refinement, not only on the tool itself.

Hou et al.\ conducted a systematic literature review of 395 research articles on LLMs for software engineering from 2017--2024 \parencite{hou2024llmse}. Code generation (118 papers, approximately 30\% of the corpus) and program repair (35 papers, approximately 9\%) are the two most-studied application areas. The review's metric inventory groups evaluation by problem type rather than by benchmark-versus-human split: 338 generation-task studies used 19 metric families (BLEU-4 in 62 studies, Pass@k in 54, Accuracy@k in 39), 147 classification-task studies used nine metric families (Precision in 35, Recall in 34, F1-score in 33), 39 recommendation-task studies used six metric families, and 1 regression-task study used MAE \parencite{hou2024llmse}. Reported effectiveness varies widely by task type. The review identified research gaps in security, requirements engineering, and empirical studies. Framework-specific boilerplate evaluation would begin to address these gaps.

Russo et al.\ developed the Human-AI Collaboration and Adaptation Framework (HACAF), which identifies nine theoretical dimensions across individual (perceived usefulness, ease of use, behavioural intention), technological (compatibility, relative advantage, complexity), and social (social influence, environmental support, self-efficacy) levels \parencite{russo2024navigating}. Technical capability was necessary but insufficient on its own; the present thesis reads their analysis as indicating that human factors including trust, skill, and workflow integration are necessary alongside technical capability for developer-tool adoption. Evaluating framework-specific boilerplate tools therefore requires attention to how well they integrate with developer workflows and support skill development.

\section{Evaluation Methodology}

The refinement of AI-generated code has received attention as a complementary evaluation dimension. Liu et al. analyzed 4,066 ChatGPT-generated programs across 2,033 programming tasks in Java and Python \parencite{liu2024refining}. Of these programs, 2,756 were deemed correct, 1,082 produced wrong outputs, and 177 contained compilation or runtime errors; 1,930 additional programs suffered from maintainability issues identified through static analysis. Their automated refinement pipeline using static-analysis feedback improved code quality by more than 20\%. Evaluation frameworks should therefore measure both initial generation quality and the effort required for refinement.

Ouyang et al. studied the non-determinism of ChatGPT in code generation \parencite{ouyang2025nondeterminism}. Across 829 problems in three benchmarks, the ratio of coding tasks with zero equal test output across different requests ranged from 47.56\% (HumanEval) to 75.76\% (CodeContests). Setting the temperature to 0 does not guarantee determinism, despite being a common practice. Reliable assessment therefore requires multiple runs with confidence intervals rather than single-point measurements.

Beller et al. proposed the DAT framework for measuring software development productivity, developed by the Developer Insights team at Meta \parencite{beller2026dat}. The approach combines diff authoring time, survey-based metrics, and AI tool-specific productivity measures. The DAT framework models a path for evaluating AI-boilerplate interaction that balances quantitative performance metrics with qualitative developer experience assessment.

Nguyen-Duc et al. distilled a research agenda of 78 open RQs across 11 software-engineering areas --- including requirements engineering, design, construction, testing, maintenance, and education --- where the current literature is comparatively sparse \parencite{nguyenduc2025genai}. The agenda explicitly calls for standardized evaluation and longitudinal studies, requirements that framework-specific evaluation frameworks can begin to satisfy.

Sauvola et al.\ projected four primary future scenarios for generative AI in software development, ranging from legacy integration to clean-slate and networked development, with software production shifting toward higher-level design and oversight roles as routine coding tasks become increasingly automated \parencite{sauvola2024future}. Research on optimizing AI interaction patterns, including framework-specific boilerplate conventions that reduce the cognitive overhead of AI-assisted development, follows from this projection.

\section{Research Gap Summary}

The reviewed literature establishes that AI coding assistants improve developer productivity on repetitive tasks, that boilerplate generation represents an AI strength area, and that existing benchmarks measure algorithmic capability rather than framework convention adherence. To the author's knowledge---given the structured-but-non-exhaustive literature search described in the next section---no prior work has specifically evaluated AI tool effectiveness on Next.js App Router conventions, React Server Components patterns, TypeScript-first boilerplate structures, or full-stack framework-specific best practices. This gap is independently supported by Hou et al.\ (2024)'s systematic review of 395 LLM-SE articles, which does not list framework-specific convention adherence as a separately tracked evaluation category \parencite{hou2024llmse}; the review's research gaps (security, requirements engineering, empirical studies) likewise do not overlap with framework-specific boilerplate evaluation. This thesis proposes a Next.js boilerplate framework engineered for AI interaction and an evaluation methodology that measures framework-specific quality dimensions, reporting both as design-stage contributions.

\section{Alternative Approaches to AI-Codebase Alignment}

The structural approach taken by SmartKit is one of several strategies that researchers and practitioners have explored to improve AI-codebase alignment. This section reviews these alternatives and justifies why the structural approach was selected for this thesis.

Linter and formatter configurations (ESLint, Prettier, TypeScript compiler) can catch some convention violations but operate after code generation rather than before it. These tools validate style and type-correctness, not semantic feature boundaries; they cannot enforce Server/Client component conventions that require architectural awareness at the structure level. Linters operate alongside SmartKit's structural conventions rather than substituting for them: Biome 2.5.6 is included in SmartKit as a post-hoc consistency check on top of the convention envelope.

The structural approach taken by SmartKit addresses these limitations by encoding conventions at the project structure level. Conventions become discoverable by AI systems through file location and naming patterns, are enforced through project structure rather than developer vigilance, and provide reusable templates that scale across features. The structural approach works alongside prompting and documentation, not as a replacement.

\chapter{Proposed Solution}
\label{sec:solution}

This section presents the design of SmartKit, a Next.js boilerplate framework engineered to optimize interaction with AI coding assistants. The design synthesizes empirical findings from the literature with domain-specific analysis of Next.js conventions to produce a codebase structure that improves AI comprehension and output quality.

\section{Design Rationale}

Empirical findings on developer practices inform the SmartKit design. Zhang et al.\ surveyed developers and found that Copilot is primarily used for code generation in general-purpose languages (JavaScript, Python) on VS Code, with data processing as the most common function category and integration difficulty as the dominant limitation \parencite{zhang2023practices}. This finding motivates the focus on boilerplate interaction as an appropriate domain for AI enhancement. Barke et al.\ observed that programmers interact with Copilot in two modes --- acceleration (Copilot executes a known plan) and exploration (Copilot helps discover APIs) --- and documented four prompting strategies in their codebook: code prompts (71.4\% in acceleration) and context prompts (15.2\% in acceleration) as unintentional strategies, and comment prompts (57.2\% in exploration versus 13.1\% in acceleration) and the multi-suggestions pane as intentional strategies \parencite{barke2022grounded}. The SmartKit design applies these findings through three concrete architectural decisions: encode conventions explicitly, group related code narrowly, and define type-safe contracts.

\textbf{Feature-based modularity over layer-based organisation.} Many Next.js projects organise code by technical layer (\filename{components/}, \filename{lib/}, \filename{hooks/}) or by page. Layer-based organisation creates wide import graphs: a single component may transitively import from dozens of files, so an AI system generating a new component receives a large, undifferentiated context. Feature-based modularity confines all code for one feature (schemas, actions, components, emails, types) within a single directory, giving the AI a narrow, self-contained context window. The trade-off is that cross-cutting concerns (shared utilities, types, or components) require deliberate extraction to a shared layer; this overhead is acceptable for SaaS boilerplate where the feature boundary is the primary decomposition axis.

\textbf{Drizzle ORM over Prisma.} Prisma uses a schema-first DSL (\filename{.prisma} file) that generates a client; Drizzle uses a TypeScript-first schema directly in \filename{.ts} files, colocated with the application code. I considered Prisma first because the schema-first DSL is easier to onboard onto. Then I read three RealWorld-tier codebases that mixed Prisma schemas with TypeScript business code, and the boundary confused the AI in every case. Drizzle's TypeScript-first approach won out for this thesis despite the steeper SQL learning curve: with Drizzle the AI reads and extends the schema using the same language model it uses for the rest of the codebase, and schema changes propagate through TypeScript's own type inference without a separate code-generation step.

\textbf{Explicit Server/Client boundaries over tRPC-based type sharing.} tRPC provides end-to-end type inference across the Server/Client boundary by sharing a single TypeScript interface definition. This eliminates a class of type errors but requires a separate router definition and does not enforce the architectural boundary at the file level. SmartKit instead uses Next.js's native \usec directive for Client Components and the \pkg{server-only} import for server-only utilities, supplemented by Zod schemas shared across the boundary. The native mechanism is framework-default rather than library-specific, which means the conventions survive beyond the SmartKit codebase and transfer to plain Next.js projects; tRPC conventions do not. The trade-off is that the native mechanism requires explicit developer discipline; tRPC enforces the boundary automatically through its type system. Per-feature Zod schemas are colocated under \filename{features/<name>/types/} so the same definition is the source of truth for both runtime validation (server action) and TypeScript inference (client component props); this location convention is described alongside the schema in §4.1.2.

\textbf{Zod schemas as the single source of truth across the Server/Client boundary.} React Server Components and Client Components communicate through typed props, but there is no built-in mechanism to ensure that the type on the server matches the type on the client. SmartKit uses Zod schemas, defined once in \filename{features/<name>/types/}, parsed at the server action boundary, and reused on the client via \pkg{z.infer}. This means a single schema definition is the source of truth for both runtime validation (server action) and TypeScript type inference (client component props), and the AI can read and extend the schema using the same Zod syntax it encounters in existing features. The trade-off is that Zod adds a runtime dependency and a learning curve for developers unfamiliar with schema-first validation.

\section{Feature-Based Modular Architecture}

Many Next.js projects organize code by technical layer (components/, lib/, hooks/) or by page structure. SmartKit instead adopts feature-based modularity, where each feature contains all code necessary for its functionality. An authentication feature, for instance, includes database schemas, API routes, React components, form validation schemas, and email templates within a single directory.

This organization improves AI comprehension by narrowing the search space for relevant context when AI generates code for a specific feature. The scope of changes becomes explicit, which reduces the risk of AI-generated code violating feature encapsulation. The organization also creates natural boundaries for testing and deployment that align with developer mental models.

The feature directory structure follows a consistent pattern across all features:

\section{Server/Client Boundary Conventions}

React Server Components introduce an explicit boundary between server-only and client-accessible code. SmartKit uses Next.js's native Server/Client boundary mechanism through the \usec directive for Client Components and the \pkg{server-only} import for server-only utilities. The pattern extends Next.js's convention-based routing to component architecture.

Server/Client boundaries affect data flow design. Server Components can access databases and environment variables directly, while Client Components must receive data through props or server actions. AI systems can invoke type-safe server actions from Client Components, which keeps
data flow consistent as new components are generated.

\section{Database Schema Patterns}

SmartKit uses Drizzle ORM with PostgreSQL to provide type-safe database access throughout the application. The schema design follows conventions that AI systems can learn and reproduce. Each table schema includes columns with explicit types, relations defined with foreign keys, and indexes specified for query optimization.

The Drizzle schema pattern enables AI-generated code to access the database through type-safe query builders. AI systems can examine existing schema patterns and generate consistent queries that maintain type safety across the application. Ad-hoc database access that bypasses type checking or violates query conventions is discouraged.

Schema files for Better Auth's shared tables (\code{user}, \code{session}, \code{account}, \code{verification}) are all implemented in \filename{src/database/schema/}, an infrastructure layer outside the Feature-Sliced Design (FSD) hierarchy, alongside the billing-specific tables (\code{billing}, \code{payment\_transactions}) used by \filename{features/billing/}. The four Better Auth tables cover the \code{user} identity, the \code{session} and \code{account} records used for sign-in flows, and the \code{verification} table for email-verification challenges; relations between them are declared in \filename{src/database/schema/relations.ts}. All Drizzle schema definitions are kept in this single directory so that \pkg{drizzle-kit} can scan them reliably and all features can import from a common location. The placement keeps database patterns centralized while remaining directly importable from any feature module.

\section{Type-Safe API Contracts}

API routes in SmartKit use Zod schemas for request and response validation. These schemas serve dual purposes: runtime validation of incoming requests and TypeScript type inference for handler code. AI systems can examine Zod schemas to understand API contracts, generating code that respects type constraints without requiring explicit type annotations.

The shared schema pattern enables consistent validation across frontend form components and backend API handlers. The same Zod schemas validate both client-submitted forms and server-handled requests. The match between frontend and backend validation reduces the gap between AI-generated client-side and server-side code, producing more coherent implementations.

\subsection{Stack Selection Rationale}
\label{sec:stack-rationale}

Each component of the stack was chosen because it reinforces one of the three evaluation dimensions rather than for its own sake. The selection rests on three guiding principles:

\begin{enumerate}
  \item \textbf{App Router-first.} Next.js~16's App Router is the architectural surface that Structural Integrity measures directly: Server/Client boundaries, file-system routing, and the \usec/\pkg{server-only} primitives are framework defaults rather than library conventions, which means the rules encoded in the rubric transfer to plain Next.js projects rather than coupling them to SmartKit.
  \item \textbf{Type-safe contracts at the boundary.} TypeScript~5.7 strict mode provides the compile-time signal that Type~\&~Contract Safety reads from \code{tsc --noEmit}, while Zod~4 schemas colocated in \filename{features/<name>/types/} are parsed at the Server Action boundary and reused on the client via \pkg{z.infer}. A single schema is the source of truth on both sides of the Server/Client boundary that Coverage~\&~Completeness checks for, so the AI tooling reads and extends the same Zod syntax it encounters in existing features.
  \item \textbf{Server/Client boundary as a first-class primitive.} The framework's runtime failures (event handlers crossing the boundary, server-only imports leaking to the client) are the failure mode the thesis targets, so the chosen tools must surface those failures naturally: Server Components fetch data directly through Drizzle, Server Actions in \filename{features/<name>/actions/} call \code{revalidatePath} after writes, and Client Components receive typed props without an intermediate client-side data layer. Adopting a tRPC-style shared-router alternative would have hidden the boundary inside library types and removed the very signal the Structural Integrity rubric is designed to read.
\end{enumerate}

The \filename{app/} directory is placed at \filename{src/app/} because that is the path Next.js~16's App Router reads as the routing surface. The \filename{database/} directory is placed at \filename{src/database/} because \pkg{drizzle-kit} reads schemas from a single configured path; co-locating every table in \filename{database/schema/} means a migration scan touches one root rather than chasing feature-local schema files. The directory therefore functions as a third tier, sitting above \filename{src/features/<name>/} in the import graph, for code that every feature may need but no feature owns. The \code{env.ts} reader belongs here for the same reason: the database client, the auth handler, and the billing webhook all read environment variables, so the reader sits at a level that all three can import without forming a cycle.

The \filename{features/flags/} directory sits at the repository top level rather than inside \filename{src/}. This placement is deliberate: the AGENTS.md rule that new feature code should live under a feature-named directory does not enforce a \filename{src/} prefix for the pilot's representative feature, and keeping \filename{features/flags/} at the top lets the AI encounter it immediately when scanning the repo root. \subsection{Feature Flag Resolution}
\label{sec:feature-flag-resolution}

The feature flag system implements a three-tier resolution hierarchy that evaluates override sources in priority order. This design reflects the convention encoding principle: per-user overrides take precedence over environment variables, which take precedence over static defaults. The implementation is located in \filename{features/flags/lib/is-enabled.ts}, which is marked \pkg{server-only} to enforce the server-side boundary.

The Zod schema that defines the allowed \code{FlagKey} values is colocated in \filename{features/flags/types/flags.ts}:

\begin{lstlisting}[
  language=TypeScript,
  caption={Zod schema for feature flag keys.},
  label={lst:flag-key-schema},
  basicstyle=\ttfamily\scriptsize,
]
import { z } from "zod";

export const FlagKeySchema = z.enum([
  "FEATURE_NEW_DASHBOARD",
  "FEATURE_BILLING_ENABLED",
  "FEATURE_DARK_MODE",
]);

export type FlagKey = z.infer<typeof FlagKeySchema>;
\end{lstlisting}

The \code{isEnabled} function implements the three-tier resolution with in-memory caching:

\begin{lstlisting}[
  language=TypeScript,
  caption={The isEnabled utility with three-tier resolution and 5-minute TTL cache.},
  label={lst:is-enabled-impl},
  basicstyle=\ttfamily\scriptsize,
]
import "server-only";
import { FlagKeySchema, type FlagKey } from "../types/flags";

const TTL_MS = 5 * 60 * 1000;

// Two parallel maps -- values holds the resolved boolean, expirations
// holds the wall-clock timestamp at which the entry expires.
const values = new Map<string, boolean>();
const expirations = new Map<string, number>();

const buildCacheKey = (flag: FlagKey, userId?: string): string =>
  userId ? `${flag}__${userId}` : `${flag}___`;

const readUserOverride = (
  _userId: string | undefined,
  _flag: FlagKey,
): boolean | undefined => {
  // Per-user DB override is not wired in this pilot.
  return undefined; // signals "no override, fall through"
};

const readEnvOverride = (flag: FlagKey): boolean | undefined => {
  const raw = process.env[`FLAG_${flag}`];
  if (raw === "true") return true;
  if (raw === "false") return false;
  return undefined;
};

export function isEnabled(
  flag: unknown,
  fallback: boolean = false,
  userId?: string,
): boolean {
  const parsed = FlagKeySchema.safeParse(flag);
  if (!parsed.success) {
    throw new Error(
      `Invalid flag key: ${JSON.stringify(flag)}. ` +
        `Allowed: ${FlagKeySchema.options.join(", ")}`,
    );
  }
  const key = buildCacheKey(parsed.data, userId);
  const now = Date.now();

  const expires = expirations.get(key);
  if (expires !== undefined && expires > now) {
    const cached = values.get(key);
    if (cached !== undefined) return cached;
  }

  let resolved: boolean | undefined =
    readUserOverride(userId, parsed.data) ??
    readEnvOverride(parsed.data) ??
    fallback;

  values.set(key, resolved);
  expirations.set(key, now + TTL_MS);
  return resolved;
}
\end{lstlisting}

\bigskip\noindent\textbf{Why this structure?}
The tiered design serves two purposes: (1) it mirrors the production pattern where feature flags support gradual rollouts via environment variables before per-user targeting, and (2) it creates a clear server-side boundary that the Structural Integrity dimension reads---the function is marked \pkg{server-only} in the barrel export, never accessible to client components without a typed prop interface. The 5-minute TTL prevents unbounded memory growth while keeping flag values reasonably fresh for environment-driven rollouts.

\subsection{Evaluation Infrastructure}
\label{sec:eval-infrastructure}

To operationalize the three evaluation dimensions, the framework includes an automated scoring script (\filename{scripts/score-flag.ts}) that reads source files and computes a 0--5 score per dimension. The script is read-only: it does not mutate the run directory and does not call any AI/LLM for scoring.

The structural integrity scoring logic detects server/client boundary violations:

\begin{lstlisting}[
  language=TypeScript,
  caption={The structural integrity scoring logic from score-flag.ts.},
  label={lst:scoring-logic},
  basicstyle=\ttfamily\scriptsize,
]
// Pattern detection for server-only imports
const SERVER_ONLY_PATTERNS = [
  /import\s+["']server-only["']/,
  /from\s+["']server-only["']/,
];

async function scoreStructural(runDir: string) {
  const tsFiles = await findTsFiles(runDir);
  let hasServerOnly = false;
  let hasUseClient = false;

  for (const f of tsFiles) {
    const content = await readFile(f, 'utf-8');
    hasServerOnly = SERVER_ONLY_PATTERNS.some(
      p => p.test(content)
    );
    hasUseClient = /['"]use client['"]/.test(content);
  }

  // Scoring: path_match (0/0.5/1) + feature_complete (0/0.5/1)
  let pathMatch = 0;
  let featureComplete = 0;

  if (inFeatures) pathMatch = 1;
  if (hasServerOnly) featureComplete = 1;
  if (hasUseClient) featureComplete = 0; // violation

  return Math.round((pathMatch + featureComplete) * 2.5);
}
\end{lstlisting}

\bigskip\noindent\textbf{How the rubric maps to code.}
Each scoring function returns 0 (violation), 3 (partial), or 5 (pass) per sub-criterion, which are then combined into a 0--5 dimension score. The script aggregates these per file, then averages across the project to produce the dimension score. This design mirrors the rubric's qualitative descriptors: files that expose server internals to the client boundary score 0, files that partially comply score 3, and files that follow conventions score 5.

The Type \& Contract Safety dimension runs \code{tsc --noEmit} and counts \code{: any} occurrences, while Coverage \& Completeness enumerates required files (\code{is-enabled.ts}, \code{is-enabled.test.ts}, \code{flags.ts}, \code{index.ts}) against a reference checklist. The complete rubric implementation is in \filename{smartkit/scripts/score-flag.ts}.

\section{Evaluation Framework}
\label{sec:evaluation-framework}

\subsection{Three Dimensions}
\label{sec:dimensions}

The evaluation uses a multi-dimensional quality framework that captures different aspects of boilerplate quality. The framework extends existing benchmark methodology to address framework-specific concerns that existing evaluations overlook; the specific literature gap that motivates this framework is documented in the Related Work chapter (\autoref{sec:relatedwork}). SmartKit's contribution is to instantiate the missing framework-specific convention-adherence measurement dimension for Next.js App Router.

The three dimensions capture distinct, non-overlapping aspects of boilerplate quality that affect real-world usability. Rather than measuring only output correctness, the framework assesses whether generated code can be integrated into production codebases without convention violations or type safety issues. Each dimension maps to an automated measurement approach and corresponds to a specific failure mode observed in AI-generated Next.js code.

\textbf{Unit of analysis.} Scoring is performed per generated file: each file receives one score per dimension, and feature-level scores are computed as the median across constituent files. The median is used rather than the mean because individual files within a feature may exhibit extreme outlier scores due to edge-case generation failures (e.g., a single malformed file), and the median is robust to such outliers.

\textbf{Structural Integrity} assesses whether generated code follows Next.js conventions for file location, naming, Server/Client component boundaries, and App Router patterns. Automated checking uses the \texttt{score-flag.ts} script (file-placement checks, \texttt{server-only} import detection, \texttt{'use client'} directive checks, barrel-file verification) specific to Next.js structural conventions. The dimension captures violations such as incorrect file placement in the \filename{features/} directory, missing \usec directives on client components, and non-standard naming patterns that break routing.

\textbf{Type \& Contract Safety} captures two related but distinct quality signals, treated as sub-scores that combine into a single Type \& Contract Safety score on the 0--5 rubric. \emph{Type Safety sub-score} focuses on compile-time checks: \code{tsc --noEmit} error counts and \pkg{@typescript-eslint/}\pkg{no-explicit-any} occurrences signal whether generated code introduces type regressions into the codebase. \emph{Contract Safety sub-score} focuses on runtime validation: the proportion of API route handlers that include Zod schemas for request/response validation indicates whether the generated feature is schema-validated at the API boundary (input parsing and type narrowing enforced at runtime via Zod), not production-deployment-ready without additional hardening such as security review and load testing (see \autoref{sec:threats}). Sub-score combination rule: the Type \& Contract Safety dimension score equals the lower of (Type Safety sub-score, Contract Safety sub-score) on the 0--5 scale, reflecting that a single weak sub-signal is not offset by a strong other. This combination rule is an inferred design choice (alternative rules such as arithmetic mean or weighted product could be substituted without changing the underlying sub-scores); the chosen lower-of rule privileges robustness against hidden weakness in either sub-dimension.

\textbf{Coverage \& Completeness} evaluates whether generated boilerplate includes all necessary artifacts for a functional feature. \autoref{tbl:coverage-checklist} shows the reference checklist for the \code{isEnabled} feature flag utility used in the pilot. Completeness is measured by enumerating generated files against the checklist and computing a coverage ratio (files present divided by required files). Missing artifacts indicate incomplete boilerplate that requires additional developer effort to make functional.

\subsubsection{Relationship between SmartKit Integrations and the Pilot Feature}
\label{sec:integrations-and-pilot}

SmartKit instantiates the framework conventions across multiple feature areas, including billing (SePay integration), authentication (Better~Auth), and email (Resend). These integrations exist because the artifact is a usable SaaS boilerplate. The pilot deliberately selects a feature---the feature-flag check utility---that uses \emph{none} of the integrated services, in order to isolate the effect of convention encoding from the effect of having integrated services available. If the pilot used a feature that integrates SePay or Resend, any observed difference between Condition~A and Condition~B would conflate convention encoding with integration availability. The integrations remain first-class in the artifact; their relation to the pilot evaluation is summarised in the scope note at the start of this chapter. This separation is what allows the framework to remain generalisable beyond SmartKit: a developer using a different stack can encode the same conventions without SePay, Resend, or Better~Auth, and the framework still measures the same three dimensions on any generated feature.

A second, related point concerns the role of the integrations during the AI session. In Condition~A, the AI sees the full SmartKit file tree, including \filename{features/billing/} (SePay HMAC, idempotency), \filename{features/auth/} (Better~Auth schemas and server actions), and the Resend email templates under \filename{features/auth/emails/}. These files belong to SmartKit's second role as a usable SaaS boilerplate (see the scope note at the start of this chapter); they encode the SmartKit convention envelope --- feature-based folder structure, colocated server actions, Zod schemas in \filename{types/}, \pkg{server-only} boundaries, and \code{revalidatePath} after mutations. The AI in Condition~A pattern-matches this envelope when generating the pilot feature, even though the pilot feature itself does not call any of the integrated services. In Condition~B, none of these pattern sources are available, so the AI must invent both the utility and its surrounding convention. The score difference between conditions therefore measures the convention envelope, not the integration surface. The convention envelope is what the framework is designed to capture; the integration surface is what makes SmartKit a usable SaaS boilerplate. Both are required for the thesis, but they play distinct roles. The integration surface contributes to the second thesis contribution---the SmartKit artifact as a working SaaS boilerplate---rather than to the pilot; the pilot is the instrument that exercises the framework on AI-generated code, while the integrations are the evidence that the framework conventions are usable in production code.

The standardised prompt's first resolution-order rule---``Per-user DB override, only if \code{userId} is passed''---is implemented in the pilot as a stubbed path: the generated \seqsplit{readUserOverride} helper returns \code{undefined} without querying any database layer, so the pilot feature genuinely touches neither Drizzle nor any external persistence. The stub keeps the resolution order observable in tests while leaving full DB-backed override as future work; this is consistent with the feature's design choice to avoid integrating any SmartKit service, including Drizzle, into the pilot scope. The relationship between this design choice and the Coverage rubric's level definitions (rubric A.5.3) is revisited in the pilot discussion (\autoref{sec:pilot} and \autoref{sec:threats}), which explains the structural constraint the design imposes on the Coverage dimension. \subsection{Rubric interpretation: what the scores measure and what they do not}
\label{sec:rubric-interpretation}

The three rubric dimensions introduced in \autoref{sec:dimensions} and detailed in \autoref{sec:pilot-rubric} carry different epistemic statuses with respect to the underlying constructs they are taken to represent. This subsection makes those statuses explicit so that pilot results (\autoref{sec:pilot-results}) are read within the framework's validated scope, and not beyond it.

\paragraph{Three dimensions, three epistemic statuses.} Each dimension is grounded in a distinct form of evidence, and the strength of the inference from a score to a substantive claim differs accordingly.

Structural Integrity: \emph{directly measured}. The score counts the presence or absence of artifacts at expected paths in the SmartKit feature-sliced layout (file placement, \code{server-only} import detection, \code{'use client'} directive checks, barrel-file verification). Differences between conditions reflect observed counts across runs (e.g.\ Cond~A 5/5 vs.\ Cond~B 0/5 on the central artifact path), not estimates or judgements, so the dimension-level score is reproducible from the run artefacts without calibration against an external construct.

For Type \& Contract Safety, the score is a \emph{justified proxy for production quality}, not a direct measurement of it. The sub-scores combine \code{tsc --noEmit} error counts and Zod-schema coverage at API boundaries; these signals are well-motivated indicators of compile-time and contract-level safety, but they do not by themselves establish that a generated feature is production-deployment-ready. Security review, load testing, observability, and runtime hardening are not subsumed by either sub-score, and \autoref{sec:measurement-validity} records that the cutoffs are asserted rather than calibrated against deployment outcomes.

Coverage \& Completeness reads as an \emph{aspirational developer-experience proxy}. The maximum score observed in the executed pilot is 3, and the relevant rubric cells at levels 4--5 require artifacts (e.g.\ a non-stubbed per-user override path, a centralised test at a specific path) that the no-integration selection criterion rules out by design (\autoref{sec:internal-validity}). \textbf{Cond~A's Cov = 3 therefore represents the design-stage ceiling for this pilot feature, not the floor of observed capability; the Coverage score is a code-artifact presence metric, not a validated developer-experience proxy.} The dimension therefore measures whether a feature contains the expected artifacts; the further claim that the resulting score predicts developer experience (time-to-integrate, onboarding friction, perceived quality) is not supported by any data collected in this thesis and is positioned as a future-validation target in \autoref{sec:future-work}.

\subsection{Evaluation Design: Rationale and Trade-offs}
\label{sec:design-rationale}

The evaluation framework design involves several deliberate choices that balance scope with feasibility. Prior work on tool-assisted coding includes rule-based static analysis (ESLint, TypeScript) and LLM-based code generation (GitHub Copilot, CodeWhisperer); SmartKit takes a third path by encoding framework conventions at the project-structure level rather than relying on post-hoc validation or prompt engineering, as established in \autoref{sec:relatedwork}.

\textbf{Dimension selection.} The three dimensions were designed to address the gap between output-oriented benchmarks (algorithmic correctness) and the framework-specific quality dimension that existing benchmarks do not measure. Each SmartKit dimension targets a distinct failure mode observed in AI-generated Next.js code: structural violations (file placement, Server/Client boundaries), type safety gaps, and missing boilerplate artifacts.

\textbf{Automated over manual evaluation.} The framework prioritizes automated metrics to enable reproducibility and scale. Expert review provides richer qualitative assessment, but automated checking ensures consistent evaluation across the large number of code samples required for meaningful comparison. Where qualitative judgment is necessary (e.g., structure quality assessment), LLM-as-judge with majority voting is a future option that was not exercised in the executed pilot; the pilot uses single-primary-rater manual scoring (deferred IRR; see \S6.5).

\textbf{6-level rubric across dimensions.} Each of the three~dimensions is scored on a 0--5 rubric (six integer levels). The per-dimension cell descriptions are detailed in §\autoref{sec:pilot-rubric}; the rough mapping is: $0$ = missing artefact, $1$ = severe violation, $2$ = partial (in the right neighbourhood but wrong sub-detail), $3$ = acceptable, $4$ = good (level 3 + a specific bonus criterion, e.g.\ \code{server-only} for Structural), $5$ = excellent (level 4 + a second bonus criterion, e.g.\ barrel re-export). The exact level descriptions are dimension-specific and were inferred from related literature on code quality rubrics (the 0--5 scale mirrors industry convention for code-review rubrics); per-level cutoffs have not been calibrated against developer-experience data within this thesis.

\textbf{Rubric scope, not calibration gap.} The rubric's level definitions are written against the \emph{full} convention envelope that SmartKit encodes (file-system routing, Server/Client boundary primitives, type-safe contract enforcement at boundaries, and integration with the database layer via Drizzle). Because the envelope is the design target of the framework, rubric levels 4--5 on dimensions where integration is one of the bonus criteria can only be reached by features that exercise the corresponding integration path. The executed pilot bounds the framework to a no-integration feature (\code{isEnabled(flagKey, userId?)}) for confound-control reasons (§\autoref{sec:design-rationale}), which sets the design-stage ceiling for Coverage at level 3 rather than at level 5. This is not a calibration gap --- it is the framework's design intent: the same rubric applied to a billing webhook handler would have a different design-stage ceiling, and a developer-experience study is required before the rubric levels can be claimed to mean ``good'' and ``excellent'' in any developer-relevant sense (§\autoref{sec:measurement-validity}). The pilot reports feasibility-stage ordinal scores on the rubric as written; the scores should be read as framework-internal measurements, not as developer-relevant quality grades.

\textbf{Single-framework focus.} The evaluation focuses exclusively on Next.js to maintain depth over breadth. Future work should extend the framework to Nuxt and Remix to assess generalizability of the approach.

\textbf{Confound control between conditions.} A central threat to the validity of the pilot results is confounding: the structured SmartKit condition and the unstructured condition differ \emph{primarily} in convention encoding, but they also differ in second-order ways that the executed pilot does not fully control. The most important residual confound is that the SmartKit repository exposes several example features (\filename{features/auth/}, \filename{features/billing/}, \filename{features/auth/emails/}) that the AI can use as pattern-matching anchors beyond the explicit AGENTS.md instructions. To isolate SmartKit's contribution from this confound, the pilot compared it against an unstructured Next.js baseline sharing the same dependency surface as SmartKit (Next.js 16.2.12, TypeScript 5.7.3, Tailwind CSS 4.3.3, Drizzle ORM 0.45.2 with PostgreSQL, Zod 4.4.3, Biome 2.5.6, Resend 6.18.1, and \pkg{better-auth} 1.6.x, plus the \filename{src/database/schema/} directory inherited from SmartKit) but with no feature-based \filename{src/features/} layout and no AGENTS.md. The exact dependency surface used to build the baseline is recorded in §\autoref{sec:pilot-conditions} (Condition~B paragraph) for replication; the \code{smartkit-baseline/package.json} shipped alongside this thesis is the canonical record of resolved versions and lock state. The exact \code{create-next-app} CLI invocation and the post-creation edits (customised \filename{.env.example}, removal of \filename{AGENTS.md} and \filename{.cursor/rules/}) are kept in the baseline repository's git history and are not duplicated in the bound thesis. The pilot feature (\code{isEnabled(flagKey, userId?)}) was chosen for the same reason: it uses no service that SmartKit integrates (no Resend, Better~Auth, SePay, or Drizzle dependency beyond the schema), so the AI cannot copy a pattern from the example features. This section refers to the baseline as the ``convention-naive scaffold'' to avoid confusion with the SmartKit repository directory itself; the build script that produces it is preserved alongside the thesis artefacts (§\autoref{sec:pilot-protocol}).

The control artifact serves as the control condition, providing a baseline that isolates the effect of SmartKit's convention encoding from the effect of the underlying technology stack.

Quantitative metrics derive from automated analysis of generated code. \textit{Structural Integrity} uses Biome custom rules to check Next.js-specific file placement, naming, and Server/Client boundary conventions. \textit{Type \& Contract Safety} uses \code{tsc --noEmit} output to identify type violations and custom Biome rules for \emph{any}-type detection and Zod coverage. \textit{Coverage \& Completeness} uses file enumeration against a reference checklist per feature type.

Qualitative metrics derive from expert review of generated code. Reviewers assess whether generated code follows Next.js best practices, whether naming conventions are consistent, and whether the overall implementation aligns with framework expectations. The expert review layer follows an inter-rater reliability (IRR) protocol: two independent raters score the same generated artifacts, with a target Cohen's $\kappa$ $\geq$ 0.7. The automated scoring layer (Biome, \code{tsc --noEmit}) is deterministic and requires no IRR. The IRR protocol is documented here as a design; execution of the IRR pass is identified as future work pending availability of a second rater.

Productivity metrics such as diff authoring time and developer-reported productivity \parencite{beller2026dat} are not collected in the current pilot and remain future work; the executed pilot reports only per-run time-to-correct (ttc, in minutes) as a coarse timing signal. Task completion time, cyclomatic complexity, maintainability index, and code smell density are documented as design-stage metrics for a future developer-participant study.

\section{Pilot Methodology}
\label{sec:pilot}
\label{sec:pilot-protocol}

The feasibility demonstration evaluates whether providing a structured ecosystem---architectural convention documentation, sibling-feature layout, and type-safety patterns---improves AI coding assistant adherence to Next.js conventions and type safety, relative to a convention-naive baseline. The independent variable is the presence of the SmartKit ecosystem, which is operationalized as the joint presence of \filename{AGENTS.md}, \filename{.cursor/rules/}, and \filename{src/features/} convention documentation together with the sibling-feature layout that makes those conventions discoverable. The dependent variables are the three rubric scores (Structural Integrity, Type \& Contract Safety, Coverage \& Completeness) on a 0--5 scale. The comparison is therefore an \emph{ecosystem comparison} (SmartKit vs.\ convention-naive scaffold), not a test of any single convention-encoding mechanism in isolation; per-arm isolation of any single mechanism would require a Cond~B that retains the SmartKit stack surface but removes the mechanism under test, which the executed demonstration does not implement.

The representative feature (\code{isEnabled(flagKey, userId?)}) was selected: it uses no service that SmartKit integrates (no Resend, Better~Auth, SePay, or Drizzle dependency beyond the schema). This choice keeps the comparison clean: by using a feature that touches none of SmartKit's integrated services, the comparison isolates the ecosystem effect (the bundled convention envelope) rather than conflating it with service-specific patterns. The evaluation scenario measures AI-generated boilerplate quality directly: AI systems receive task descriptions, and the generated code is measured against the framework dimensions. The demonstration focuses on Cursor as the primary case study, consistent with the scope defined in Section~\autoref{sec:introduction}. All evaluations use multiple runs to address non-determinism concerns raised by Ouyang et al.\ \parencite{ouyang2025nondeterminism}; the Cursor tool does not expose user-settable temperature (the snapshot used in the demonstration does not surface this control), so multi-run evaluation substitutes for temperature variation as the determinism-handling mechanism. Results report per-condition medians and ranges, plus Wilson 95\% confidence intervals on the binary pass rate ($\geq 3/5$).

The prompt intentionally avoids referencing SmartKit-specific conventions (\emph{do not} say ``for SmartKit'', ``follow the feature-based layout'', ``use \filename{.server} naming'', or ``refer to AGENTS.md''). The same per-run pipeline was applied to all ten runs, with per-condition aggregates reported in \autoref{tbl:pilot-actual}:
\begin{enumerate}
    \item Initialize a fresh copy of the codebase with the pre-registered tooling verified against a run-day checklist.
    \item Invoke Cursor with the standardized prompt; start the time-to-correct clock.
    \item Collect generated files, Biome violations, \code{tsc --noEmit} output, and artifact enumeration; snapshot the run in \filename{runs/cond-<a,b>/run-<NN>/}.
    \item Score each run on the three-dimension rubric; record per-run JSON plus manual cells; commit before the next run.
\end{enumerate}

\subsection{Run Schedule and Verdict Rule}
\label{sec:pilot-schedule}

The pilot followed a pre-registered adaptive schedule, detailed in \autoref{sec:pilot-protocol}: five runs in Condition~B (Runs~1--5) and five runs in Condition~A (Runs~6--10). Both arms reached adaptive-$N=5$ to satisfy the binary verdict rule and open the comparative-CI gate. The verdict rule in force: 5/5 confirmed; 0/5 refuted; 1--4/5 inconclusive. The full schedule with tool snapshots, verdict counts, and timestamps is in \autoref{tbl:pilot-actual} and the pilot audit trail released in the thesis GitHub repository.

For each run treated as a binary outcome (pass = score $\geq 3/5$; fail = score $< 3/5$), the Wilson 95\% confidence interval on the proportion of passing runs is computed by:
\begin{equation}
\frac{k + \frac{z^2}{2}}{n + z^2} \pm \frac{z}{n + z^2} \sqrt{\frac{k(n-k)}{n} + \frac{z^2}{4}}
\label{eq:wilson}
\end{equation}
where $k$ is the number of passing runs, $n=5$, and $z = 1.96$ for 95\% confidence. The Wilson interval is preferred over the normal approximation (Wald interval) for small $n$ because it never produces bounds outside $[0, 1]$ and has better coverage properties when the true proportion is near 0 or 1. Results are reported as median [min, max] with Wilson 95\% CI for the pass rate.

A second rater was scheduled to independently score 2 runs (1 per condition) using the same rubric, with Cohen's $\kappa \geq 0.7$ as the threshold for rubric revision. The IRR pass was deferred for lack of a second rater; see \S6.5.2 (Measurement Validity) for the canonical limitation disclosure.
\label{sec:pilot-irr}

\section{Results and Discussion}
\label{sec:pilot-results}

This section reports the feasibility demonstration of the \code{isEnabled(flagKey, userId?)} utility under the pre-registered adaptive protocol, comparing Condition~A (SmartKit with full convention encoding) against Condition~B (convention-naive scaffold). The final tally is $10$ runs: $n=5$ per condition. The demonstration is reported as an applicability check, not a hypothesis test: it verifies that the framework produces scores when applied to real AI-generated code. Binary-rule verdicts (5/5 confirmed, 0/5 refuted, 1--4/5 inconclusive) are reported per the adaptive-N protocol; they are binary-rule outcomes, not parameter estimates. See \S6.4.3 for the verdict mechanics and epistemic status. Two of the three directional predictions are confirmed outright (DP1, structural placement); one is confirmed as an instruction-following asymmetry rather than as a convention-encoding benefit (DP2, Zod-derived FlagKey type); and one is asymmetric, confirmed in Condition~A and refuted in Condition~B (DP3), reported as such rather than collapsed into a single label. \subsubsection*{Verdict-language scope}
\addcontentsline{toc}{subsubsection}{Verdict-language scope}
The verdicts in this section are \emph{binary-rule outcomes}, not frequentist hypothesis tests. The pilot uses an adaptive design at $n=5$ per condition; the binary verdict rule ($5/5$ confirmed, $0/5$ refuted, $1$--$4/5$ inconclusive) resolves outcomes at this sample size but does not provide a frequentist test. A future replication at $n \approx 30$ per condition is required for inferential claims (\S7.2). The comparative Bonferroni 99\% CI on the $A$--$B$ difference is reported for completeness: at $n=5$ per arm the CI collapses to the single point $\{1.0\}$ because every Cond~A run and every Cond~B run falls in the predicted direction; the CI width (driven by the Wilson half-widths on each arm) does not add inferential content beyond the binary outcome. Wilson 95\% CIs on each arm are similarly wide (half-width $\approx 0.21$) and are reported to anchor the DP verdicts in the executed numbers rather than to support a hypothesis test.

\subsection{DP1 -- Structural Placement}
\label{sec:dp1-results}
\label{sec:pilot-results-dp}

\textbf{What the rubric records and what it does not.} Across DP1, DP2, and DP3 the rubric captures the same kind of evidence: a 0--5 score per condition, and a binary verdict under the $N=5$ rule. What the rubric does not capture, in any of the three predictions, is which component of the SmartKit ecosystem produced the conformity; per-mechanism attribution would require a Cond~B that retains the SmartKit stack surface but removes only the mechanism under test, which the executed pilot does not implement. The three DP subsections below each open with this framing rather than repeating it.

\subsection{DP1 -- Structural Placement}
\label{sec:dp1-results}
\label{sec:pilot-results-dp}

\textbf{Verdict.} Condition~A: $5/5$ runs placed the utility at the predicted path \filename{features/flags/lib/is-enabled.ts}; Condition~B: $5/5$ runs placed it at root \filename{lib/} ($0/5$ in Condition~A's predicted location). Wilson 95\% CI: Condition~A $[0.57, 1.00]$; Condition~B $[0.57, 1.00]$ for absence at the predicted path. Comparative Bonferroni 99\% CI on the $A-B$ difference (now populated with both conditions at adaptive-$N=5$): the comparison is one-sided: every Cond~A run hits the FSD path and every Cond~B run misses it, so the difference is identically $1$ at the empirical level, and the comparative CI collapses to the single point $1.0$ (the dispersion is in the Wilson half-widths on each arm, not in the difference). \textbf{Binary-rule outcome: confirmed} ($5/5$ under the $N=5$ rule); \emph{not a precise inferential estimate} (see verdict-language scope above).

\textbf{What the rubric records.} DP1 is an ecosystem-comparison outcome: the SmartKit ecosystem produces consistent placement at the predicted FSD path ($5/5$ Cond~A runs at \filename{features/flags/lib/is-enabled.ts}), while the convention-naive scaffold produces consistent placement at root \filename{lib/} ($5/5$ Cond~B runs). The mechanism the rubric captures is observational at the ecosystem level: when an assistant is given the SmartKit codebase (with \filename{AGENTS.md}, sibling features under \filename{features/}, and the established \filename{is-enabled.ts} placement in adjacent features), the bundled convention envelope pushes the generated output into the predicted FSD path; when the same assistant is given the convention-naive scaffold (with none of these), the bundled absence of discoverable conventions produces a generic root-level placement. The $5/5$ vs.\ $5/5$ contrast is consistent with the rubric's design intent --- Structural Integrity rewards convention-conformity, and the two conditions differ by design in the density of the convention envelope that the rubric scores against. This is an ecosystem-level finding, not an attribution to any single mechanism (e.g.\ AGENTS.md alone, sibling features alone, or FSD layout alone).

\textbf{What the rubric does not capture.} The mechanism remains observational at this point: the framework records that the convention envelope was followed, not which component of the envelope (AGENTS.md, sibling features, FSD layout, or their combination) produced the conformity. A future controlled design (e.g.\ a Cond~B that retains the SmartKit stack surface but drops AGENTS.md, then a Cond~B that retains AGENTS.md but drops sibling features) would be required to attribute the conformity to specific mechanisms. Such a design is sketched in \S7.4 as a follow-up variation; the pilot as executed supports the ecosystem-comparison conclusion at the bundled-effect level.

\subsection{DP2 -- Zod-derived FlagKey}
\label{sec:dp2-results}

\textbf{Verdict.} Condition~A: $5/5$ runs used a Zod-derived \code{FlagKey} enum; Condition~B: $5/5$ runs used a raw \code{string} type alias (no Zod-derived enum). Wilson 95\% CI: Condition~A $[0.57, 1.00]$; Condition~B $[0.57, 1.00]$ for absence of a Zod-derived enum. Comparative Bonferroni 99\% CI on the $A-B$ difference (now populated with both conditions at adaptive-$N=5$): as with DP1, the difference is identically $1$ at the empirical level (every Cond~A run uses Zod, every Cond~B run uses raw \code{string}), so the comparative CI collapses to the single point $1.0$. \textbf{Confirmed as instruction-following asymmetry} ($5/5$ Cond~A complied with the directive, $5/5$ Cond~B did not) under the binary rule, but \textbf{not a precise inferential estimate} and \textbf{not a confirmation of convention-encoding benefit} on this dimension.\ \textbf{Mechanism interpretation.} Read against the rubric, the asymmetry is plausibly attributable to ecosystem-level reinforcement. The SmartKit stack exposes colocated Zod schemas in sibling features, which makes the shared ``use a Zod schema'' directive easier to comply with. The convention-naive scaffold has no such pre-existing patterns. On reflection, I should have anticipated this: the asymmetry tells me that pre-existing patterns in a codebase do most of the work, and an explicit directive without patterns is not enough. The bundled-effect limitation (ecosystem + directive vs.\ directive alone) is acknowledged in \S6.5.

\textbf{What the rubric does not capture.} The standardized prompt (Listing~\autoref{lst:control-prompt}) instructs both conditions to ``use a Zod schema to derive'' the \code{FlagKey} type, so the observed difference measures the \emph{ecosystem-level} asymmetry: the SmartKit ecosystem (with its colocated Zod configuration and existing Zod schemas in sibling features) reinforces the prompt directive, while the convention-naive scaffold does not reinforce it. The rubric scores this dimension identically in both conditions (a Zod-derived type scores 5, a raw alias scores 0--1), so the dimensional verdict (Condition~A wins) is correct. What the verdict does not separate is the structural contribution from the prompting contribution: both the ecosystem convention (Zod is the existing type-source pattern in SmartKit) and the shared prompt directive (``use a Zod schema'') point in the same direction, so a compliant Condition~A run cannot be attributed to either factor in isolation. The Cond~B non-compliance is informative because it shows the directive was available and the convention-naive ecosystem did not follow it, but that observation alone does not tell a reader whether Condition~A's compliance was caused by the ecosystem, the directive, or both. The bundled-effect limitation is acknowledged in \S6.5 and the design variation that would isolate the structural contribution (drop the shared Zod directive from the Cond~B prompt) is recorded in \S7.4.

\subsection{DP3 -- Centralized Test Path}
\label{sec:dp3-results}

\textbf{Verdict.} This prediction has two clauses: Condition~A places the test at \filename{src/tests/features/flags/} (predicted); Condition~B produces no test file (predicted). Condition~A: $5/5$ colocated as predicted --- \textbf{confirmed}. Wilson 95\% CI: $[0.57, 1.00]$. Condition~B: $5/5$ runs \emph{did} produce a test file (at the repository root), the opposite of the prediction --- \textbf{refuted}. Wilson 95\% CI: $[0.57, 1.00]$ for the absence of a test file (note that the script-level \texttt{cond\_b\_not\_colocated} count is $5/5$ because every Cond~B run has a root-level test, which the script records as ``Cond B follows its predicted (non-colocated) direction'' under the mechanical reading of the binary rule; this collapses to ``confirmed'' at the automated-aggregator level but does not change the substantive two-clause verdict reported here). Comparative Bonferroni 99\% CI on the $A-B$ difference (DP3-A clause): the two arms diverge maximally --- Cond~A hits the FSD path in $5/5$ runs, Cond~B never hits the FSD path --- so the difference is identically $1$ at the empirical level and the comparative CI collapses to the single point $1.0$. This asymmetric outcome is reported as two separate clauses rather than collapsed into a single verdict: the pre-registration did not anticipate that Condition~B would consistently generate tests, and that is itself a finding worth noting.

\textbf{What the rubric does not capture.} The mechanism the rubric fails to capture here is general-purpose test-generation behaviour: an assistant given a TypeScript utility and an instruction to ``write tests if appropriate'' will, under most prompting configurations, generate some test file rather than none. The original DP3 design assumed Condition~B would treat the prompt as optional with respect to tests; that assumption was incorrect for the prompt phrasing used. Condition~A's $5/5$ prediction match on placement (centralized at `src/tests/features/flags/`) is unaffected, and that placement is what DP3 was designed to measure; the refuted clause is reported as two separate clauses rather than collapsed into a single ``confirmed'' verdict.

\textbf{Secondary DP3 finding: Coverage cap at 3 in Condition~A.} Rubric A.5.3 levels 4--5 require a non-stubbed per-user override path, which the pilot feature structurally cannot produce by design (no SmartKit integration means no database layer to derive an override value from). The executed pilot therefore reports Coverage scores capped at $3$ for all Cond~A runs (\autoref{tbl:pilot-actual}); these Cov $=$ 3 values reflect the design contradiction itself, not a finding about AI capability. This design consequence is analyzed in \S6.5.3, which is the canonical location for the rubric-flaw discussion.

\subsection{Statistical Context: \texorpdfstring{$n=5$}{n=5} per Condition is not Inferential}
\label{sec:discussion-statistics}

The Wilson 95\% half-widths reported in \autoref{sec:pilot-results-dp} anchor the DP verdicts in the executed numbers, not in summary prose: Condition~A half-width $\approx 0.21$ (CI $[0.57, 1.00]$ on $5/5$); Condition~B half-width $\approx 0.21$ (CI $[0.57, 1.00]$ on $5/5$). At these widths, a single-condition Wilson interval cannot distinguish a true proportion of $0.50$ from one of $0.80$; the DP verdicts are therefore binary-rule outcomes (a $5/5$ count resolves ``confirmed'' under the rule's $N=5$ requirement) rather than parameter estimates with confidence. The DP verdicts should be read as feasibility-stage evidence that the framework can measure the predicted contrast under the executed conditions, not as estimates of that contrast in a population of AI assistants or codebases.

The conditional coverage of the comparative Bonferroni 99\% CI on the $A-B$ difference is now active (both arms at adaptive-$N=5$). Because every Cond~A run lands in the predicted location and every Cond~B run lands outside it on DP1, DP2, and the DP3-A clause, the empirical difference is identically $1$ on each prediction and the comparative CI collapses to the single point $1.0$. The dispersion is concentrated in the per-arm Wilson half-widths ($\approx 0.21$), not in the difference; the comparative CI does not add inferential content at this sample size but does report a numerical quantity consistent with the per-arm verdicts. A future symmetric-$N \approx 30$ replication is required before the comparative CI provides inferential leverage; see \S7.4 for the sample-size discussion.

A reader asking ``how big is the Condition~A effect?'' is asking a question the executed pilot does not answer. I want to be honest here: that reader is asking the right question. I considered re-running with $n=30$; I did not, because Bachelor's thesis time was finite. The conditions under which the effect size would become estimable (per-arm $N \approx 30$, symmetric $N$ across both arms, two or more tool families) are recorded as future work in \S7.4 and as a Known Limitation in \S6.5. The Discussion above reads the DP verdicts against the rubric mechanics for what they show at the executed sample size; it does not extrapolate.

\section{Threats to Validity}
\label{sec:threats}

The threats-to-validity taxonomy below organizes the limitations of the pilot under four categories.
\begin{itemize}
    \item \textbf{External Validity} (\autoref{sec:external-validity}) covers transfer across frameworks.
    \item \textbf{Measurement Validity} (\autoref{sec:measurement-validity}) covers rubric cutoffs and inter-rater reliability.
    \item \textbf{Internal Validity} (\autoref{sec:internal-validity}) covers rubric-calibration consequences and protocol deviations.
    \item \textbf{Conclusion Validity} (\autoref{sec:conclusion-validity}) covers alternative explanations.
\end{itemize}
This section is the analytical taxonomy, with each category discussed against the executed pilot rather than the pre-registered design.

\subsection{External Validity}
\label{sec:external-validity}

\textbf{Generalizability.} Findings are bounded to Next.js App Router; whether the directional predictions hold for Nuxt (Vue) or Remix environments is unverified. The framework's three dimensions are designed for portability but require framework-specific instantiation before cross-framework claims can be made; the roadmap is in \autoref{sec:future-work}.

\subsection{Measurement Validity}
\label{sec:measurement-validity}

\textbf{Rubric cutoffs and IRR calibration.} The three evaluation dimensions are derived from design principles that address the gap between output-oriented benchmarks and framework-specific quality dimensions (foundation in \autoref{sec:relatedwork}), but the specific dimension selection and rubric cutoffs are design choices rather than empirically validated constructs. The cutoffs (0--1: serious violations, 1--2: minor, 2--3: acceptable, 3--4: good, 4--5: excellent) are asserted mappings to developer outcomes; the claim that rubric level 5 means ``excellent boilerplate'' and level 0 means ``missing artifact'' in any developer-relevant sense is asserted rather than calibrated. Multi-run evaluation, IRR with Cohen's $\kappa \geq 0.7$, and criterion-referenced validation remain follow-up steps; until validation-stage replication is executed, the rubric scores should be read as ordinal, reproducible measurements of the framework's three dimensions, not as developer-relevant quality grades.

\textbf{Known Limitations (Measurement Subset).} Three identified limitations bound every quantitative claim in this thesis and are referenced from \S6.5 rather than restated at each location. (a)~\emph{Small per-arm sample size}: $n=5$ per condition ($n=5$ Cond~A, $n=5$ Cond~B after the 2026-09-14 amendment); no frequentist inferential claim supported at these sample sizes (see \autoref{sec:future-work} for the sample-size calculation that places validation-stage replication at $n \approx 30$ per condition). (b)~\emph{Deferred inter-rater reliability}: the pre-registered IRR pass with Cohen's $\kappa \geq 0.7$ was deferred for lack of a second rater within the Bachelor's thesis timeline; all manual scores in \autoref{tbl:pilot-actual} are single-rater, and the deferral is recorded in the pilot audit trail released in the thesis GitHub repository (\autoref{sec:pilot-protocol}). (c)~\emph{Unblinded primary-rater scoring}: the same author designed the rubric, built the \texttt{score-flag.ts} script, and produced SmartKit, creating a confirmation-bias risk that blinding would have prevented. The Coverage rubric's post-hoc re-evaluation (Cov 4--5 $\to$ 3, see \S6.3 ``Per-condition aggregate'') is the most visible instance of a judgment-call that blinding would have governed. Mitigation for future work: each run's files should be stripped of condition-identifying paths (e.g.\ \filename{features/flags/} vs.\ root \filename{lib/}) and re-labelled before scoring, with condition membership recovered only after the scores are committed to \filename{score.json}; the current pilot's per-run JSON artefacts are preserved so the re-scoring can be done ex post if a second rater becomes available.

\subsection{Internal Validity}
\label{sec:internal-validity}

\textbf{Coverage design ceiling, not a rubric flaw.} The Coverage \& Completeness rubric (\autoref{sec:pilot-rubric}, \autoref{tab:rubric-cov}) defines level~4 as requiring the per-user override path to be ``implemented (not stubbed --- i.e. returns a value derived from the database)'' and level~5 as additionally requiring the centralized test path. The pilot feature (\code{isEnabled(flagKey, userId?)}) was chosen specifically to avoid any SmartKit integration including the database layer (\autoref{sec:integrations-and-pilot}), so the per-user DB override path is structurally out of scope for any feature meeting the no-integration selection criterion. I went back and forth on the Coverage ceiling for several weeks. Eventually I decided that a rubric whose highest level depends on a SmartKit integration the pilot deliberately excludes is not actually a rubric for the rubric's own purpose. That decision is what made the pilot defensible, and is the source of the design ceiling: the rubric is calibrated to the full convention envelope (\autoref{sec:design-rationale}), and the no-integration feature can only reach level 3 by the rubric's own design. The executed pilot therefore reports Coverage scores capped at 3 for all Cond~A runs (\autoref{tbl:pilot-actual}); these Cov $=$ 3 values reflect the framework's intended coverage of the envelope, not a scoring error or a contingent finding about AI capability. Whether level 5 corresponds to ``excellent boilerplate'' in a developer-relevant sense --- and what an additional bonus criterion beyond the per-user-override path would mean --- remains a validation-stage question for a developer-experience study. The current rubric is preserved as written, the pilot's Coverage scores are read at the design ceiling for this feature, and a re-scoped pilot that integrates a SmartKit service would exercise the upper-end rubric cells as part of the validation stage (\autoref{sec:future-work}).

\textbf{Protocol Deviations (Internal-Validity Subset).} Five protocol-affecting decisions bound how the within-condition results should be read; the full audit log with dates and justifications is in the pilot audit trail released in the thesis GitHub repository, and the concise summary is in \S6.5. (i)~\emph{IRR deferral}: no second rater was available within the Bachelor's thesis timeline, so all manual scores are single-rater. (ii)~\emph{Cursor-snapshot difference across the run window}: Cond~B runs 4--5 and Cond~A runs 8--10 were generated under a different Cursor UI snapshot (\texttt{cursor-assistant/agent-mode/2026-09-06}) than the early-batch runs (Cond~A runs 6--7 under \texttt{cursor-ai/auto/2026-09-05}); the snapshot difference is recorded per-run in the pilot audit trail (thesis GitHub repository) and is disclosed as a confound rather than treated as a deliberate experimental factor. (iii)~\emph{N-extension asymmetry (resolved)}: Cond~A was extended from $n=2$ to $n=5$ post-data-collection so the binary verdict rule could issue a determinate outcome; Cond~B was subsequently extended from $n=3$ to $n=5$ so that the comparative Bonferroni 99\% CI gate on the $A-B$ difference could open. Both extensions remain post-hoc and the post-hoc nature of each is the load-bearing concern; with both arms now at adaptive-$N=5$, the original ``asymmetric N-extension produces one-sided confirmation'' bias risk is downgraded (both arms are now symmetric in count and rule-applicability) but the \emph{post-hoc} nature of both extensions is not removed. (iv)~\emph{Verdict-rule shift}: the adaptive $N=3$ rule was replaced mid-pilot by the binary $N=5$ rule (\autoref{sec:pilot-schedule}); the lock permitted rubric and schedule amendments but not protocol-rule amendments, so this falls outside the categories enumerated in \autoref{sec:pilot-lock}. (v)~\emph{DP3-B refuted outright}: the Cond~B clause of DP3 was falsified when all five Cond~B runs produced root-level test files, opposite to the prediction.

\textbf{Protocol-rule violation: N-extension and verdict-rule shift exceeded permitted amendments.} The N-extension to Condition~A ($n=2\!\to\!5$) and the shift from the adaptive $N=3$ verdict rule to the binary rule (\autoref{sec:pilot-schedule}) fall outside the amendments the pre-registration lock explicitly permits: the lock (\autoref{sec:pilot-lock}) allows only IRR-triggered rubric revision and exclusion-triggered schedule replacement, not protocol-rule changes motivated by indeterminate verdicts. This is a protocol-rule violation of the same commitment device that otherwise constrains the pilot; the substantive effect is captured by the bias-risk disclosure above, and the formal effect is that the pre-registration's amendment procedure (see pilot audit trail released in the thesis GitHub repository, amendment log) records these changes under the ``permitted amendments'' clause in form, while in substance they constitute a fourth category --- protocol-rule amendment --- that the lock did not enumerate. Future replication should add ``protocol-rule amendment'' as a fourth permitted-amendment category or, preferably, redesign the verdict rule so that an indeterminate result can be reported as inconclusive without requiring asymmetric N-extension.

\textbf{Tool-dependent, one-sided confirmation.} Three post-hoc decisions bound the DP verdicts. First, Cond~A was extended from $n=2$ to $n=5$ at 2026-09-06; Cond~B was subsequently extended from $n=3$ to $n=5$ at 2026-09-14 so that both arms are now at adaptive-$N=5$ and the comparative Bonferroni 99\% CI on the $A-B$ difference can be reported. With the symmetric-$N$ extension in place, the original ``asymmetric N-extension produces one-sided confirmation'' bias risk \parencite{simmons2011falsepositive} on researcher degrees of freedom is downgraded: the symmetric-count design now satisfies the comparative-CI gate, and the per-arm Wilson half-widths are now equal ($0.21$) on both arms. The post-hoc nature of both extensions is not removed by the second extension and remains a disclosed limitation. Second, Cond~A runs 8--10 were generated under a different AI-tool snapshot (\texttt{cursor-assistant/agent-mode/2026-09-06}) than Cond~A runs 6--7 (\texttt{cursor-ai/auto/2026-09-05}); excluding runs 8--10 would leave Cond~A at $N=2$, below the verdict rule's threshold, so the \emph{confirmed} status of DP1 and DP2 depends on treating runs 8--10 as comparable to runs 6--7. The scores from runs 8--10 reproduce the runs 6--7 pattern under an unchanged rubric and prompt, which is the basis for retaining them; this is a single worked pilot on one feature and one tool family, not a controlled cross-tool replication. Third, DP3's Condition~B clause (predicting no test file) was falsified: all five Condition~B runs produced a test file, which the pre-registration did not anticipate. The full chronology, with dates and reasoning for each decision, is recorded in the pilot audit trail released in the thesis GitHub repository (amendment log).

\textbf{Design confounds and deferred validation.} Two further limitations bound how the pilot's numbers should be read. The locked run schedule executed Condition~B first (Runs~1--5), followed by Condition~A (Runs~6--10); time-of-day, session-memory, and experimenter-familiarity confounds cannot be ruled out across these condition blocks. Because the Cond~A block itself spans two tool snapshots (\texttt{cursor-ai/auto/2026-09-05} for runs 6--7 and \texttt{cursor-assistant/agent-mode/2026-09-06} for runs 8--10), the run-order confound and the tool-snapshot difference are partially entangled for that condition, and a fully randomized run order is left as future work. Separately, every score in \autoref{tbl:pilot-actual} reflects a single primary rater (see Known Limitations in \autoref{sec:threats}); the scores remain reproducible from the underlying run artefacts, but have not been cross-checked against independent judgement.

\subsection{Conclusion Validity}
\label{sec:conclusion-validity}

\textbf{Alternative Solutions / Alternative Explanations.} The pilot's directional predictions are explained in terms of the three-dimension framework's structural conventions; whether the same directional verdicts would emerge under alternative solution strategies (prompting-only, linter-based enforcement, enhanced documentation) is left as future work (\autoref{sec:future-work}). The confirmed DP1 and DP2 verdicts cannot, by themselves, distinguish ``structural convention-encoding benefit'' from ``instruction-following asymmetry that the structural convention incidentally enables'', because Cond~A's prompt bundles both the AGENTS.md structural directives and the explicit instruction-following cues that Cond~B's prompt also contains. The bundled-effect limitation is disclosed here rather than retrofitted into a clean causal story; future work should re-run DP2 with the Cond~B prompt removing the shared Zod directive to isolate the structural convention-encoding contribution from the prompting contribution.

\chapter{Conclusion and Future Work}
\label{sec:conclusion}

\section{Summary}

The primary contribution of this thesis is the design of a three-dimensional evaluation framework for assessing AI-generated Next.js boilerplate, instantiated in SmartKit as a working artifact. A bounded feasibility demonstration ($n=5$ Cond~A, $n=5$ Cond~B) on one representative feature verifies that the framework produces scores when applied to real AI-generated code. The demonstration is a feasibility check, not an empirical test; the verdicts are binary-rule outcomes, not parameter estimates. Two of the three directional predictions are confirmed outright (DP1, structural placement); one is confirmed as an instruction-following asymmetry rather than as a convention-encoding benefit (DP2, Zod-derived FlagKey type); and one is asymmetric, confirmed in Condition~A and refuted in Condition~B (DP3). The full verdicts and disclosed protocol adaptations are in \autoref{sec:pilot-results} and \autoref{sec:threats}. Quantitative claims are bounded by the limitations documented in \S6.5 --- small per-arm samples, deferred IRR, and unblinded scoring --- which the thesis treats as the canonical reference rather than restating them at each reporting point. The framework, artefact, and executed demonstration are intended as a foundation for larger-$N$ replication, cross-tool validation, and developer-participant studies, all documented in \autoref{sec:future-work}.

\medskip\noindent\textbf{Ceiling--floor pattern in the executed scores.} I want to acknowledge the ceiling-floor pattern in the per-run scores explicitly: Condition~A medians (Structural $5$, T\&C $4$, Coverage $3$) sit at or near the rubric ceiling, while Condition~B medians (Structural $2$, T\&C $1$, Coverage $1$) sit at or near the rubric floor, with the single exception of Condition~B's T\&C range ($0$--$3$). Three structural causes produce this pattern, none of which retracts the confirmed verdicts. First, the Condition~A Coverage score is capped at $3$ by the framework's design ceiling rather than by a rubric flaw (§6.5.3): rubric levels $4$--$5$ require a non-stubbed per-user override path, and the no-integration selection criterion rules out that artifact by the rubric's own design. Second, the Cond~A score direction is reinforced by multiple bundled signals --- \filename{AGENTS.md}, the sibling-feature layout under \filename{features/billing/} and \filename{features/auth/}, the colocated Zod configuration, and the Zod directive in the standardized prompt --- all of which push toward the same FSD path, so the directional predictions cannot separate convention-reading from instruction-following (\S6.5.4). Condition~B was bootstrapped specifically to remove the SmartKit ecosystem (no AGENTS.md, no sibling features, no FSD layout), so its scores aggregate near the floor of a rubric calibrated to that ecosystem; the absence of AGENTS.md in Cond~B is therefore a design feature of the ecosystem comparison rather than an accidental confound. Third, the comparative Bonferroni 99\% CI collapses to the single point $\{1.0\}$ because every Cond~A run is in the predicted location and every Cond~B run is outside it on DP1, DP2, and the DP3-A clause; this saturation is the expected behaviour of a $k/n = 5/5$ vs.\ $5/5$ comparison at the binary-rule stage and is not an inferential estimate. The confirmed verdicts are therefore feasibility-stage binary outcomes, not parameter estimates.

\section{Future Work}
\label{sec:future-work}

Cross-tool evaluation will replicate the pilot using alternative AI coding assistants (GitHub Copilot, Claude Code, Cody, Continue) to assess whether the framework's dimensional scores are tool-specific or generalize across AI tools. The directional predictions (DP1--DP3) can be tested on each tool, producing a per-tool verdict table. Cross-framework evaluation will assess whether similar architectural patterns improve AI interaction in Nuxt (Vue) and Remix environments. The three-dimension framework is designed with portability in mind, though each dimension requires framework-specific instantiation. \textbf{Structural Integrity} maps directly: in Nuxt, the conventions are file-based routing via \filename{/pages/}, \code{definePageMeta()} for metadata, \code{useAsyncData()} for server data boundaries, and \code{.client.vue} suffix for client-only components; in Remix, they are flat routes via \filename{/routes/}, \code{loader}/\code{action} functions as server-side entry points, and \code{ErrorBoundary} components for error handling. These conventions are structurally analogous to Next.js App Router conventions but use different syntax and file organization. \textbf{Type \& Contract Safety} transfers directly because it operates at the language level (TypeScript strict mode) and API level (Zod schemas), which are framework-agnostic. \textbf{Coverage \& Completeness} requires per-framework checklist instantiation: Nuxt checklists include \filename{middleware/} files and \filename{composables/} for shared logic, while Remix checklists include \filename{utils/} and \filename{styles/} conventions. Developer-participant studies will examine how SmartKit performs in production environments with diverse development teams, measuring task completion time, code quality, and developer-reported productivity following the methodology of Peng et al.\ \parencite{peng2023impact} and Tariq et al.\ \parencite{tariq2026enterprise}. Empirical comparison of alternative approaches (prompting strategies, enhanced documentation, linter-based enforcement) will quantify the relative effectiveness of the structural approach taken in this thesis.

In addition to the items above, the rubric's epistemic scope (\S\ref{sec:rubric-interpretation}) motivates two further work items. \textbf{(6)~Calibrate rubric scores against developer-experience evidence.} The Coverage \& Completeness dimension is interpreted as an aspirational developer-experience proxy at present; a developer-participant study that pairs each rubric level (0, 1, 2, 3) with developer-reported time-to-integrate and onboarding-friction ratings is needed before the Coverage score can be claimed to track a developer-relevant construct. \textbf{(7)~Extend the rubric to cover quality dimensions outside the current proxy.} The Type \& Contract Safety column currently stands in as a proxy for production quality, but error handling, security review, and performance are not subsumed by either sub-score; a future revision of the rubric should add dimensions (or sub-scores) for these constructs so that the framework's production-quality reading is not carried by a single proxy dimension.

\textbf{Sample-size determination.} The executed pilot ($n=5$ per condition after the pre-registered Cond~A extension and the 2026-09-14 Cond~B extension) is feasibility-stage, not validation-stage. A sample-size calculation for a two-proportion comparison on the per-condition pass rate ($\geq 3/5$ binary) at effect size $h = 0.5$ (Cohen's medium effect), $\alpha = 0.05$, and power $0.8$ gives $n \approx 30$ per condition (chi-squared approximation). At a stricter effect size $h = 0.3$ (small), the requirement rises to $n \approx 90$ per condition. The binary verdict rule used in the pilot ($5/5$ confirmed, $0/5$ refuted, $1$--$4/5$ inconclusive) is appropriate for a feasibility-stage design at small $N$, but it is not a substitute for a frequentist sample-size calculation when moving to validation-stage replication: a confirmed verdict at $N=5$ should not be over-interpreted as a strong inferential claim.

\textbf{Empirical validation of the orthogonality claim.} The three evaluation dimensions (Structural Integrity, Type \& Contract Safety, Coverage \& Completeness) are claimed in \S1.3 to be \emph{designed to be} orthogonal in the sense that they measure distinct aspects of generated code. This orthogonality is a design-stage hypothesis---the three dimensions are intended to vary independently, but this intent has not been empirically tested. A Pearson correlation matrix across the three dimension scores, computed on $n \geq 30$ per condition, would distinguish genuine orthogonality (correlations $\approx 0$) from subtle coupling.

\textbf{Re-execution of the IRR pass.} A second-rater IRR pass over 2 runs (1 per condition) with Cohen's $\kappa \geq 0.7$ is the pre-registered validation step (§\autoref{sec:pilot-irr}). The pass was deferred for lack of a second rater within the thesis timeline (Section~\autoref{sec:threats}). Future work should re-execute the IRR pass once a second rater is available; the rubric-revision clause remains in force but was not exercised.

\textbf{Broader adoption implications.} Beyond the technical replication items above, SmartKit's adoption profile depends on relative advantage, compatibility, complexity, trialability, and observability \parencite{rogers2003diffusion, storey2016frameworkadoption}. Empirical measurement of these factors through developer-participant studies that pair SmartKit-generated and unstructured Next.js codebases would test whether the structural-convention effect observed in the pilot generalizes to real developer workflows. A secondary concern is whether explicit convention frameworks partially mitigate the developer deskilling risk identified by \parencite{dakhel2023github} by making AI-generated structure legible to developers who did not produce the code themselves.
