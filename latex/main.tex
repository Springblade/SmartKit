\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

AI coding assistants such as GitHub Copilot and Cursor are now in daily use, with substantial reported gains for boilerplate-heavy tasks: Peng et al.\ report a 55.8\% completion-time reduction on a controlled HTTP-server task \parencite{peng2023impact}, and Yetistiren et al.\ find boilerplate generation the strongest use case among practitioners \parencite{yetistiren2022assessing}. The benchmarks that dominate the literature, including HumanEval, MBPP+, APPS, BigCodeBench, and LiveCodeBench for algorithms and SWE-bench for bug fixing, measure problem-solving and patch generation, not whether AI-generated code respects framework conventions. Server/Client boundary violations in Next.js App Router, for instance, fail at runtime in a way no static type check catches.

This thesis proposes a three-dimensional evaluation framework for AI-generated Next.js boilerplate and instantiates it in SmartKit, an open-source Next.js 16.2.12 boilerplate that acts as both the framework's target codebase and a usable SaaS scaffold. The framework scores each generated feature on Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness, each reported on a 0--5 scale. A pre-registered adaptive pilot ran 10 times on one feature: $n=5$ per condition (Cond~A: SmartKit; Cond~B: convention-naive scaffold) after two mid-study extensions to balance the design at adaptive-$N=5$ and unlock the comparative Bonferroni 99\% CI on the $A-B$ difference. One of three directional predictions is confirmed outright (structural placement); one is confirmed as an instruction-following asymmetry rather than as a convention-encoding benefit (Zod-derived FlagKey type); and one is asymmetric, confirmed in Condition~A and refuted in Condition~B, and is reported as such rather than collapsed into a single verdict.

The pilot is feasibility-stage evidence rather than an inferential test. Per-arm samples are too small for inferential statistics, and four protocol adaptations are disclosed: an adaptive extension applied to Condition~A only (later balanced by a second extension to Condition~B), a tool substitution for runs $6$--$10$, and two-clause reporting of the asymmetric prediction introduced after data collection. Larger-N replication, cross-tool validation, and developer-participant studies remain future work.

\chapter{Introduction and Motivation}
\label{sec:introduction}

The chapter opens with the recent wave of AI coding assistants and the parallel shift in Next.js toward the App Router, then identifies the absence of an evaluation framework for framework-specific convention adherence. From that gap the chapter derives the research objectives, questions, and hypotheses that structure the rest of the thesis, and closes with the scope within which the SmartKit framework is designed and evaluated.

\section{Overview}

Controlled studies report substantial productivity gains from AI coding assistants. Peng et al. showed that developers using GitHub Copilot completed tasks 55.8\% faster than control groups \parencite{peng2023impact}, while Yetistiren et al. found AI tools particularly effective for boilerplate-generation tasks \parencite{yetistiren2022assessing}. Next.js has emerged as the dominant React meta-framework for production web applications, with its App Router architecture introduced in version 13 fundamentally changing application structure through React Server Components and explicit Server/Client boundaries \parencite{nextjsdocs}. The failure mode that motivates this thesis is concrete (Figure~\ref{fig:motivated-example}): when an AI coding assistant generates a Server Component that imports a Client Component and passes an event handler as a prop, Next.js produces the runtime error ``Event handlers cannot be passed to Client Component props''---a failure that \code{tsc --noEmit} cannot catch because it has no type-level representation. During SmartKit's development, recurring AI generation errors were observed firsthand in Next.js App Router code, including authentication security flaws, component boundary violations, and outdated API usage from older training data; these are development-time observations rather than measured prevalence figures. Without systematic evaluation, developers cannot assess whether AI-generated Next.js code adheres to framework conventions or will fail in production.

Existing benchmarks address algorithmic problem-solving and bug-fixing capabilities but not framework convention adherence. HumanEval evaluates Python code generation for standalone functions \parencite{chen2021evaluating}; SWE-bench assesses AI ability to resolve GitHub issues \parencite{jimenez2024swebench}; a systematic review of 395 LLM-for-SE studies found that framework-convention adherence is not separately tracked as an evaluation category, with benchmark evaluation (60\%) dominating over human evaluation (40\%) \parencite{hou2024llmse}. None of these capture the specific architectural requirements of Next.js App Router, such as Server/Client component boundaries, type-safe contracts, or file-system routing conventions. The gap means developers have no quantitative basis for comparing AI tools on framework-specific tasks.\footnote{RigorBench \parencite{rigorbench2026}, an as-yet-unreviewed preprint with a self-disclosed author conflict of interest (the authors co-developed the Agent-Rigor framework that RigorBench evaluates), addresses an adjacent concern---engineering process discipline---and is referenced here for completeness rather than as a load-bearing citation for the gap claim above.}

\textbf{Intended users.} SmartKit targets solo developers and small teams (2--5 members) working on Next.js projects with AI coding assistants. They are intermediate developers who already understand React and TypeScript fundamentals and want to reduce boilerplate setup time while enforcing consistent conventions in AI-assisted development. The framework supports incremental adoption: teams can apply the feature-based folder structure and Server/Client boundary conventions without committing to the full stack.

\section{The Problem: AI Convention Violations in Next.js}

This thesis addresses a concrete problem: AI coding assistants consistently generate Next.js App Router code that violates framework conventions, producing runtime errors and technical debt, yet no evaluation framework exists to measure this adherence. Three principal challenges shape the framework design.

First, framework conventions are implicit and distributed across documentation, error messages, and community patterns. Enumerating them into testable metrics is itself an open problem. Second, AI-generated code failures in Next.js manifest at runtime rather than compile time --- the Server/Client boundary error ``Event handlers cannot be passed to Client Component props'' only fires when the component is executed, so the framework needs dynamic analysis rather than static linting alone. Third, the three evaluation dimensions are designed to be orthogonal: a structural-integrity violation does not imply a type error, and a coverage gap operates independently of both. Collapsing them into a single composite score would hide which dimension is actually regressing. The orthogonality of the three dimensions is asserted at design stage and awaits empirical validation; the executed pilot's per-arm sample is far below the $n \approx 30$ required to confirm that the dimensions vary independently in practice (Section~\ref{sec:future-work} documents a Pearson correlation analysis as future work).

The focus on Next.js App Router is deliberate. First, market dominance makes it the primary target: community surveys consistently place Next.js among the most widely adopted React meta-frameworks \parencite{nextjsdocs}; Stack Overflow's annual Developer Survey has tracked Next.js as the most-used React meta-framework since 2021 \parencite[Stack Overflow Developer Survey]{stackoverflow2025}. Second, training-data mismatch creates measurable failures: AI tools generate outdated patterns from older training data that conflict with current Next.js conventions, particularly around Server/Client boundaries and async API changes. Third, practical feasibility applies: the author has existing Next.js expertise, enabling direct testing of enforcement mechanisms. The pilot targets Cursor as the primary case study because its AGENTS.md feature implements documentation-based guidance, which prior research on grounded prompting suggests can improve AI output quality \parencite{barke2022grounded,zhang2023practices}.

\section{Research Objectives and Questions}

While Next.js dominates React meta-framework adoption and AI coding assistants such as GitHub Copilot and Cursor have demonstrated substantial productivity gains, there is a distinct gap at the intersection of these two areas: a systematic, operationalizable evaluation framework that measures how closely AI-generated Next.js boilerplate code adheres to framework-specific conventions. Existing benchmarks---HumanEval, SWE-bench---address algorithmic problem-solving and bug-fixing capability, but none capture the architectural requirements of Next.js App Router such as Server/Client component boundaries, type-safe contracts, or file-system routing conventions \parencite{chen2021evaluating,jimenez2024swebench}. This thesis targets precisely that gap.

The primary motivation of this thesis is to bridge this gap by designing a three-dimensional evaluation framework that turns an implicit set of framework conventions into measurable, comparable scores, and by instantiating that framework in SmartKit, a structured Next.js boilerplate that provides the necessary enforcement mechanisms and the evaluation target codebase.

The research pursues three objectives:
{\sloppy
\begin{itemize}
    \item \textbf{Design a three-dimensional evaluation framework.}
    Construct a framework that scores AI-generated Next.js boilerplate
    code along three dimensions: Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness, so that convention adherence becomes a quantitative,
    comparable property of generated code.
    \item \textbf{Implement SmartKit as a structured architecture.}
    The thesis releases SmartKit, an open-source Next.js boilerplate
    that demonstrates feature-based modularity, explicit Server/Client
    boundaries, and type-safe contracts, providing both the enforcement
    mechanisms and the target codebase for the framework.
    \item \textbf{Conduct a pilot empirical case study.} The thesis applies the
    framework to a representative feature generated by Cursor under
    the SmartKit condition to demonstrate that the framework can
    produce illustrative, actionable scores on real generated code.
\end{itemize}
}

Consequently, this research seeks to answer the following research questions:
\begin{enumerate}
    \item How can an evaluation framework be consistently designed to
    measure AI coding assistant adherence to Next.js App Router boilerplate conventions along the Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness dimensions?
    \item Can the resulting framework be operationalized into measurable
    metrics, and does it produce illustrative, actionable scores when
    applied to representative AI-generated Next.js features?
\end{enumerate}

These objectives and questions give rise to two classes of claims, both
documented as design-level pre-registrations to be exercised by the pilot
(§6.2). The first class states \textbf{framework
properties}---descriptive claims about whether the framework can measure
the dimensions it targets. The second class states \textbf{directional
predictions}---falsifiable claims about the sign of the score difference
between conditions, to be reported as confirmed, refuted, or inconclusive
per §6.2.

\paragraph{Framework properties.} The pilot is designed to demonstrate that
the framework can be operationalised on a real artifact:
\begin{itemize}
    \item \textbf{FP1 (Structural Integrity).} The framework can measure
    file placement, Server/Client boundary usage, and naming patterns in
    AI-generated Next.js code, producing a 0--5 score per run on a
    representative feature.
    \item \textbf{FP2 (Type \& Contract Safety).} The framework can measure
    TypeScript error counts and Zod-validation coverage in AI-generated
    Next.js code, producing a 0--5 score per run that combines a
    Type-Safety sub-score and a Contract-Safety sub-score via the
    weakest-link rule.
    \item \textbf{FP3 (Coverage \& Completeness).} The framework can
    enumerate AI-generated files against a feature-specific checklist and
    produce a 0--5 per-run score that reflects required-artifact presence.
\end{itemize}

\paragraph{Directional predictions.} Each directional prediction states
the expected sign of the difference between Condition~A (SmartKit at full
setup) and Condition~B (convention-naive scaffold) on a representative
feature---the \code{isEnabled(flagKey, userId?)} utility. Predictions are
evaluated as \emph{confirmed} (all runs in the predicted direction),
\emph{refuted} (no runs in the predicted direction), or
\emph{inconclusive} (intermediate), per the adaptive-N protocol
documented in §6.2.

\begin{itemize}
    \item \textbf{DP1 (Structural).} Condition~A is predicted to place the
    utility in the SmartKit feature-based layout in the majority of runs;
    Condition~B is predicted to use a root-level or flat structure.
    \item \textbf{DP2 (Type \& Contract).} Condition~A is predicted to
    produce Zod-typed schema definitions in the majority of runs;
    Condition~B is predicted to use raw string types.
    \item \textbf{DP3 (Coverage).} Condition~A is predicted to include a
    centralized test file in the majority of runs;
    Condition~B is predicted to omit a test file in the majority of runs.
\end{itemize}
\noindent\textit{Formal definitions and exact expected file paths appear in §6.2.}

Framework properties and directional predictions serve different
purposes. A framework property is a descriptive claim about the
framework itself; it cannot be refuted by pilot data, only supported or
unsupported. A directional prediction is a falsifiable claim about the
artifact and is the only class of claim to which the binary
\emph{confirmed/refuted/inconclusive} verdict applies. The pilot
protocol (§6.2) documents how each is reported. Full
statistical validation---including larger sample sizes, cross-tool
replication, and developer-participant studies---remains future
empirical work.

Designing an evaluation framework for AI-generated Next.js boilerplate encounters three key challenges that distinguish it from existing code generation benchmarks. First, framework conventions are implicit and distributed across documentation, error messages, and community patterns, requiring deliberate extraction into enumerable, testable rules rather than relying on predefined quality criteria. Second, convention violations in Next.js App Router manifest primarily at runtime. Server/Client boundary violations produce errors only when executed, so evaluation must go beyond static analysis to capture dynamic execution behaviour. Third, the evaluation dimensions are orthogonal: structural integrity violations do not imply type errors, and coverage gaps operate independently of both, demanding a multi-dimensional framework rather than a single composite score. Pearson correlation analysis across runs (Section~\ref{sec:future-work}) would empirically test whether the three dimensions are genuinely orthogonal or merely weakly coupled; the executed pilot's small per-arm sample precludes such analysis.

The contributions of this thesis are as follows. First, it proposes a three-dimensional evaluation framework (Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness) for measuring how closely AI coding assistants adhere to Next.js App Router conventions. The framework addresses a gap left by existing benchmarks, which score algorithmic correctness rather than framework-specific quality. Second, it releases SmartKit, an open-source Next.js boilerplate demonstrating feature-based modularity, explicit Server/Client boundaries, and type-safe contracts. SmartKit supplies both the conventions the framework measures and the target codebase it measures them on; all four Better Auth tables (user, session, account, verification), the billing feature (SePay integration with HMAC signature verification and idempotent webhook handling), and the email integration (Resend + React Email) are implemented at the current snapshot rather than deferred to future phases, supporting SmartKit's role as a functional SaaS boilerplate. Third, it releases the pilot protocol and the baseline comparison design as artefacts: a pre-registration document, a Condition~A vs.\ Condition~B comparison scaffold, a scoring rulebook, and a baseline-bootstrap script. The artefacts are concrete enough that another researcher can replicate the pilot without re-deriving the protocol from the thesis prose.

\section{Scope and Limitations}

To keep the empirical rigor and feasibility of this research within the resource envelope of a single-author thesis, the scope is strictly defined by the following parameters and limitations:

\begin{enumerate}
    \item \textbf{Framework scope:} Next.js App Router only. No comparison with Nuxt, Remix, or other meta-frameworks.
    \item \textbf{AI assistants:} Cursor used for the pilot empirical case study. Broader AI assistant evaluation (GitHub Copilot, Claude Code) is future work.
    \item \textbf{Project type:} Single representative Next.js project demonstrating SaaS patterns.
    \item \textbf{Pilot study limitation:} The empirical case study is a worked-example executed against a total of $10$ runs under a pre-registered adaptive schedule, distributed as $n=5$ Cond~A and $n=5$ Cond~B (the latter extended from $n=3$ to $n=5$ via the 2026-09-14 amendment to satisfy the comparative-CI gate) on a single representative feature, the \code{isEnabled(flagKey, userId?)} utility, which uses no service that SmartKit integrates. The pilot illustrates framework applicability and produces per-condition medians plus directional predictions (DP1--DP3), evaluated against the pre-registered verdict rule in §6.2. Both arms are at symmetric adaptive-$N=5$, so the comparative Bonferroni 99\% CI on the $A-B$ difference is now populated, but the per-arm sample is still far below the $n \approx 30$ required for inferential validation (Section~\ref{sec:future-work}). Cross-tool replication, larger-$N$ studies, and developer-participant validation remain future empirical work.
\end{enumerate}

These boundaries are deliberate methodological choices. Fixing the framework, the AI assistant, and the project type removes confounding variance so that any measured difference between structured and unstructured conditions can be attributed to the SmartKit approach alone.


\chapter{Background}
\label{sec:background}

Understanding the intersection of AI coding assistants and Next.js development requires grounding in three domains: the capabilities and limitations of current AI coding tools, the architectural patterns of the Next.js framework, and the principles of SaaS boilerplate design.

\section{AI Coding Assistants}

GitHub Copilot, Anthropic's Claude, and Cursor all use transformer-based LLMs fine-tuned for code understanding and generation. GitHub Copilot provides inline code completions and entire function generation within supported editors (using OpenAI's GPT series and Anthropic's Claude series models, with specific model versions varying over time). Anthropic's Claude offers conversational code assistance through the Claude Code CLI and IDE integrations. Cursor combines Claude with a custom codebase indexing system that enables context-aware suggestions across entire projects.

These assistants share common architectural elements. They process code through transformer-based models trained on large corpora of publicly available source code, learning statistical patterns that inform code generation. When producing completions, they consider surrounding code context, natural language comments, and project-wide information to generate relevant suggestions. Their effectiveness varies with programming language, task complexity, and code structure \parencite{yetistiren2023evaluating}.

Research documents both strengths and limitations. Dakhel et al. found that AI assistance benefits expert developers who can filter suboptimal suggestions but may harm novice developers who lack the expertise to identify incorrect or inefficient code \parencite{dakhel2023github}. Liu et al. documented that ChatGPT performs better on older problems (pre-2021) than newer ones, with a 48.14\% advantage on the Accepted rate, though it struggles with complex algorithms and domain-specific code, frequently generating solutions with security vulnerabilities and inefficient implementations \parencite{liu2024chatgpt}.

The task taxonomy for AI suitability shows that boilerplate generation represents a strength area. Zhang et al. observed that developers primarily use Copilot for boilerplate generation, test writing, and code explanation rather than novel algorithmic development \parencite{zhang2023practices}. Pandey et al. confirmed this pattern, finding strong AI performance on template generation and documentation tasks but weak performance on complex logic and integration code \parencite{pandey2024transforming}. These findings focus the study on boilerplate interaction as an appropriate domain for AI enhancement.

\section{Next.js Framework Architecture}

Next.js is a React meta-framework that provides server-side rendering, static site generation, and API capabilities within a unified application model. Version 13 introduced the App Router paradigm, fundamentally changing how React applications structure pages, layouts, and data fetching. Developers who learned the Pages Router encounter several App Router concepts that the older model did not surface, including Server/Client boundaries and file-system conventions for special files.

React Server Components represent a core innovation in Next.js App Router. These components execute exclusively on the server, which lets them access databases and sensitive operations directly without exposing logic to the client. The distinction between Server and Client components requires explicit marking through the \\usec directive, creating a boundary that developers must carefully manage. Incorrect placement of components across this boundary produces runtime errors and performance degradation.

The App Router organizes applications through a file-system-based routing mechanism. Each folder within the \filename{app/} directory corresponds to a route segment, with \filename{page.tsx} files defining the content for each route. Special files such as \filename{layout.tsx}, \filename{loading.tsx}, and \filename{error.tsx} provide shared UI and error handling across route hierarchies. This convention-driven structure enables rapid scaffolding but requires adherence to specific naming and placement patterns.

TypeScript integration in Next.js emphasizes type safety throughout the application. The framework provides typed interfaces for page properties, API request and response objects, and data fetching results. Achieving full type coverage requires consistent use of TypeScript patterns including generics, utility types, and strict mode configuration. AI coding assistants may generate code that compiles but violates framework conventions, producing runtime errors or subtle bugs.

\section{SaaS Boilerplate Patterns}

Software-as-a-service applications share common requirements that boilerplate frameworks address: user authentication, database access patterns, multi-tenancy support, and deployment configurations. The economics of SaaS development favor approaches that reduce per-project initialization effort while maintaining code quality and consistency.

Krüger et al. established that platform reuse reduces maintenance effort but involves upfront investment in framework adoption and learning curve \parencite{kruger2020empirical}. The trade-off explains the appeal of well-designed boilerplate templates that amortize initialization cost across multiple projects. Aleem et al. identified customization, scalability, multi-tenancy, security, integration, and fault tolerance as key factors in SaaS architecture decisions \parencite{aleem2019maturity}.

Modern scaffolding approaches build on model-driven architecture principles. Inayatullah and Azam showed that automated code generation reduces boilerplate development effort for cross-platform applications \parencite{inayatullah2019model}. Liu and Sra recently showed that LLMs have potential for automatically generating scaffolded user interfaces, reducing complexity for users in professional creative software \parencite{liu2025auggen}.

Meta-framework evaluation identifies architectural trade-offs across options. Prior work on framework adoption in software engineering has identified learnability, extensibility, and ease of migration as primary drivers of adoption, while framework lock-in and high configurability are commonly cited as major adoption risks \parencite{storey2016frameworkadoption}. Next.js App Router emphasizes React Server Components as a first-class primitive, while maintaining full compatibility with Client Components for interactive UI. The hybrid model creates specific conventions that boilerplate frameworks should encode.

\chapter{Related Work}
\label{sec:relatedwork}

This section surveys existing research on code generation benchmarks, empirical studies of AI-assisted development, and systematic literature reviews on AI for software engineering. The analysis identifies the specific gap this thesis addresses: the absence of framework-specific evaluation for AI coding assistants operating on Next.js boilerplate conventions.

\section{Code Generation Benchmarks}

The evaluation of AI coding assistants relies heavily on standardized benchmarks that measure code generation capability. Chen et al. introduced HumanEval as a foundational benchmark containing 164 hand-written programming problems with function signatures, docstrings, and unit tests \parencite{chen2021evaluating}. The benchmark evaluates models using Pass@1, Pass@10, and Pass@100 metrics. OpenAI's Codex achieved 28.7\% Pass@1 on this benchmark, establishing a baseline for subsequent model development.

HumanEval focuses exclusively on single-function Python code generation with algorithmic and reasoning requirements. The design prioritizes general programming capability over domain-specific or framework-aware generation. Yu et al. extended the benchmark concept with HumanEval Pro, adding self-invoking code generation tasks that require models to generate functions calling previously defined functions \parencite{yu2025humanevalpro}. Their work documented up to 30\% performance degradation on self-invoking tasks compared to standalone tasks, indicating that current benchmarks underestimate real-world code generation complexity.

SWE-bench represents a substantial advance in benchmark realism by evaluating AI models on real GitHub issues from popular Python repositories \parencite{jimenez2024swebench}. Each task requires understanding the issue description, locating relevant code, implementing a fix, and passing unit tests. Jimenez et al. found that state-of-the-art models resolved only a small fraction of issues --- Claude 2 solved approximately 1.96\% with BM25 retrieval (4.8\% with oracle retrieval) and GPT-4 only 1.74\% with oracle retrieval (0\% with BM25) --- and the gap between benchmark performance and practical software engineering capability is substantial.

Language-specific benchmarks identify further evaluation limitations. Petrukha et al. developed SwiftEval for Swift programming, finding that general-purpose benchmarks overestimated Swift code generation capability \parencite{petrukha2025swifteval}. Their language-specific benchmark documented 40--60\% performance gaps not captured by cross-language evaluations.

No existing benchmark evaluates framework convention adherence, boilerplate structure quality, TypeScript or Next.js-specific patterns, or multi-file scaffolding tasks. The benchmarks measure whether AI assistants can solve algorithmic problems or fix bugs in existing codebases, not whether they can generate framework-compliant boilerplate from scratch.

Several extensions and alternatives warrant mention. Liu et al. developed HumanEval+ and MBPP+ as rigorous extensions of the original benchmarks, finding that pass rates drop often by 30\% or more when evaluated against additional high-quality tests per problem \parencite{liu2024correct}. Zhuo et al. introduced BigCodeBench, which evaluates 1,140 fine-grained tasks combining diverse function calls with complex natural-language instructions \parencite{zhuo2024bigcodebench}. Hendrycks et al. proposed APPS, a 10,000-problem benchmark spanning introductory, interview, and competition-level coding challenges \parencite{hendrycks2021apps}. Jain et al. addressed the critical contamination problem through LiveCodeBench, which sources problems from recent competitive programming contests published after model training cutoffs \parencite{jain2024livecodebench}. Li et al. developed CodeReviewer for code review automation, an adjacent evaluation direction that assesses code quality dimensions relevant to AI-assisted development workflows \parencite{li2022codereviewer}. Each of these benchmarks measures distinct aspects of code generation or code quality capability, yet none evaluate the framework-specific convention adherence that the SmartKit framework targets.

\section{Empirical Studies on Developer Productivity}

Several empirical studies examine how AI assistance affects real developer workflows. Peng et al. conducted the seminal controlled experiment on GitHub Copilot with 95 recruited developers implementing an HTTP server in JavaScript \parencite{peng2023impact}. Their methodology used a treatment-control design with matched tasks, finding the 55.8\% completion time improvement cited earlier. Heterogeneous effects showed that less experienced developers benefited most from AI assistance.

The enterprise-level .NET study by Tariq et al.\ (SSRN, 2026; not peer-reviewed) extended this methodology to enterprise software development scenarios \parencite{tariq2026enterprise}. With 60 developers and 960 task observations across eight enterprise-oriented tasks, they measured task completion time, implementation errors, cyclomatic complexity, maintainability index, code smells, and NASA-TLX cognitive load scores. AI-assisted development reduced task completion time, errors, code smells, and cognitive workload while improving maintainability. The trade-off was that AI generated redundant abstractions and increased code verbosity, with effectiveness depending on developer expertise and continued oversight. Note that the Tariq et al. study focuses on .NET enterprise settings; its findings are cited as methodology precedent rather than as evidence about Next.js or AI-tool-specific effects.

Liu et al. assessed ChatGPT code generation quality across multiple languages and task types \parencite{liu2024chatgpt}. ChatGPT performs better on pre-2021 problems with a 48.14\% advantage on Accepted rate, but its ability to directly fix erroneous code through multi-round dialogue is relatively weak. Generated code often contained security vulnerabilities and inefficient implementations requiring human verification, though ChatGPT could resolve over 89\% of identified vulnerabilities through multi-round fixing. Yetiştiren et al. documented that Copilot generates functionally correct code for many problems but frequently produces solutions with higher cyclomatic complexity and lower readability than human-written solutions \parencite{yetistiren2022assessing}.

AlOmar et al. examined developer-ChatGPT refactoring conversations, finding that developers frequently needed multiple iterations to achieve satisfactory refactoring \parencite{alomar2024refactoring}. AI often missed design-level improvements, and common anti-patterns emerged in developer-AI refactoring interactions. AI effectiveness therefore depends on the structure of the interaction and on the developer's ability to guide refinement, not only on the tool itself.

Hou et al. conducted a systematic literature review of 395 research articles on LLMs for software engineering from 2017--2024 \parencite{hou2024llmse}. Code generation (35\%) and code repair (25\%) are the most studied application areas. Most studies use benchmark evaluation (60\%) rather than human evaluation, and reported effectiveness varies widely by task type. The review identified research gaps in security, requirements engineering, and empirical studies. Framework-specific boilerplate evaluation would begin to address these gaps.

Russo et al. analyzed GenAI adoption complexity, identifying five key dimensions: technical, organizational, individual, process-related, and ethical \parencite{russo2024navigating}. Technical capability was necessary but insufficient; human factors including trust, skill, and workflow integration were critical success factors. Evaluating framework-specific boilerplate tools therefore requires attention to how well they integrate with developer workflows and support skill development.

\section{Evaluation Methodology}

The refinement of AI-generated code has received attention as a complementary evaluation dimension. Liu et al. analyzed 4,066 ChatGPT-generated programs across 2,033 programming tasks in Java and Python \parencite{liu2024refining}. Of these programs, 2,756 were deemed correct, 1,082 produced wrong outputs, and 177 contained compilation or runtime errors; 1,930 additional programs suffered from maintainability issues identified through static analysis. Their automated refinement pipeline using static-analysis feedback improved code quality by more than 20\%. Evaluation frameworks should therefore measure both initial generation quality and the effort required for refinement.

Ouyang et al. studied the non-determinism of ChatGPT in code generation \parencite{ouyang2025nondeterminism}. Across 829 problems in three benchmarks, the ratio of coding tasks with zero equal test output across different requests ranged from 47.56\% (HumanEval) to 75.76\% (CodeContests). Setting the temperature to 0 does not guarantee determinism, despite being a common practice. Reliable assessment therefore requires multiple runs with confidence intervals rather than single-point measurements.

Beller et al. proposed the DAT framework for measuring software development productivity at Meta \parencite{beller2026dat}. The approach combines diff authoring time, survey-based metrics, and AI tool-specific productivity measures. The DAT framework models a path for evaluating AI-boilerplate interaction that balances quantitative performance metrics with qualitative developer experience assessment.

Nguyen-Duc et al. outlined a research agenda for GenAI in software engineering, emphasizing code generation quality, testing and verification, developer experience, education and training, ethics and security, and process and project management \parencite{nguyenduc2025genai}. The agenda explicitly calls for standardized evaluation and longitudinal studies, requirements that framework-specific evaluation frameworks can begin to satisfy.

Sauvola et al. projected four primary future scenarios for generative AI in software development, ranging from legacy integration to clean-slate and networked development, with software production shifting toward higher-level design and oversight roles as routine coding tasks become increasingly automated \parencite{sauvola2024future}. Research on optimizing AI interaction patterns, including framework-specific boilerplate conventions that reduce the cognitive overhead of AI-assisted development, follows from this projection.

\section{Research Gap Summary}

The reviewed literature establishes that AI coding assistants improve developer productivity on repetitive tasks, that boilerplate generation represents an AI strength area, and that existing benchmarks measure algorithmic capability rather than framework convention adherence. To the author's knowledge---given the structured-but-non-exhaustive literature search described in the next section---no prior work has specifically evaluated AI tool effectiveness on Next.js App Router conventions, React Server Components patterns, TypeScript-first boilerplate structures, or full-stack framework-specific best practices. This gap is independently supported by Hou et al.\ (2024)'s systematic review of 395 LLM-SE articles, which does not list framework-specific convention adherence as a separately tracked evaluation category \parencite{hou2024llmse}; the review's documented research gaps (security, requirements engineering, empirical studies) likewise do not overlap with framework-specific boilerplate evaluation. This thesis proposes a Next.js boilerplate framework engineered for AI interaction and an evaluation methodology that measures framework-specific quality dimensions, reporting both as design-stage contributions.

\section{Alternative Approaches to AI-Codebase Alignment}

The structural approach taken by SmartKit is one of several strategies that researchers and practitioners have explored to improve AI-codebase alignment. This section briefly reviews these alternatives and justifies why the structural approach was selected for this thesis.

\textbf{Prompting strategies} represent the most lightweight alternative. Enhanced system prompts, few-shot examples, and retrieval-augmented generation (RAG) can improve AI output quality without modifying project structure. Prompting approaches suffer from context window limitations, require repeated re-instruction across sessions, and cannot enforce consistency across a codebase without external governance. Hou et al.\ (2024) note in their systematic review that most LLM-for-SE studies use benchmark evaluation (60\%) rather than human evaluation, and reported effectiveness varies widely by task type; this leaves open the question of how prompting-only approaches hold up outside benchmark settings \parencite{hou2024llmse}. Prompting alone cannot address the structural convention-adherence gap the review identifies.

\textbf{Enhanced documentation} such as thorough READMEs, inline comments, and architecture decision records (ADRs) can guide AI behavior. Documentation requires human maintenance, is easily ignored by AI systems generating new code, and does not provide machine-readable enforcement mechanisms.

\textbf{Linter and formatter configurations} (ESLint, Prettier) can catch some convention violations but operate post-generation rather than preventing them. These tools validate style, not semantics; they cannot enforce feature boundaries or Server/Client component conventions that require architectural awareness.

The \textbf{structural approach} taken by SmartKit addresses these limitations by encoding conventions at the project structure level. Conventions become discoverable by AI systems through file location and naming patterns, are enforced through project structure rather than developer vigilance, and provide reusable templates that scale across features. The structural approach works alongside prompting and documentation, not as a replacement.

\paragraph{Caveat on the alternative-approaches dismissals.} The dismissals of prompting, enhanced documentation, and linter-based enforcement above are \emph{design-stage reasoning} based on prior literature, not empirical comparisons. The pilot's Condition~A advantage is the \emph{combined} effect of multiple overlapping signals---the \filename{AGENTS.md} instructions, the visible example features (\filename{features/auth/}, \filename{features/billing/}), and the existing linter/Zod configuration---and the executed pilot does not isolate ``structural'' conventions from the prompting, documentation, and tooling layers that operate alongside them. A controlled comparison of structural vs.\ prompting vs.\ documentation vs.\ linter-only conditions is left as future work (Section~\ref{sec:future-work}); the present thesis reports only the bundled effect of the SmartKit convention envelope.

\chapter{Proposed Solution}
\label{sec:solution}

This section presents the design of SmartKit, a Next.js boilerplate framework engineered to optimize interaction with AI coding assistants. The design synthesizes empirical findings from the literature with domain-specific analysis of Next.js conventions to produce a codebase structure that improves AI comprehension and output quality.

\section{Design Rationale}

Zhang et al. found that structured, well-documented codebases improve AI coding assistant performance \parencite{zhang2023practices}. Barke et al. showed that grounded prompting, providing relevant code context, improves AI output quality \parencite{barke2022grounded}. The SmartKit design applies these findings through concrete architectural decisions: encode conventions explicitly so that AI systems can discover them, group related code so that context stays narrow, and define type-safe contracts so that data shapes remain explicit.

These principles translate into four concrete design choices, each chosen over an alternative.

\textbf{Feature-based modularity over layer-based organisation.} Many Next.js projects organise code by technical layer (\filename{components/}, \filename{lib/}, \filename{hooks/}) or by page. Layer-based organisation creates wide import graphs: a single component may transitively import from dozens of files, so an AI system generating a new component receives a large, undifferentiated context. Feature-based modularity confines all code for one feature (schemas, actions, components, emails, types) within a single directory, giving the AI a narrow, self-contained context window. The trade-off is that cross-cutting concerns (shared utilities, types, or components) require deliberate extraction to a shared layer; this overhead is acceptable for SaaS boilerplate where the feature boundary is the primary decomposition axis.

\textbf{Drizzle ORM over Prisma.} Prisma uses a schema-first DSL (\filename{.prisma} file) that generates a client; Drizzle uses a TypeScript-first schema directly in \filename{.ts} files, co-located with the application code. The TypeScript-native approach means Drizzle schemas are importable as regular modules without a generated-client intermediary, and schema changes propagate through TypeScript's own type inference without a separate code-generation step. For AI-assisted code generation, co-located TypeScript schemas are more likely to be surfaced in context than an external DSL file; the AI can read and extend them using the same language model it uses for the rest of the codebase. The trade-off is that Drizzle requires more explicit SQL awareness from the developer; Prisma's generated client abstracts SQL differences.

\textbf{Explicit Server/Client boundaries over tRPC-based type sharing.} tRPC provides end-to-end type inference across the Server/Client boundary by sharing a single TypeScript interface definition. This eliminates a class of type errors but requires a separate router definition and does not enforce the architectural boundary at the file level. SmartKit instead uses Next.js's native \usec directive for Client Components and the \pkg{server-only} import for server-only utilities, supplemented by Zod schemas shared across the boundary (see below). The native mechanism is framework-default rather than library-specific, which means the conventions survive beyond the SmartKit codebase and transfer to plain Next.js projects; tRPC conventions do not. The trade-off is that the native mechanism requires explicit developer discipline; tRPC enforces the boundary automatically through its type system.

\textbf{Zod schemas as the single source of truth across the Server/Client boundary.} React Server Components and Client Components communicate through typed props, but there is no built-in mechanism to ensure that the type on the server matches the type on the client. SmartKit uses Zod schemas, defined once in \filename{features/<name>/types/}, parsed at the server action boundary, and reused on the client via \pkg{z.infer}. This means a single schema definition is the source of truth for both runtime validation (server action) and TypeScript type inference (client component props), and the AI can read and extend the schema using the same Zod syntax it encounters in existing features. The trade-off is that Zod adds a runtime dependency and a learning curve for developers unfamiliar with schema-first validation.

\section{Feature-Based Modular Architecture}

Many Next.js projects organize code by technical layer (components/, lib/, hooks/) or by page structure. SmartKit instead adopts feature-based modularity, where each feature contains all code necessary for its functionality. An authentication feature, for instance, includes database schemas, API routes, React components, form validation schemas, and email templates within a single directory.

This organization improves AI comprehension by narrowing the search space for relevant context when AI generates code for a specific feature. The scope of changes becomes explicit, which reduces the risk of AI-generated code violating feature encapsulation. The organization also creates natural boundaries for testing and deployment that align with developer mental models.

\section{Server/Client Boundary Conventions}

React Server Components introduce an explicit boundary between server-only and client-accessible code. SmartKit uses Next.js's native Server/Client boundary mechanism through the \usec directive for Client Components and the \pkg{server-only} import for server-only utilities. The pattern extends Next.js's convention-based routing to component architecture.

Server/Client boundaries affect data flow design. Server Components can access databases and environment variables directly, while Client Components must receive data through props or server actions. AI systems can invoke type-safe server actions from Client Components, which keeps
data flow consistent as new components are generated.

\section{Database Schema Patterns}

SmartKit uses Drizzle ORM with PostgreSQL to provide type-safe database access throughout the application. The schema design follows conventions that AI systems can learn and reproduce. Each table schema includes columns with explicit types, relations defined with foreign keys, and indexes specified for query optimization.

The Drizzle schema pattern enables AI-generated code to access the database through type-safe query builders. AI systems can examine existing schema patterns and generate consistent queries that maintain type safety across the application. Ad-hoc database access that bypasses type checking or violates query conventions is discouraged.

Schema files for Better Auth's shared tables (\code{user}, \code{session}, \code{account}, \code{verification}) are all implemented in \filename{src/database/schema/}, an infrastructure layer outside the Feature-Sliced Design (FSD) hierarchy, alongside the billing-specific tables (\code{billing}, \code{payment\_transactions}) used by \filename{features/billing/}. The four Better Auth tables cover the \code{user} identity, the \code{session} and \code{account} records used for sign-in flows, and the \code{verification} table for email-verification challenges; relations between them are declared in \filename{src/database/schema/relations.ts}. All Drizzle schema definitions are kept in this single directory so that \pkg{drizzle-kit} can scan them reliably and all features can import from a common location. The placement keeps database patterns centralized while remaining directly importable from any feature module.

\section{Type-Safe API Contracts}

API routes in SmartKit use Zod schemas for request and response validation. These schemas serve dual purposes: runtime validation of incoming requests and TypeScript type inference for handler code. AI systems can examine Zod schemas to understand API contracts, generating code that respects type constraints without requiring explicit type annotations.

The shared schema pattern enables consistent validation across frontend form components and backend API handlers. The same Zod schemas validate both client-submitted forms and server-handled requests. The match between frontend and backend validation reduces the gap between AI-generated client-side and server-side code, producing more coherent implementations.

\chapter{Implementation}
\label{sec:implementation}

This chapter describes the technical implementation of the SmartKit framework, covering the architecture, technology stack, and key design decisions that enable AI-friendly development patterns.

\section{Technology Stack}
\label{sec:technology-stack}

This section describes the technical implementation of the SmartKit framework using Next.js 16.2.12 and associated technologies. The implementation shows how the design principles translate into working code.\footnote{The pilot evaluation (Chapter~\ref{sec:evaluation}) exercises a single representative feature --- the \code{isEnabled(flagKey, userId?)} flag utility --- that touches none of SmartKit's integrated services. The billing (Section~\ref{sec:billing-sepay}), authentication, and email integrations documented below are not exercised by the pilot; they are documented here as part of SmartKit's second role --- a usable SaaS boilerplate --- independent of the evaluation framework. See Section~\ref{sec:integrations-and-pilot} for the relationship between the integrations and the pilot feature.}

\subsection{Stack Selection Rationale}
\label{sec:stack-rationale}

Each component of the stack was chosen because it reinforces one of the three evaluation dimensions rather than for its own sake. The selection rests on three guiding principles:

\begin{enumerate}
  \item \textbf{App Router-first.} Next.js~16's App Router is the architectural surface that Structural Integrity measures directly: Server/Client boundaries, file-system routing, and the \usec/\pkg{server-only} primitives are framework defaults rather than library conventions, which means the rules encoded in the rubric transfer to plain Next.js projects rather than coupling them to SmartKit.
  \item \textbf{Type-safe contracts at the boundary.} TypeScript~5.7 strict mode provides the compile-time signal that Type~\&~Contract Safety reads from \code{tsc --noEmit}, while Zod~4 schemas colocated in \filename{features/<name>/types/} are parsed at the Server Action boundary and reused on the client via \pkg{z.infer}. A single schema is the source of truth on both sides of the Server/Client boundary that Coverage~\&~Completeness checks for, so the AI tooling reads and extends the same Zod syntax it encounters in existing features.
  \item \textbf{Server/Client boundary as a first-class primitive.} The framework's runtime failures (event handlers crossing the boundary, server-only imports leaking to the client) are the failure mode the thesis targets, so the chosen tools must surface those failures naturally: Server Components fetch data directly through Drizzle, Server Actions in \filename{features/<name>/actions/} call \code{revalidatePath} after writes, and Client Components receive typed props without an intermediate client-side data layer. Adopting a tRPC-style shared-router alternative would have hidden the boundary inside library types and removed the very signal the Structural Integrity rubric is designed to read.
\end{enumerate}

|   +-- lib/              # Shared utilities
|   +-- config/           # Site and environment config
+-- docs/                 # Documentation

The \filename{app/} directory is placed at \filename{src/app/} because that is the path Next.js~16's App Router reads as the routing surface. Pages and layouts live here, not feature code, so the route composition that the Structural Integrity rubric inspects (server-only imports, \usec directives, file-system routing) is read directly from this directory by the framework itself rather than from a custom layout the AI would have to learn. Each route imports feature modules from \filename{src/features/} but never the other way around, which is what keeps the page-vs-feature separation enforceable by static analysis: a feature module cannot accidentally import from a route, because that would invert the dependency direction the App Router expects.

The \filename{database/} directory is placed at \filename{src/database/} because \pkg{drizzle-kit} reads schemas from a single configured path; co-locating every table in \filename{database/schema/} means a migration scan touches one root rather than chasing feature-local schema files. Hosting the four Better Auth tables (\filename{user.ts}, \filename{session.ts}, \filename{account.ts}, \filename{verification.ts}), the relations graph in \filename{relations.ts}, and the billing tables (\filename{billing.ts} with \code{payment\_transactions}) together lets any feature module import shared row types (\filename{database/schema/index.ts}) without depending on a sibling feature's directory. The \filename{database/db.ts} client also sits here so that the \pkg{pg} pool, the \filename{env.DATABASE\_URL} read, and the schema registration live in one file --- the runtime surface that Type~\&~Contract Safety checks via \code{tsc --noEmit} stays minimal and central.

The \filename{lib/} directory is placed at \filename{src/lib/} because the utilities inside (the \code{cn} class-name helper in \filename{utils.ts}, the typed \filename{env.ts} reader, any future cross-feature helper) do not belong to a single feature. Putting \code{cn} inside \filename{src/features/auth/lib/} would force the billing feature to import from auth just to merge class names, which inverts the feature-isolation rule AGENTS.md sets and creates a spurious cross-feature dependency for a generic helper. The directory therefore functions as a third tier, sitting above \filename{src/features/<name>/} in the import graph, for code that every feature may need but no feature owns. The \code{env.ts} reader belongs here for the same reason: the database client, the auth handler, and the billing webhook all read environment variables, so the reader sits at a level that all three can import without forming a cycle.

The \filename{features/flags/} directory sits at the repository top level rather than inside \filename{src/}. This placement is deliberate: the AGENTS.md rule that new feature code should live under a feature-named directory does not enforce a \filename{src/} prefix for the pilot's representative feature, and keeping \filename{features/flags/} at the top lets the AI encounter it immediately when scanning the repo root. The pilot's baseline-bootstrap script adds this directory so that the framework has a non-trivial integration target for the Coverage dimension without requiring a hand-written feature.

Internally, \filename{features/flags/} follows the same conventions as \filename{src/features/auth/}: \filename{lib/} holds the \code{isEnabled} implementation, \filename{types/} holds the Zod-derived \code{FlagKey} schema, and \filename{index.ts} is the public API barrel. The unit test sits at \filename{src/tests/features/flags/is-enabled.test.ts}, inside \filename{src/}, in line with the centralized-test convention in AGENTS.md. Its presence is what makes the pilot executable against the framework without having to first create a feature by hand.

\section{Core Feature Implementation}
\label{sec:core-feature-implementation}

This section details the implementation of the three core patterns that the evaluation rubric targets.

\subsection{Feature Flag Resolution}
\label{sec:feature-flag-resolution}

The feature flag system implements a three-tier resolution hierarchy that evaluates override sources in priority order. This design reflects the convention encoding principle: per-user overrides take precedence over environment variables, which take precedence over static defaults. The implementation is located in \filename{features/flags/lib/is-enabled.ts}, which is marked \pkg{server-only} to enforce the server-side boundary.

The Zod schema that defines the allowed \code{FlagKey} values is colocated in \filename{features/flags/types/flags.ts}:

\begin{lstlisting}[
  language=TypeScript,
  caption={Zod schema for feature flag keys.},
  label={lst:flag-key-schema},
  basicstyle=\ttfamily\scriptsize,
]
import { z } from "zod";

export const FlagKeySchema = z.enum([
  "FEATURE_NEW_DASHBOARD",
  "FEATURE_BILLING_ENABLED",
  "FEATURE_DARK_MODE",
]);

export type FlagKey = z.infer<typeof FlagKeySchema>;
\end{lstlisting}

The \code{isEnabled} function implements the three-tier resolution with in-memory caching:

\begin{lstlisting}[
  language=TypeScript,
  caption={The isEnabled utility with three-tier resolution and 5-minute TTL cache.},
  label={lst:is-enabled-impl},
  basicstyle=\ttfamily\scriptsize,
]
import "server-only";
import { FlagKeySchema, type FlagKey } from "../types/flags";

const TTL_MS = 5 * 60 * 1000;

// Two parallel maps -- values holds the resolved boolean, expirations
// holds the wall-clock timestamp at which the entry expires.
const values = new Map<string, boolean>();
const expirations = new Map<string, number>();

const buildCacheKey = (flag: FlagKey, userId?: string): string =>
  userId ? `${flag}__${userId}` : `${flag}___`;

const readUserOverride = (
  _userId: string | undefined,
  _flag: FlagKey,
): boolean | undefined => {
  // Per-user DB override is not wired in this pilot.
  return undefined; // signals "no override, fall through"
};

const readEnvOverride = (flag: FlagKey): boolean | undefined => {
  const raw = process.env[`FLAG_${flag}`];
  if (raw === "true") return true;
  if (raw === "false") return false;
  return undefined;
};

export function isEnabled(
  flag: unknown,
  fallback: boolean = false,
  userId?: string,
): boolean {
  const parsed = FlagKeySchema.safeParse(flag);
  if (!parsed.success) {
    throw new Error(
      `Invalid flag key: ${JSON.stringify(flag)}. ` +
        `Allowed: ${FlagKeySchema.options.join(", ")}`,
    );
  }
  const key = buildCacheKey(parsed.data, userId);
  const now = Date.now();

  const expires = expirations.get(key);
  if (expires !== undefined && expires > now) {
    const cached = values.get(key);
    if (cached !== undefined) return cached;
  }

  let resolved: boolean | undefined =
    readUserOverride(userId, parsed.data) ??
    readEnvOverride(parsed.data) ??
    fallback;

  values.set(key, resolved);
  expirations.set(key, now + TTL_MS);
  return resolved;
}
\end{lstlisting}

\bigskip\noindent\textbf{Why this structure?}
The tiered design serves two purposes: (1) it mirrors the production pattern where feature flags support gradual rollouts via environment variables before per-user targeting, and (2) it creates a clear server-side boundary that the Structural Integrity dimension reads---the function is marked \pkg{server-only} in the barrel export, never accessible to client components without a typed prop interface. The 5-minute TTL prevents unbounded memory growth while keeping flag values reasonably fresh for environment-driven rollouts.

\subsection{Server/Client Boundary Enforcement}
\label{sec:server-client-boundary}

The framework's runtime failures (event handlers crossing the boundary, server-only imports leaking to the client) are the failure mode the thesis targets. Next.js surfaces these failures naturally through build-time errors: Server Components fetch data directly through Drizzle, Server Actions in \filename{features/<name>/actions/} call \code{revalidatePath} after writes, and Client Components receive typed props without an intermediate client-side data layer.

To prevent accidental client bundling of server-only code, the framework uses the \pkg{server-only} package~\cite{server-only-npm}:

\begin{lstlisting}[
  language=TypeScript,
  caption={Using server-only to prevent client bundling.},
  label={lst:server-only-usage},
  basicstyle=\ttfamily\scriptsize,
]
import "server-only";

// This module cannot be imported into Client Components.
// Next.js will throw a build-time error if attempted.
export async function getServerData() {
  // server-side only logic
}
\end{lstlisting}

\bigskip\noindent\textbf{Why this pattern?}
The \pkg{server-only} import serves two purposes: (1) it mirrors the production pattern where server utilities must never cross to the client, and (2) it creates a clear server-side boundary that the Structural Integrity dimension reads. The function is marked \pkg{server-only} in the barrel export, never accessible to client components without a typed prop interface.

\subsection{Evaluation Infrastructure}
\label{sec:eval-infrastructure}

To operationalize the three evaluation dimensions, the framework includes an automated scoring script (\filename{scripts/score-flag.ts}) that reads source files and computes a 0--5 score per dimension. The script is read-only: it does not mutate the run directory and does not call any AI/LLM for scoring.

The structural integrity scoring logic detects server/client boundary violations:

\begin{lstlisting}[
  language=TypeScript,
  caption={The structural integrity scoring logic from score-flag.ts.},
  label={lst:scoring-logic},
  basicstyle=\ttfamily\scriptsize,
]
// Pattern detection for server-only imports
const SERVER_ONLY_PATTERNS = [
  /import\s+["']server-only["']/,
  /from\s+["']server-only["']/,
];

async function scoreStructural(runDir: string) {
  const tsFiles = await findTsFiles(runDir);
  let hasServerOnly = false;
  let hasUseClient = false;

  for (const f of tsFiles) {
    const content = await readFile(f, 'utf-8');
    hasServerOnly = SERVER_ONLY_PATTERNS.some(
      p => p.test(content)
    );
    hasUseClient = /['"]use client['"]/.test(content);
  }

  // Scoring: path_match (0/0.5/1) + feature_complete (0/0.5/1)
  let pathMatch = 0;
  let featureComplete = 0;

  if (inFeatures) pathMatch = 1;
  if (hasServerOnly) featureComplete = 1;
  if (hasUseClient) featureComplete = 0; // violation

  return Math.round((pathMatch + featureComplete) * 2.5);
}
\end{lstlisting}

\bigskip\noindent\textbf{How the rubric maps to code.}
Each scoring function returns 0 (violation), 3 (partial), or 5 (pass) per sub-criterion, which are then combined into a 0--5 dimension score. The script aggregates these per file, then averages across the project to produce the dimension score. This design mirrors the rubric's qualitative descriptors: files that expose server internals to the client boundary score 0, files that partially comply score 3, and files that follow conventions score 5.

The Type \& Contract Safety dimension runs \code{tsc --noEmit} and counts \code{: any} occurrences, while Coverage \& Completeness enumerates required files (\code{is-enabled.ts}, \code{is-enabled.test.ts}, \code{flags.ts}, \code{index.ts}) against a reference checklist. The complete rubric implementation is in \filename{smartkit/scripts/score-flag.ts}.

\section{Billing and SePay Integration}
\label{sec:billing-sepay}

The \filename{features/billing/} feature implements a payment and order-management flow backed by SePay, a Vietnamese payment gateway. SePay webhook handling uses HMAC-SHA256 signature verification (\filename{signature.ts}) and idempotent processing via a payment-transactions dedup key (\filename{payment-transactions.ts}), so that repeated delivery attempts under transient failures produce a no-op rather than duplicate side effects. This feature serves as a second-tier pattern source for AI code generation in Condition~A: its feature-based directory layout, server-action conventions, and Zod schema patterns are visible to the AI alongside \filename{features/auth/}, giving the AI additional convention anchors beyond the explicit AGENTS.md rules. The billing feature's relation to the pilot evaluation is summarised in the scope note at the start of this chapter (and detailed further in \S\ref{sec:integrations-and-pilot}); the SePay integration is described here as part of SmartKit's second role as a usable SaaS boilerplate and has not been independently audited for security, load, or test coverage.

\section{Evaluation Framework}
\label{sec:evaluation-framework}

\subsection{Three Dimensions}
\label{sec:dimensions}

The evaluation uses a multi-dimensional quality framework that captures different aspects of boilerplate quality. The framework extends existing benchmark methodology to address framework-specific concerns that existing evaluations overlook; the specific literature gap that motivates this framework is documented in Chapter~3 (Related Work, \S\ref{sec:relatedwork}). SmartKit's contribution is to instantiate the missing framework-specific convention-adherence measurement dimension for Next.js App Router.

The three dimensions capture distinct, non-overlapping aspects of boilerplate quality that affect real-world usability. Rather than measuring only output correctness, the framework assesses whether generated code can be integrated into production codebases without convention violations or type safety issues. Each dimension maps to an automated measurement approach and corresponds to a specific failure mode observed in AI-generated Next.js code.

\textbf{Unit of analysis.} Scoring is performed per generated file: each file receives one score per dimension, and feature-level scores are computed as the median across constituent files. The median is used rather than the mean because individual files within a feature may exhibit extreme outlier scores due to edge-case generation failures (e.g., a single malformed file), and the median is robust to such outliers.

\textbf{Structural Integrity} assesses whether generated code follows Next.js conventions for file location, naming, Server/Client component boundaries, and App Router patterns. Automated checking uses the \texttt{score-flag.ts} script (file-placement checks, \texttt{server-only} import detection, \texttt{'use client'} directive checks, barrel-file verification) specific to Next.js structural conventions. The dimension captures violations such as incorrect file placement in the \filename{features/} directory, missing \usec directives on client components, and non-standard naming patterns that break routing.

\textbf{Type \& Contract Safety} captures two related but distinct quality signals, treated as sub-scores that combine into a single Type \& Contract Safety score on the 0--5 rubric. \emph{Type Safety sub-score} focuses on compile-time checks: \code{tsc --noEmit} error counts and \pkg{@typescript-eslint/}\pkg{no-explicit-any} occurrences signal whether generated code introduces type regressions into the codebase. \emph{Contract Safety sub-score} focuses on runtime validation: the proportion of API route handlers that include Zod schemas for request/response validation indicates whether the generated feature is schema-validated at the API boundary (input parsing and type narrowing enforced at runtime via Zod), not production-deployment-ready without additional hardening such as security review and load testing (see Section~\ref{sec:limitations}). Sub-score combination rule: the Type \& Contract Safety dimension score equals the lower of (Type Safety sub-score, Contract Safety sub-score) on the 0--5 scale, reflecting that a single weak sub-signal is not offset by a strong other. This combination rule is an inferred design choice (alternative rules such as arithmetic mean or weighted product could be substituted without changing the underlying sub-scores); the chosen lower-of rule privileges robustness against hidden weakness in either sub-dimension.

\textbf{Coverage \& Completeness} evaluates whether generated boilerplate includes all necessary artifacts for a functional feature. Table~\ref{tbl:coverage-checklist} shows the reference checklist for the \code{isEnabled} feature flag utility used in the pilot. Completeness is measured by enumerating generated files against the checklist and computing a coverage ratio (files present divided by required files). Missing artifacts indicate incomplete boilerplate that requires additional developer effort to make functional.

\subsubsection{Relationship between SmartKit Integrations and the Pilot Feature}
\label{sec:integrations-and-pilot}

SmartKit instantiates the framework conventions across multiple feature areas, including billing (SePay integration), authentication (Better~Auth), and email (Resend). These integrations exist because the artifact is a usable SaaS boilerplate, not because the evaluation framework requires them. The pilot deliberately selects a feature---the feature-flag check utility---that uses \emph{none} of the integrated services, in order to isolate the effect of convention encoding from the effect of having integrated services available. If the pilot used a feature that integrates SePay or Resend, any observed difference between Condition~A and Condition~B would conflate convention encoding with integration availability. The integrations remain first-class in the artifact; their relation to the pilot evaluation is summarised in the scope note at the start of this chapter. This separation is what allows the framework to remain generalisable beyond SmartKit: a developer using a different stack can encode the same conventions without SePay, Resend, or Better~Auth, and the framework still measures the same three dimensions on any generated feature.

A second, related point concerns the role of the integrations during the AI session. In Condition~A, the AI sees the full SmartKit file tree, including \filename{features/billing/} (SePay HMAC, idempotency), \filename{features/auth/} (Better~Auth schemas and server actions), and the Resend email templates under \filename{features/auth/emails/}. These files belong to SmartKit's second role as a usable SaaS boilerplate (see the scope note at the start of this chapter); they encode the SmartKit convention envelope --- feature-based folder structure, colocated server actions, Zod schemas in \filename{types/}, \pkg{server-only} boundaries, and \code{revalidatePath} after mutations. The AI in Condition~A pattern-matches this envelope when generating the pilot feature, even though the pilot feature itself does not call any of the integrated services. In Condition~B, none of these pattern sources are available, so the AI must invent both the utility and its surrounding convention. The score difference between conditions therefore measures the convention envelope, not the integration surface. The convention envelope is what the framework is designed to capture; the integration surface is what makes SmartKit a usable SaaS boilerplate. Both are required for the thesis, but they play distinct roles. The integration surface contributes to the second thesis contribution---the SmartKit artifact as a working SaaS boilerplate---rather than to the pilot; the pilot is the instrument that exercises the framework on AI-generated code, while the integrations are the evidence that the framework conventions are usable in production code.

The standardised prompt's first resolution-order rule---``Per-user DB override, only if \code{userId} is passed''---is implemented in the pilot as a stubbed path: the generated \seqsplit{readUserOverride} helper returns \code{undefined} without querying any database layer, so the pilot feature genuinely touches neither Drizzle nor any external persistence. The stub keeps the resolution order observable in tests while leaving full DB-backed override as future work; this is consistent with the feature's design choice to avoid integrating any SmartKit service, including Drizzle, into the pilot scope. The relationship between this design choice and the Coverage rubric's level definitions (rubric A.5.3) is revisited in the pilot discussion (\S\ref{sec:pilot} and \S\ref{sec:limitations}), which explains the structural constraint the design imposes on the Coverage dimension; the corrected Coverage cells in Table~\ref{tbl:pilot-actual} and the correction footnote immediately following that table record the resulting scores.

\subsection{Design Rationale and Trade-offs}
\label{sec:design-rationale}

The evaluation framework design involves several deliberate choices that balance scope with feasibility.

\textbf{Dimension selection.} The three dimensions were designed to address the gap between output-oriented benchmarks (algorithmic correctness) and the framework-specific quality dimension that existing benchmarks do not measure. Each SmartKit dimension targets a distinct failure mode observed in AI-generated Next.js code: structural violations (file placement, Server/Client boundaries), type safety gaps, and missing boilerplate artifacts.

\textbf{Automated over manual evaluation.} The framework prioritizes automated metrics to enable reproducibility and scale. Expert review provides richer qualitative assessment, but automated checking ensures consistent evaluation across the large number of code samples required for meaningful comparison. Where qualitative judgment is necessary (e.g., structure quality assessment), LLM-as-judge with majority voting is a future option that was not exercised in the executed pilot; the pilot uses single-primary-rater manual scoring (deferred IRR; see \S7.2).

\textbf{6-level rubric across dimensions.} Each of the three~dimensions is scored on a 0--5 rubric (six integer levels). The per-dimension cell descriptions are detailed in §\ref{sec:pilot-rubric}; the rough mapping is: $0$ = missing artefact, $1$ = severe violation, $2$ = partial (in the right neighbourhood but wrong sub-detail), $3$ = acceptable, $4$ = good (level 3 + a specific bonus criterion, e.g.\ \code{server-only} for Structural), $5$ = excellent (level 4 + a second bonus criterion, e.g.\ barrel re-export). The exact level descriptions are dimension-specific and were inferred from related literature on code quality rubrics (the 0--5 scale mirrors industry convention for code-review rubrics); per-level cutoffs have not been calibrated against developer-experience data within this thesis.

\textbf{Single-framework focus.} The evaluation focuses exclusively on Next.js to maintain depth over breadth. Future work should extend the framework to Nuxt and Remix to assess generalizability of the approach.

\textbf{Confound control between conditions.} A central threat to the validity of the pilot results is confounding: the structured SmartKit condition and the unstructured condition differ \emph{primarily} in convention encoding, but they also differ in second-order ways that the executed pilot does not fully control. The most important residual confound is that the SmartKit repository exposes several example features (\filename{features/auth/}, \filename{features/billing/}, \filename{features/auth/emails/}) that the AI can use as pattern-matching anchors beyond the explicit AGENTS.md instructions. To isolate SmartKit's contribution from this confound, the pilot compared it against an unstructured Next.js baseline sharing the same dependency surface as SmartKit (Next.js 16.2.12, TypeScript 5.7.3, Tailwind CSS 4.3.3, Drizzle ORM 0.45.2 with PostgreSQL, Zod 4.4.3, Biome 2.5.6, Resend 6.18.1, and \pkg{better-auth} 1.6.x, plus the \filename{src/database/schema/} directory inherited from SmartKit) but with no feature-based \filename{src/features/} layout and no AGENTS.md. The exact dependency surface used to build the baseline is recorded in §\ref{sec:pilot-conditions} (Condition~B paragraph) for replication; the \code{smartkit-baseline/package.json} shipped alongside this thesis is the canonical record of resolved versions and lock state. The exact \code{create-next-app} CLI invocation and the post-creation edits (customised \filename{.env.example}, removal of \filename{AGENTS.md} and \filename{.cursor/rules/}) are kept in the baseline repository's git history and are not duplicated in the bound thesis. The pilot feature (\code{isEnabled(flagKey, userId?)}) was chosen for the same reason: it uses no service that SmartKit integrates (no Resend, Better~Auth, SePay, or Drizzle dependency beyond the schema), so the AI cannot copy a pattern from the example features. This design follows established experimental practice for fair comparison \parencite{peng2023impact}. This section refers to the baseline as the ``convention-naive scaffold'' to avoid confusion with the SmartKit repository directory itself; the build script that produces it is preserved alongside the thesis artefacts (§\ref{sec:pilot-protocol}).

The control artifact serves as the control condition, providing a baseline that isolates the effect of SmartKit's convention encoding from the effect of the underlying technology stack.

\subsection{Evaluation Metrics}

Quantitative metrics derive from automated analysis of generated code. \textit{Structural Integrity} uses Biome custom rules to check Next.js-specific file placement, naming, and Server/Client boundary conventions. \textit{Type \& Contract Safety} uses \code{tsc --noEmit} output to identify type violations and custom Biome rules for \emph{any}-type detection and Zod coverage. \textit{Coverage \& Completeness} uses file enumeration against a reference checklist per feature type.

Qualitative metrics derive from expert review of generated code. Reviewers assess whether generated code follows Next.js best practices, whether naming conventions are consistent, and whether the overall implementation aligns with framework expectations. The expert review layer follows an inter-rater reliability (IRR) protocol: two independent raters score the same generated artifacts, with a target Cohen's $\kappa$ $\geq$ 0.7. The automated scoring layer (Biome, \code{tsc --noEmit}) is deterministic and requires no IRR. The IRR protocol is documented here as a design; execution of the IRR pass is identified as future work pending availability of a second rater.

Productivity metrics such as diff authoring time and developer-reported productivity \parencite{beller2026dat} are not collected in the current pilot and remain future work; the executed pilot reports only per-run time-to-correct (ttc, in minutes) as a coarse timing signal. Task completion time, cyclomatic complexity, maintainability index, and code smell density are documented as design-stage metrics for a future developer-participant study.

\section{Pilot Methodology}
\label{sec:pilot}
\label{sec:pilot-protocol}

The pilot evaluates whether providing architectural convention documentation improves AI coding assistant adherence to Next.js conventions and type safety. The independent variable is the presence of SmartKit's \filename{AGENTS.md}, \filename{.cursor/rules/}, and \filename{src/features/} convention documentation. The dependent variables are the three rubric scores (Structural Integrity, Type \& Contract Safety, Coverage \& Completeness) on a 0--5 scale.

The pilot feature (\code{isEnabled(flagKey, userId?)}) was selected because it uses no service that SmartKit integrates (no Resend, Better~Auth, SePay, or Drizzle dependency beyond the schema). This choice keeps the comparison clean: by using a feature that touches none of SmartKit's integrated services, the comparison isolates convention-encoding effects rather than conflating them with service-specific patterns. The evaluation scenario measures AI-generated boilerplate quality directly: AI systems receive task descriptions, and the generated code is measured against the framework dimensions. The current pilot focuses on Cursor as the primary case study, consistent with the scope defined in Section~\ref{sec:introduction}. All evaluations use multiple runs to address non-determinism concerns raised by Ouyang et al. \parencite{ouyang2025nondeterminism}; the Cursor tool does not allow user-settable temperature in Auto mode (the tool snapshot used in the pilot), so multi-run evaluation substitutes for temperature variation as the determinism-handling mechanism. Results report per-condition medians and ranges, plus Wilson 95\% confidence intervals on the binary pass rate ($\geq 3/5$).

  - Use TypeScript strict mode.

\end{lstlisting}

The prompt intentionally avoids referencing SmartKit-specific conventions (\emph{do not} say ``for SmartKit'', ``follow the feature-based layout'', ``use \filename{.server} naming'', or ``refer to AGENTS.md''). The same prompt applies to both SmartKit and the convention-naive scaffold, so any difference in output quality is attributable to the convention encoding rather than the prompt content. The full pre-registration record, including the frozen prompt hash, is reproduced in \S\ref{sec:pilot-protocol}.

The same per-run pipeline was applied to all ten runs, with per-condition aggregates reported in Table~\ref{tbl:pilot-actual}:
\begin{enumerate}
    \item Initialize a fresh copy of the codebase with the pre-registered tooling verified against a run-day checklist.
    \item Invoke Cursor with the standardized prompt; start the time-to-correct clock.
    \item Collect generated files, Biome violations, \code{tsc --noEmit} output, and artifact enumeration; snapshot the run in \filename{runs/cond-<a,b>/run-<NN>/}.
    \item Score each run on the three-dimension rubric; record per-run JSON plus manual cells; commit before the next run.
\end{enumerate}

\subsection{Run Schedule and Verdict Rule}
\label{sec:pilot-schedule}

The pilot used an adaptive 10-run schedule: three Cond~B runs first, then Cond~A, with the binary verdict rule governing whether Cond~A extended to $N=5$; a second amendment (2026-09-14) extended Cond~B from $n=3$ to $n=5$ so that both arms are now at adaptive-$N=5$ and the comparative Bonferroni 99\% CI on the $A-B$ difference can be reported. The full schedule with tool snapshots and verdict counts is in Table~\ref{tbl:pilot-actual}; the per-minute timestamps live in the pilot audit trail released in the thesis GitHub repository. The verdict rule in force applies to the post-extension data: 5/5 confirmed; 0/5 refuted; 1--4/5 inconclusive. The original adaptive $N=3$ rule was superseded by amendment 2026-09-01 (§\ref{sec:pilot-record}).

The pilot followed a pre-registered adaptive schedule, detailed in \S\ref{sec:pilot-protocol}: the first three runs were executed in Condition~B, and the inter-run range on Type~\&~Contract Safety ($0$--$3$) exceeded the pre-registered continuation threshold, triggering Runs~6--7 in Condition~A. Condition~A was then extended from $n=2$ to $n=5$ (Runs~8--10) so the pre-registered binary verdict rule ($N=5$ per condition) could issue a determinate outcome; the extension and its justification are logged in the amendment history (\S\ref{sec:pilot-protocol}; full chronology in the pilot audit trail released in the thesis GitHub repository). Subsequently, Condition~B was extended from $n=3$ to $n=5$ (Runs~4--5, 2026-09-14) so that both arms are at adaptive-$N=5$ and the comparative-CI gate opens (defined in \S\ref{sec:pilot-schedule}). The final tally is ten runs: $n=5$ per condition.

For each run treated as a binary outcome (pass = score $\geq 3/5$; fail = score $< 3/5$), the Wilson 95\% confidence interval on the proportion of passing runs is computed by:
\begin{equation}
\frac{k + \frac{z^2}{2}}{n + z^2} \pm \frac{z}{n + z^2} \sqrt{\frac{k(n-k)}{n} + \frac{z^2}{4}}
\label{eq:wilson}
\end{equation}
where $k$ is the number of passing runs, $n=5$, and $z = 1.96$ for 95\% confidence. The Wilson interval is preferred over the normal approximation (Wald interval) for small $n$ because it never produces bounds outside $[0, 1]$ and has better coverage properties when the true proportion is near 0 or 1. Results are reported as median [min, max] with Wilson 95\% CI for the pass rate.

A second rater was scheduled to independently score 2 runs (1 per condition) using the same rubric, with Cohen's $\kappa \geq 0.7$ as the threshold for rubric revision. The IRR pass was deferred for lack of a second rater; see \S6.5.2 (Measurement Validity) for the canonical limitation disclosure.
\label{sec:pilot-irr}

\section{Results and Discussion}
\label{sec:pilot-results}

This section reports the pilot evaluation of the \code{isEnabled(flagKey, userId?)} utility under the pre-registered adaptive protocol, comparing Condition~A (SmartKit with full convention encoding) against Condition~B (convention-naive scaffold). The final tally is $10$ runs: $n=5$ per condition after the Cond~B extension amendment 2026-09-14 (Section~\ref{sec:pilot-conditions}). The pilot is reported as a worked example, not a hypothesis test: two of the three directional predictions are confirmed outright under the binary verdict rule (\S\ref{sec:pilot-schedule}) (DP1, DP2); DP3 is confirmed on its Condition~A clause (5/5 colocated tests) and refuted on its Condition~B clause (5/5 Cond~B runs produce a root-level test file, opposite to the original ``no test'' prediction), and is reported as an asymmetric two-clause verdict rather than collapsed into a single label. The per-arm sample remains far below the $n \approx 30$ needed for inferential validation, so cross-tool replication, larger-$N$ validation, and developer-participant studies remain future work; with both conditions now at adaptive-$N=5$, the comparative Bonferroni 99\% CI on the $A-B$ difference is now populated (it was omitted before the extension).

The Results and Discussion are interleaved: \S\ref{sec:pilot-results-perrun} through \S\ref{sec:pilot-results-cross-check} present the raw data and the cross-check methodology; \S\ref{sec:dp1-results} through \S\ref{sec:dp3-results} read each directional prediction against the rubric mechanics in one pass; \S\ref{sec:discussion-statistics} anchors the verdicts in the executed numbers, not in summary prose. Threats-to-validity items (IRR deferral, unblinded scoring, tool substitution, post-hoc $N$-extension disclosure, rubric-design contradiction) are catalogued in \S6.5 and not re-litigated here.

\subsection{DP1 -- Structural Placement}
\label{sec:dp1-results}
\label{sec:pilot-results-dp}

\textbf{Verdict.} Condition~A: $5/5$ runs placed the utility at the predicted path \filename{features/flags/lib/is-enabled.ts}; Condition~B: $5/5$ runs placed it at root \filename{lib/} ($0/5$ in Condition~A's predicted location). Wilson 95\% CI: Condition~A $[0.57, 1.00]$; Condition~B $[0.57, 1.00]$ for absence at the predicted path. Comparative Bonferroni 99\% CI on the $A-B$ difference (now populated with both conditions at adaptive-$N=5$): the comparison is one-sided — every Cond~A run hits the FSD path and every Cond~B run misses it — so the difference is identically $1$ at the empirical level, and the comparative CI collapses to the single point $1.0$ (the dispersion is in the Wilson half-widths on each arm, not in the difference). \textbf{Confirmed} ($5/5$) under the binary rule, but not a precise inferential estimate.

\textbf{What the rubric captures.} DP1 is a measurement success of the framework, not a causal claim about the convention itself. The mechanism the rubric captures is the discovery path: when an assistant is given a Next.js codebase with a `features/flags/lib/` convention already established by sibling features (e.g.\ the existing `is-enabled.ts` placement documented in \S\ref{sec:integrations-and-pilot}), it reads those siblings, recognises the convention, and replicates it at the predicted location. Condition~B's $3/3$ placement at root `lib/` is the mirror image: in the absence of a sibling convention to discover, the assistant defaults to a generic location. The gap between the two arms is consistent with the rubric's design intent --- Structural Integrity rewards convention-conformity, and the two conditions differ by design in the density of discoverable conventions.

\textbf{What the rubric does not capture.} The mechanism is observational at this point: the framework records that the convention was followed, not why the assistant chose to follow it. A future controlled design (dropping all explicit prompts that hint at `features/flags/`, comparing assistant behaviour against a sibling-less SmartKit branch) would be required to attribute the conformity to convention-reading rather than to instruction-following. Such a design is sketched in \S7.4 as a follow-up variation; the pilot as executed does not support that attribution.

\subsection{DP2 -- Zod-derived FlagKey}
\label{sec:dp2-results}

\textbf{Verdict.} Condition~A: $5/5$ runs used a Zod-derived \code{FlagKey} enum; Condition~B: $5/5$ runs used a raw \code{string} type alias (no Zod-derived enum). Wilson 95\% CI: Condition~A $[0.57, 1.00]$; Condition~B $[0.57, 1.00]$ for absence of a Zod-derived enum. Comparative Bonferroni 99\% CI on the $A-B$ difference (now populated with both conditions at adaptive-$N=5$): as with DP1, the difference is identically $1$ at the empirical level (every Cond~A run uses Zod, every Cond~B run uses raw \code{string}), so the comparative CI collapses to the single point $1.0$. \textbf{Confirmed as instruction-following asymmetry} ($5/5$ Cond~A complied with the directive, $5/5$ Cond~B did not) under the binary rule, but \textbf{not a precise inferential estimate} and \textbf{not a confirmation of convention-encoding benefit} on this dimension.

\textbf{What the rubric does not capture.} The standardized prompt (Listing~\ref{lst:control-prompt}) instructs both conditions to ``use a Zod schema to derive'' the \code{FlagKey} type, so the observed difference measures Condition~B's instruction-following failure (ignoring an explicit directive) rather than Condition~A's convention-encoding benefit. The rubric scores this dimension identically in both conditions (a Zod-derived type scores 5, a raw alias scores 0--1), so the dimensional verdict (Condition~A wins) is correct. What the verdict does not separate is the structural contribution from the prompting contribution: both the codebase convention (Zod is the existing type-source pattern in SmartKit) and the shared prompt directive (``use a Zod schema'') point in the same direction, so a compliant Condition~A run cannot be attributed to either factor in isolation. The Cond~B non-compliance is informative because it shows the directive was available and Condition~B did not follow it, but that observation alone does not tell a reader whether Condition~A's compliance was caused by the convention, the directive, or both. The bundled-effect limitation is acknowledged in \S7.2 and the design variation that would isolate the structural contribution (drop the shared Zod directive from the Cond~B prompt) is recorded in \S7.4.

\subsection{DP3 -- Centralized Test Path}
\label{sec:dp3-results}

\textbf{Verdict.} This prediction has two clauses: Condition~A places the test at \filename{src/tests/features/flags/} (predicted); Condition~B produces no test file (predicted). Condition~A: $5/5$ colocated as predicted --- \textbf{confirmed}. Wilson 95\% CI: $[0.57, 1.00]$. Condition~B: $5/5$ runs \emph{did} produce a test file (at the repository root), the opposite of the prediction --- \textbf{refuted}. Wilson 95\% CI: $[0.57, 1.00]$ for the absence of a test file (note that the script-level \texttt{cond\_b\_not\_colocated} count is $5/5$ because every Cond~B run has a root-level test, which the script records as ``Cond B follows its predicted (non-colocated) direction'' under the mechanical reading of the binary rule; this collapses to ``confirmed'' at the automated-aggregator level but does not change the substantive two-clause verdict reported here). Comparative Bonferroni 99\% CI on the $A-B$ difference (DP3-A clause): the two arms diverge maximally --- Cond~A hits the FSD path in $5/5$ runs, Cond~B never hits the FSD path --- so the difference is identically $1$ at the empirical level and the comparative CI collapses to the single point $1.0$. This asymmetric outcome is reported honestly rather than retrofitted to a single verdict: the pre-registration did not anticipate that Condition~B would consistently generate tests, and that is itself a finding worth noting.

\textbf{What the rubric does not capture.} The mechanism the rubric fails to capture here is general-purpose test-generation behaviour: an assistant given a TypeScript utility and an instruction to ``write tests if appropriate'' will, under most prompting configurations, generate some test file rather than none. The original DP3 design assumed Condition~B would treat the prompt as optional with respect to tests; that assumption was incorrect for the prompt phrasing used. Condition~A's $5/5$ prediction match on placement (centralized at `src/tests/features/flags/`) is unaffected, and that placement is what DP3 was designed to measure; the refuted clause is reported honestly rather than collapsed into a single ``confirmed'' verdict.

\textbf{Secondary DP3 finding: Coverage cap at 3 in Condition~A.} Rubric A.5.3 levels 4--5 require a non-stubbed per-user override path, which the pilot feature structurally cannot produce by design (no SmartKit integration means no database layer to derive an override value from). The executed pilot therefore reports Coverage scores capped at $3$ for all Cond~A runs (Table~\ref{tbl:pilot-actual}); these Cov $=$ 3 values reflect the design contradiction itself, not a finding about AI capability. The structural contradiction is analysed in \S6.5.3, which is the canonical location for the rubric-flaw discussion.

\subsection{Statistical Context: \texorpdfstring{$n=5$}{n=5} per Condition is not Inferential}
\label{sec:discussion-statistics}

The Wilson 95\% half-widths reported in \S\ref{sec:pilot-results-dp} anchor the DP verdicts in the executed numbers, not in summary prose: Condition~A half-width $\approx 0.21$ (CI $[0.57, 1.00]$ on $5/5$); Condition~B half-width $\approx 0.21$ (CI $[0.57, 1.00]$ on $5/5$ after the 2026-09-14 extension). At these widths, a single-condition Wilson interval cannot distinguish a true proportion of $0.50$ from one of $0.80$; the DP verdicts are therefore binary-rule outcomes (a $5/5$ count resolves ``confirmed'' under the rule's $N=5$ requirement) rather than parameter estimates with confidence. The DP verdicts should be read as feasibility-stage evidence that the framework can measure the predicted contrast under the executed conditions, not as estimates of that contrast in a population of AI assistants or codebases.

The conditional coverage of the comparative Bonferroni 99\% CI on the $A-B$ difference is now active (both arms at adaptive-$N=5$). Because every Cond~A run lands in the predicted location and every Cond~B run lands outside it on DP1, DP2, and the DP3-A clause, the empirical difference is identically $1$ on each prediction and the comparative CI collapses to the single point $1.0$. The dispersion is concentrated in the per-arm Wilson half-widths ($\approx 0.21$), not in the difference; the comparative CI does not add inferential content at this sample size but does report a numerical quantity consistent with the per-arm verdicts. A future symmetric-$N \approx 30$ replication is required before the comparative CI provides inferential leverage; see \S7.4 for the sample-size discussion.

A reader asking ``how big is the Condition~A effect?'' is asking a question the executed pilot does not answer. The conditions under which the effect size would become estimable (per-arm $N \approx 30$, symmetric $N$ across both arms, two or more tool families) are recorded as future work in \S7.4 and as a Known Limitation in \S7.2. The Discussion above reads the DP verdicts against the rubric mechanics for what they show at the executed sample size; it does not extrapolate.

\section{Threats to Validity}
\label{sec:threats}

The threats-to-validity taxonomy below organizes the limitations of the pilot under four categories. External and Temporal Validity (§\ref{sec:external-temporal}) covers transfer across frameworks, tool versions, and the lab-to-production gap; Measurement Validity (§\ref{sec:measurement-validity}) covers rubric cutoffs and inter-rater reliability; Internal Validity (§\ref{sec:internal-validity}) covers the rubric-design contradiction and protocol deviations; Conclusion Validity (§\ref{sec:conclusion-validity}) covers alternative explanations. The result-bound summary of known limitations and protocol deviations is in \S7.2; this section is the analytical taxonomy, with each category discussed against the executed pilot rather than the pre-registered design.

\subsection{External and Temporal Validity (Generalizability)}
\label{sec:external-temporal}

\textbf{Cross-framework transfer.} The SmartKit implementation focuses exclusively on Next.js App Router. Architectural patterns specific to Next.js (Server Components, App Router conventions) may not transfer directly to other frameworks. The cross-framework transfer analysis (\S\ref{sec:future-work}) provides a conceptual roadmap for Nuxt and Remix instantiation. Future work should evaluate generalizability across Nuxt and Remix by applying the same three-dimension framework with framework-specific checklists; the cross-section is at present unverified.

\textbf{Temporal stability.} The pilot was executed within a fixed Bachelor's thesis timeline (2026-09-01 to 2026-09-08; the full chronology is in the pilot audit trail released in the thesis GitHub repository); whether the framework's directional predictions remain stable as AI coding assistants evolve (Cursor auto-mode / agent-mode, underlying model versions, Next.js minor releases) is unquantified. The amendment log already records a tool-snapshot boundary between Runs~5 and Runs~6 within the same condition; this single pilot therefore delimits the precision of DP verdicts to the tool snapshot in force at execution time, and warrants future replication under current tool snapshots before the framework's verdicts are treated as time-invariant.

\textbf{Lab-to-Production Gap.} The pilot was executed in a single-author, single-tool, single-feature setting; whether the framework's directional predictions transfer to multi-developer production codebases with team-level code review and longer feedback loops remains unquantified. The deployed artefact, however, is publicly released, which permits replication by independent groups; this scope limitation thus delimits the precision of the present claims rather than blocking external replication.

\textbf{Scope limitations.} Coverage of the framework's three dimensions was demonstrated on one representative feature (\code{isEnabled(flagKey, userId?)}); no claim is made about how the rubric discriminates across heterogeneous feature surfaces (e.g.\ authentication flows, billing integrations, real-time collaboration). The post-hoc $N$-extension disclosure in \S6.5.3 further bounds how the cross-condition comparison should be read; with both arms now at symmetric adaptive-$N=5$ (2026-09-14 amendment), the bound is the post-hoc nature of both extensions rather than the asymmetric-count design itself. The boundary is the pilot feature, not Next.js boilerplate in general.

\subsection{Measurement Validity}
\label{sec:measurement-validity}

\textbf{Rubric cutoffs and IRR calibration.} The three evaluation dimensions are derived from design principles that address the gap between output-oriented benchmarks and framework-specific quality dimensions (foundation in \S\ref{sec:relatedwork}), but the specific dimension selection and rubric cutoffs are design choices rather than empirically validated constructs. The cutoffs (0--1: serious violations, 1--2: minor, 2--3: acceptable, 3--4: good, 4--5: excellent) are asserted mappings to developer outcomes; the claim that rubric level 5 means ``excellent boilerplate'' and level 0 means ``missing artifact'' in any developer-relevant sense is asserted rather than calibrated. Multi-run evaluation, IRR with Cohen's $\kappa \geq 0.7$, and criterion-referenced validation remain follow-up steps; until validation-stage replication is executed, the rubric scores should be read as ordinal, reproducible measurements of the framework's three dimensions, not as developer-relevant quality grades.

\textbf{Known Limitations (Measurement Subset).} Three identified limitations bound every quantitative claim in this thesis and are referenced from \S7.2 rather than restated at each location. (a)~\emph{Small per-arm sample size}: $n=5$ per condition ($n=5$ Cond~A, $n=5$ Cond~B after the 2026-09-14 amendment); no frequentist inferential claim supported at these sample sizes (see \S\ref{sec:future-work} for the sample-size calculation that places validation-stage replication at $n \approx 30$ per condition). (b)~\emph{Deferred inter-rater reliability}: the pre-registered IRR pass with Cohen's $\kappa \geq 0.7$ was deferred for lack of a second rater within the Bachelor's thesis timeline; all manual scores in Table~\ref{tbl:pilot-actual} are single-rater, and the deferral is recorded in the pilot audit trail released in the thesis GitHub repository (\S\ref{sec:pilot-protocol}). (c)~\emph{Unblinded primary-rater scoring}: the same author designed the rubric, built the \texttt{score-flag.ts} script, and produced SmartKit, creating a confirmation-bias risk that blinding would have prevented. The Coverage rubric's post-hoc re-evaluation (Cov 4--5 $\to$ 3, see \S6.3 ``Per-condition aggregate'') is the most visible instance of a judgment-call that blinding would have governed. Mitigation for future work: each run's files should be stripped of condition-identifying paths (e.g.\ \filename{features/flags/} vs.\ root \filename{lib/}) and re-labelled before scoring, with condition membership recovered only after the scores are committed to \filename{score.json}; the current pilot's per-run JSON artefacts are preserved so the re-scoring can be done ex post if a second rater becomes available.

\subsection{Internal Validity}
\label{sec:internal-validity}

\textbf{Rubric design flaw: Coverage levels 4--5 are unreachable for the pilot feature by construction.} The Coverage \& Completeness rubric (\S\ref{sec:pilot-rubric}, Table~\ref{tab:rubric-cov}) defines level~4 as requiring the per-user override path to be ``implemented (not stubbed --- i.e. returns a value derived from the database)'' and level~5 as additionally requiring the centralized test path. The pilot feature (\code{isEnabled(flagKey, userId?)}) was chosen specifically to avoid any SmartKit integration including the database layer (\S6.1, \S\ref{sec:integrations-and-pilot}), so the per-user DB override path is structurally out of scope for any feature meeting the no-integration selection criterion. The result is a \emph{structural contradiction} between the rubric and the confound-control design: rubric levels 4--5 are unreachable for the very feature the pilot chose to evaluate \emph{by construction}, not as a contingent scoring error. The executed pilot therefore reports Coverage scores capped at 3 for all Cond~A runs (Table~\ref{tbl:pilot-actual}); these Cov $=$ 3 values reflect the design contradiction itself, not a finding about AI capability. Fixing this confound requires either (a) revising the rubric to remove the DB-implementation requirement from levels 4--5, or (b) selecting a pilot feature that integrates at least one SmartKit service and re-running the analysis with both arms at symmetric adaptive-$N=5$; both are documented as future work (\S\ref{sec:future-work}).

\textbf{Protocol Deviations (Internal-Validity Subset).} Five protocol-affecting decisions bound how the within-condition results should be read; the full audit log with dates and justifications is in the pilot audit trail released in the thesis GitHub repository, and the result-bound summary is in \S7.2. (i)~\emph{IRR deferral}: no second rater was available within the Bachelor's thesis timeline, so all manual scores are single-rater. (ii)~\emph{Tool substitution}: Runs~6--10 used \code{cursor/agent-mode} rather than \code{cursor/auto-mode} (forced by tool availability, not experimental design). (iii)~\emph{N-extension asymmetry (resolved)}: originally the Cond~A arm was extended from $n=2$ to $n=5$ post-data-collection so the binary verdict rule could issue a determinate outcome, leaving Cond~B at $n=3$; the 2026-09-14 amendment extended Cond~B from $n=3$ to $n=5$ via Runs 4--5 so that the comparative Bonferroni 99\% CI gate on the $A-B$ difference could open. Both extensions remain post-hoc and the post-hoc nature of each is the load-bearing concern; with both arms now at adaptive-$N=5$, the original ``asymmetric N-extension produces one-sided confirmation'' bias risk is downgraded (both arms are now symmetric in count and rule-applicability) but the \emph{post-hoc} nature of both extensions is not removed. (iv)~\emph{Verdict-rule shift}: the adaptive $N=3$ rule was replaced mid-pilot by the binary $N=5$ rule (\S\ref{sec:pilot-schedule}); the lock permitted rubric and schedule amendments but not protocol-rule amendments, so this falls outside the categories enumerated in \S\ref{sec:pilot-lock}. (v)~\emph{DP3-B refuted outright}: the Cond~B clause of DP3 was falsified when all five Cond~B runs produced root-level test files, opposite to the prediction.

\textbf{Protocol-rule violation: N-extension and verdict-rule shift exceeded permitted amendments.} The N-extension to Condition~A ($n=2\!\to\!5$) and the shift from the adaptive $N=3$ verdict rule to the binary rule (\S\ref{sec:pilot-schedule}) fall outside the amendments the pre-registration lock explicitly permits: the lock (\S\ref{sec:pilot-lock}) allows only IRR-triggered rubric revision and exclusion-triggered schedule replacement, not protocol-rule changes motivated by indeterminate verdicts. This is a protocol-rule violation of the same commitment device that otherwise constrains the pilot; the substantive effect is captured by the bias-risk disclosure above, and the formal effect is that the pre-registration's amendment procedure (see pilot audit trail released in the thesis GitHub repository, amendment log) records these changes under the ``permitted amendments'' clause in form, while in substance they constitute a fourth category --- protocol-rule amendment --- that the lock did not enumerate. Future replication should add ``protocol-rule amendment'' as a fourth permitted-amendment category or, preferably, redesign the verdict rule so that an indeterminate result can be reported as inconclusive without requiring asymmetric N-extension.

\textbf{Tool-dependent, one-sided confirmation.} Three post-hoc decisions bound the DP verdicts. First, the adaptive extension to $N=5$ was applied to Condition~A only at first (2026-09-06); the 2026-09-14 amendment extended Condition~B from $n=3$ to $n=5$ so that both arms are now at adaptive-$N=5$ and the comparative Bonferroni 99\% CI on the $A-B$ difference can be reported. With the symmetric-$N$ extension in place, the original ``asymmetric N-extension produces one-sided confirmation'' bias risk \parencite{simmons2011falsepositive} on researcher degrees of freedom is downgraded: the symmetric-count design now satisfies the comparative-CI gate, and the per-arm Wilson half-widths are now equal ($0.21$) on both arms. The post-hoc nature of both extensions is not removed by the second extension and remains a disclosed limitation. Second, three of the five Condition~A runs (Runs~8--10) were generated under a different AI-tool snapshot than Runs~6--7 (Table~\ref{tbl:pilot-actual}); excluding them would leave Condition~A at $N=2$, below the verdict rule's threshold, so the \emph{confirmed} status of DP1 and DP2 depends on treating Runs~6--8 as comparable to Runs~4--5. The scores from Runs~6--8 reproduce the Runs~4--5 pattern under an unchanged rubric and prompt, which is the basis for retaining them; this is a single worked pilot on one feature and one tool family, not a controlled cross-tool replication. Third, DP3's Condition~B clause (predicting no test file) was falsified: all five Condition~B runs produced a test file, which the pre-registration did not anticipate. The full chronology, with dates and reasoning for each decision, is recorded in the pilot audit trail released in the thesis GitHub repository (amendment log).

\textbf{Design confounds and deferred validation.} Two further limitations bound how the pilot's numbers should be read. The locked run schedule executed all three Condition~B sessions before any Condition~A session, so time-of-day, session-memory, and experimenter-familiarity confounds cannot be ruled out; because the Condition~A block itself spans two tool snapshots, the run-order confound and the tool-snapshot difference are partially entangled for that condition, and a fully randomized run order is left as future work. Separately, every score in Table~\ref{tbl:pilot-actual} reflects a single primary rater (see Known Limitations in \S\ref{sec:limitations}); the scores remain reproducible from the underlying run artefacts, but have not been cross-checked against independent judgement.

\subsection{Conclusion Validity}
\label{sec:conclusion-validity}

\textbf{Alternative Solutions / Alternative Explanations.} The pilot's directional predictions are explained in terms of the three-dimension framework's structural conventions; whether the same directional verdicts would emerge under alternative solution strategies (prompting-only, linter-based enforcement, enhanced documentation) is left as future work (\S\ref{sec:future-work}). The confirmed DP1 and DP2 verdicts cannot, by themselves, distinguish ``structural convention-encoding benefit'' from ``instruction-following asymmetry that the structural convention incidentally enables'', because Cond~A's prompt bundles both the AGENTS.md structural directives and the explicit instruction-following cues that Cond~B's prompt also contains. The bundled-effect limitation is disclosed here rather than retrofitted into a clean causal story; future work should re-run DP2 with the Cond~B prompt removing the shared Zod directive to isolate the structural convention-encoding contribution from the prompting contribution.

\label{sec:conclusion}

\section{Summary}

This thesis proposes a three-dimensional evaluation framework (Structural Integrity, Type~\&~Contract Safety, Coverage~\&~Completeness) for assessing AI-generated Next.js boilerplate, and instantiates it in SmartKit, an open-source Next.js App Router boilerplate with feature-based modularity, explicit Server/Client boundaries, and type-safe contracts. An adaptive pilot ($n=5$ Cond~A, $n=5$ Cond~B after the Cond~B extension amendment 2026-09-14) on one representative feature produces feasibility-stage evidence that one of three directional predictions is confirmed outright (DP1, structural placement), one is confirmed as an instruction-following asymmetry rather than as a convention-encoding benefit (DP2), and one is asymmetric between its two clauses (DP3 confirmed Cond~A, refuted Cond~B); the full verdicts and disclosed protocol adaptations are in \S\ref{sec:pilot-results} and \S\ref{sec:limitations}. Quantitative claims are bounded by the Known Limitations consolidated in \S7.2 --- small per-arm samples, deferred IRR, and unblinded scoring --- which the thesis treats as the canonical reference rather than restating them at each reporting point. The framework, artefact, and executed pilot are intended as a foundation for larger-$N$ replication, cross-tool validation, and developer-participant studies, all documented in \S\ref{sec:future-work}.

\medskip\noindent\textbf{Ceiling--floor pattern in the executed scores.} The per-run scores cluster in a way that should be acknowledged explicitly: Condition~A medians (Structural $5$, T\&C $4$, Coverage $3$) sit at or near the rubric ceiling, while Condition~B medians (Structural $2$, T\&C $1$, Coverage $1$) sit at or near the rubric floor, with the single exception of Condition~B's T\&C range ($0$--$3$). Three structural causes produce this pattern, none of which retracts the confirmed verdicts. First, the Condition~A Coverage score is capped at $3$ by rubric-design contradiction rather than by ceiling saturation (\S6.5.3): rubric levels $4$--$5$ require a non-stubbed per-user override path, and the no-integration selection criterion rules out that artifact by construction. Second, the Cond~A score direction is reinforced by multiple bundled signals --- \filename{AGENTS.md}, the sibling-feature layout under \filename{features/billing/} and \filename{features/auth/}, the colocated Zod configuration, and the Zod directive in the standardized prompt --- all of which push toward the same FSD path, so the directional predictions cannot separate convention-reading from instruction-following (\S6.5.4). Condition~B was bootstrapped specifically to remove SmartKit's convention envelope, so its scores aggregate near the floor of a rubric calibrated to that envelope. Third, the comparative Bonferroni 99\% CI collapses to the single point $\{1.0\}$ because every Cond~A run is in the predicted location and every Cond~B run is outside it on DP1, DP2, and the DP3-A clause; this saturation is the expected behaviour of a $k/n = 5/5$ vs.\ $5/5$ comparison at the binary-rule stage and is not an inferential estimate. The confirmed verdicts are therefore feasibility-stage binary outcomes, not parameter estimates; the bounded scope and protocol deviations are catalogued in \S\ref{sec:limitations} below.

\section{Summary of Limitations}
\label{sec:limitations}

This section is the executive summary of the pilot's known limitations and protocol deviations. The analytical taxonomy with the full discussion of each limitation is in \S6.5 (Threats to Validity); readers should consult \S6.5 for the substantive analysis and consult this section only for a quick orientation during defence and replication. Each bullet below points to the canonical location.

\begin{itemize}
    \item \textbf{Rubric design flaw (Coverage levels 4--5 unreachable).} The structural contradiction between rubric A.5.3 levels 4--5 (require non-stubbed per-user override) and the no-integration selection criterion is analysed in \S6.5.3 (Internal Validity). The executed pilot reports Cov $=$ 3 for all Cond~A runs, reflecting the design contradiction rather than a finding about AI capability.
    \item \textbf{Known Limitations.} Three limitations bind every quantitative claim in this thesis: (a)~\emph{small per-arm samples} ($n=5$ Cond~A, $n=5$ Cond~B after the 2026-09-14 amendment; no frequentist inferential claim supported; validation-stage replication at $n \approx 30$ per condition; details in \S6.5.2), (b)~\emph{deferred IRR} (single-rater manual scores, Cohen's $\kappa \geq 0.7$ target not exercised; details in \S6.5.2), (c)~\emph{unblinded primary-rater scoring} (rubric, \texttt{score-flag.ts}, and SmartKit all produced by the same author; details in \S6.5.2 and \S7.4).
    \item \textbf{Protocol Deviations.} Five protocol-affecting decisions bound how the within-condition results should be read: (i)~IRR deferral, (ii)~tool substitution (Runs 4--5 and Runs 8--10 used \code{cursor/agent-mode} rather than the originally intended \code{cursor/auto-mode}), (iii)~N-extension (Cond~A extended $n=2\!\to\!5$ post-data-collection in the 2026-09-06 amendment, and Cond~B extended $n=3\!\to\!5$ post-data-collection in the 2026-09-14 amendment; both extensions remain post-hoc, but the second extension brings both arms to symmetric adaptive-$N=5$ and unblocks the comparative CI gate), (iv)~verdict-rule shift (adaptive $N=3$ rule replaced by binary $N=5$ rule mid-pilot), (v)~DP3-B refuted outright (all five Cond~B runs produced root-level test files, opposite to the prediction). All five are discussed in \S6.5.3 (Internal Validity, Protocol Deviations).
    \item \textbf{Tool-dependent, one-sided confirmation (downgraded).} With both arms now at adaptive-$N=5$ (Cond~B extended 2026-09-14), the original ``asymmetric N-extension produces one-sided confirmation'' bias risk \parencite{simmons2011falsepositive} is downgraded: symmetric-count design satisfies the comparative CI gate, and the per-arm Wilson half-widths are now equal ($0.21$). The post-hoc nature of both extensions remains a disclosed limitation (researcher degrees of freedom). Analysis: \S6.5.3.
    \item \textbf{Bundled-effect limitation (DP2).} The confirmed DP2 verdict cannot distinguish ``structural convention-encoding benefit'' from ``instruction-following asymmetry'' because the standardized prompt and the codebase convention both push toward Zod. The design variation that would isolate the structural contribution (drop the shared Zod directive from the Cond~B prompt) is recorded in \S7.4. Analysis: \S6.5.4 (Conclusion Validity).
    \item \textbf{Construct and Measurement validity.} The three dimensions and their 0--5 cutoffs are design choices, not empirically validated constructs; multi-run evaluation, IRR with $\kappa \geq 0.7$, and criterion-referenced validation remain follow-up work. Analysis: \S6.5.2 (Measurement Validity).
    \item \textbf{External Validity / Generalizability.} Findings are bounded to Next.js App Router; cross-framework transfer (Nuxt, Remix) is unverified; one-feature pilot scope (no heterogeneous feature surfaces). Analysis: \S6.5.1 (External and Temporal Validity).
    \item \textbf{Temporal Validity.} Findings are bounded to the tool snapshot in force 2026-09-01 to 2026-09-08 (Cursor auto-mode / agent-mode, underlying model versions, Next.js version); replication under current tool snapshots is required before the DP verdicts are treated as time-invariant. Analysis: \S6.5.1.
    \item \textbf{Alternative Solutions.} The thesis does not empirically compare the structural approach against prompting-only, enhanced documentation, or linter-based enforcement; the Cond~A advantage is the bundled effect of conventions + prompting + tooling. Analysis: \S6.5.4 (Conclusion Validity).
    \item \textbf{Lab-to-Production Gap.} The evaluation is scenario-based, not production-deployed; SmartKit's integrations are implemented but have not been audited for production deployment (no security review, load testing, or penetration testing). Analysis: \S6.5.1.
\end{itemize}

\section{Diffusion Pathway and Adoption Risks}
\label{sec:diffusion}

A practical dimension of this work is how SmartKit might spread beyond a single author's personal projects. Drawing on Rogers' diffusion of innovations framework \parencite{rogers2003diffusion} as applied to developer tooling \parencite{storey2016frameworkadoption}, the adoption profile of SmartKit depends on five attributes: relative advantage, compatibility, complexity, trialability, and observability.

\textbf{Relative advantage} for the early-majority segment is plausible but unquantified. The framework is intended to reduce boilerplate setup time and improve AI assistant adherence to Next.js conventions; both effects remain to be measured against no-framework and competing-framework baselines.

\textbf{Compatibility} with Next.js is high by construction (SmartKit is a Next.js boilerplate). \textbf{Complexity}, however, is substantial: developers adopting SmartKit must internalize feature-based folder conventions, Next.js Server/Client boundary directives (\usec and \code{server-only} imports, which are Next.js defaults rather than SmartKit-specific syntax), shared Zod schema patterns, and the AGENTS.md instruction format. This overhead targets the innovator and early-adopter segments of the developer community; whether the framework can spread to the early majority depends on whether the maintenance overhead is amortized across projects.

\textbf{Trialability} is well-addressed: the SmartKit codebase is publicly released, and incremental adoption (taking only the feature-based layout and Server/Client boundary conventions without committing to the full stack) is documented. \textbf{Observability} is partially addressed: the proposed three-dimension rubric provides numeric scores per dimension, which can serve as an observability signal in published comparisons.

\textbf{Adoption risks.} Prior work on framework adoption identifies framework lock-in as a major adoption risk \parencite{storey2016frameworkadoption}; SmartKit may intensify this risk by introducing a layer of project-specific conventions above plain Next.js. If a future Next.js major release changes its Server/Client boundary conventions (currently \usec directives and \code{server-only} imports)---or if the conventions are folded into mainstream documentation---the SmartKit conventions may need to be migrated or retired. Teams that adopt SmartKit incrementally incur a partial lock-in: they may find rewriting their \filename{features/} layout or unwiring shared Zod schemas across feature boundaries to be a non-trivial refactor. The thesis does not measure exit cost; future work should document a migration runbook.

\textbf{Developer deskilling.} A separate concern identified in adjacent work is whether structural boilerplate frameworks erode the developer expertise needed to debug, maintain, or evolve the generated code \parencite{dakhel2023github}. Dakhel et al. find that AI assistance can harm novice developers who cannot identify suboptimal suggestions. SmartKit's explicit, named conventions (``always put Zod schemas in \filename{schemas/}'') are arguably more legible than AI-generated invisible structure, which can partially mitigate this risk: a developer who reads the AGENTS.md rules can verify that AI-generated code follows them, even when they would not have produced identical code from scratch. Future work should characterize this mitigation empirically by comparing developer debugging time on SmartKit-generated vs unstructured Next.js codebases.

\section{Future Work}
\label{sec:future-work}

Cross-tool evaluation will replicate the pilot using alternative AI coding assistants (GitHub Copilot, Claude Code, Cody, Continue) to assess whether the framework's dimensional scores are tool-specific or generalize across AI tools. The directional predictions (DP1--DP3) can be tested on each tool, producing a per-tool verdict table. Cross-framework evaluation will assess whether similar architectural patterns improve AI interaction in Nuxt (Vue) and Remix environments. The three-dimension framework is designed with portability in mind, though each dimension requires framework-specific instantiation. \textbf{Structural Integrity} maps directly: in Nuxt, the conventions are file-based routing via \filename{/pages/}, \code{definePageMeta()} for metadata, \code{useAsyncData()} for server data boundaries, and \code{.client.vue} suffix for client-only components; in Remix, they are flat routes via \filename{/routes/}, \code{loader}/\code{action} functions as server-side entry points, and \code{ErrorBoundary} components for error handling. These conventions are structurally analogous to Next.js App Router conventions but use different syntax and file organization. \textbf{Type \& Contract Safety} transfers directly because it operates at the language level (TypeScript strict mode) and API level (Zod schemas), which are framework-agnostic. \textbf{Coverage \& Completeness} requires per-framework checklist instantiation: Nuxt checklists include \filename{middleware/} files and \filename{composables/} for shared logic, while Remix checklists include \filename{utils/} and \filename{styles/} conventions. Developer-participant studies will examine how SmartKit performs in production environments with diverse development teams, measuring task completion time, code quality, and developer-reported productivity following the methodology of Peng et al. \parencite{peng2023impact} and Tariq et al. \parencite{tariq2026enterprise}. Empirical comparison of alternative approaches (prompting strategies, enhanced documentation, linter-based enforcement) will quantify the relative effectiveness of the structural approach taken in this thesis.

Concrete next steps: (1)~run the cross-tool replication on at least two non-Cursor assistants, now that all three DPs have been issued a verdict on the current tool family; (2)~\emph{(completed 2026-09-14)} extend Cond~B from $n=3$ to $n=5$ so a symmetric two-condition comparison with a comparative confidence interval becomes possible --- this is now in place and the comparative Bonferroni 99\% CI on the $A-B$ difference is populated in \S6.3 / \S6.4, though the post-hoc nature of both extensions remains a disclosed limitation; (3)~instantiate the Nuxt and Remix checklists in draft form for review; (4)~pilot a developer-participant session with three developers on a single SmartKit codebase and report findings before scaling further; (5)~re-run DP2 with the Cond~B prompt removing the shared Zod directive (i.e.\ instruct Cond~B to use raw \code{string} only) to isolate the structural convention-encoding contribution from the prompting contribution, addressing the bundled-effect limitation disclosed in Section~\ref{sec:pilot}.

\textbf{Sample-size determination.} The executed pilot ($n=5$ per condition after the pre-registered Cond~A extension and the 2026-09-14 Cond~B extension) is feasibility-stage, not validation-stage. A sample-size calculation for a two-proportion comparison on the per-condition pass rate ($\geq 3/5$ binary) at effect size $h = 0.5$ (Cohen's medium effect), $\alpha = 0.05$, and power $0.8$ gives $n \approx 30$ per condition (chi-squared approximation). At a stricter effect size $h = 0.3$ (small), the requirement rises to $n \approx 90$ per condition. The binary verdict rule used in the pilot ($5/5$ confirmed, $0/5$ refuted, $1$--$4/5$ inconclusive) is appropriate for a feasibility-stage design at small $N$, but it is not a substitute for a frequentist sample-size calculation when moving to validation-stage replication: a confirmed verdict at $N=5$ should not be over-interpreted as a strong inferential claim.

\textbf{Empirical validation of the orthogonality claim.} The three evaluation dimensions (Structural Integrity, Type \& Contract Safety, Coverage \& Completeness) are claimed in \S1.3 to be \emph{designed to be} orthogonal in the sense that they measure distinct aspects of generated code. This orthogonality is a design-stage hypothesis---the three dimensions are intended to vary independently, but this intent has not been empirically tested. A Pearson correlation matrix across the three dimension scores, computed on $n \geq 30$ per condition, would distinguish genuine orthogonality (correlations $\approx 0$) from subtle coupling.

\textbf{Re-execution of the IRR pass.} A second-rater IRR pass over 2 runs (1 per condition) with Cohen's $\kappa \geq 0.7$ is the pre-registered validation step (§\ref{sec:pilot-irr}). The pass was deferred for lack of a second rater within the thesis timeline (Section~\ref{sec:limitations}). Future work should re-execute the IRR pass once a second rater is available; the rubric-revision clause remains in force but was not exercised.
