% --- Abstract ---
AI coding assistants can generate Next.js App Router code that violates framework conventions. A common example, observed during SmartKit's development: a Server Component imports a Client Component and passes an event handler as a prop. \code{tsc --noEmit} cannot catch this, since the type system has no representation for boundary violations. Existing benchmarks, HumanEval and SWE-bench, measure algorithmic capability. None of them measures framework-convention adherence.

I designed a three-dimensional evaluation framework for AI-generated Next.js boilerplate. The framework scores Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness on a 0--5 rubric. The pilot validates measurement on Structural Integrity and Type \& Contract Safety across the full range; Coverage \& Completeness is validated across the 0--3 range (pilot feature deliberately excludes integrations to isolate convention effect). SmartKit, an open-source Next.js boilerplate I released alongside the thesis, instantiates the framework's conventions. A bounded feasibility pilot with five runs per condition produced measurable scores on real AI-generated code.

Three directional predictions carried pre-registered verdicts. DP1, structural placement, confirmed at 5/5 in Condition~A and 0/5 in Condition~B. DP3-A, centralized test path, confirmed under the same rule. DP2, Type \& Contract Safety, confirmed the predicted ecosystem-level contrast (bundled conventions + directive reinforcement); component isolation remains future work. DP3-B refuted: Condition~B placed test files at the repository root in all five runs, the opposite of the prediction.

The pilot uses one tool, one feature, and five runs per condition; its scope and threats are set out in \autoref{sec:threats}.

\chapter{Introduction and Motivation}
\label{sec:introduction}

The chapter opens with the recent wave of AI coding assistants and the parallel shift in Next.js toward the App Router, identifies the absence of an evaluation framework for framework-specific convention adherence, and derives from that gap the research objectives, questions, and hypotheses that structure the rest of the thesis. The chapter closes with the scope within which SmartKit is designed and evaluated.

\section{Overview}

AI coding assistants now drive a substantial share of routine code production. Peng et al. showed that developers using GitHub Copilot completed tasks 55.8\% faster than control groups \parencite{peng2023impact}. Yetiştiren et al.\ separately reported that GitHub Copilot generated valid code for 91.5\% of HumanEval problems ($n=164$), with 28.7\% fully correct, 51.2\% partially correct, and 20.1\% incorrect \parencite{yetistiren2022assessing}. Next.js has emerged as the dominant React meta-framework for production web applications; its App Router architecture, introduced in version 13, fundamentally changed application structure through React Server Components and explicit Server/Client boundaries \parencite{nextjsdocs}.

A concrete failure mode motivates this thesis (\autoref{fig:motivated-example}). When an AI coding assistant generates a Server Component that imports a Client Component and passes an event handler as a prop, Next.js produces the runtime error ``Event handlers cannot be passed to Client Component props.'' \code{tsc --noEmit} cannot catch this, since the type system has no representation for boundary violations. During SmartKit's development I observed recurring AI generation errors in Next.js App Router code first-hand, including authentication security flaws, component boundary violations, and outdated API usage from older training data. These are development-time observations, not measured prevalence figures.

Existing benchmarks, HumanEval and SWE-bench, score algorithmic correctness and bug-fixing capability, but none of them measures framework convention adherence \parencite{chen2021evaluating,jimenez2024swebench}. A systematic literature review of 395 LLM-for-SE studies confirmed that framework-convention adherence is not separately tracked as an evaluation category: 338 of 395 studies (~86\%) rely on generation-task metrics such as BLEU-4, Pass@k, and Accuracy@k \parencite{hou2024llmse}. None of these capture the specific architectural requirements of Next.js App Router: Server/Client component boundaries, type-safe contracts, or file-system routing conventions. Developers therefore have no quantitative basis for comparing AI tools on these architectural tasks. This thesis proposes a three-dimensional evaluation framework, structural integrity, type \& contract safety, and coverage \& completeness, to fill that gap.

This overview has sketched the problem from a practitioner angle. The next section formalises the technical challenges that make convention adherence hard to measure. The formal research objectives, contribution list, and framework definition follow in \autoref{sec:research-objectives}.

\section{The Problem: AI Convention Violations in Next.js}

This thesis addresses a concrete problem: AI coding assistants consistently generate Next.js App Router code that violates framework conventions. The violations produce runtime errors and technical debt, yet no evaluation framework exists to measure adherence. Three principal challenges shape the framework design.

Framework conventions are implicit and distributed across documentation, error messages, and community patterns. Enumerating them into testable metrics is itself an open problem. AI-generated code failures in Next.js manifest at runtime rather than compile time. The Server/Client boundary error ``Event handlers cannot be passed to Client Component props'' only fires when the component is executed, so the framework needs dynamic analysis rather than static linting alone. And the three evaluation dimensions are designed to be orthogonal: a structural-integrity violation does not imply a type error, and a coverage gap operates independently of both. Collapsing the three into a single composite score would hide which dimension is actually regressing. Their orthogonality is asserted at design stage and awaits empirical validation; the executed pilot's per-arm sample is far below the $n \approx 30$ required to confirm that the dimensions vary independently in practice. Pearson correlation analysis on $n \geq 30$ per condition would distinguish genuine orthogonality from subtle coupling, and that analysis is part of the validation-stage work described at the end of this thesis.

The focus on Next.js App Router is deliberate. Market dominance makes it the primary target: Next.js is reported at 20.8\% in the Stack Overflow 2025 Developer Survey's web-frameworks-and-technologies category, ahead of Express (19.9\%) and Angular (18.2\%) \parencite[1, Stack Overflow Developer Survey]{stackoverflow2025}. Training-data mismatch is a recognised failure mode of LLM-based code assistants; Wu et al.\ introduced VersiCode, a benchmark spanning 300 libraries and 2{,}000+ versions over 9 years, and showed that version-controllable code generation (version-specific completion and version-aware migration) remains a significant challenge even for frontier models \parencite{versicode2024}. Practical feasibility also applies: I have existing Next.js expertise, which enables direct testing of enforcement mechanisms. The pilot targets Cursor because its AGENTS.md feature implements documentation-based guidance, an approach consistent with prior research suggesting that explicit context and structured prompts improve AI coding-assistant output quality \parencite{barke2022grounded,zhang2023practices}.

\section{Research Objectives and Questions}
\label{sec:research-objectives}

Next.js dominates React meta-framework adoption, and AI coding assistants such as GitHub Copilot and Cursor have demonstrated substantial productivity gains, yet no systematic evaluation framework bridges the two areas: a framework that measures how closely AI-generated Next.js boilerplate code adheres to framework-specific conventions is missing. Existing benchmarks, HumanEval and SWE-bench, address algorithmic problem-solving and bug-fixing capability, but none captures the architectural requirements of Next.js App Router: Server/Client component boundaries, type-safe contracts, or file-system routing conventions \parencite{chen2021evaluating,jimenez2024swebench}. This thesis targets that gap.

The primary motivation is to bridge it by designing a three-dimensional evaluation framework that turns an implicit set of framework conventions into measurable, comparable scores, and by instantiating the framework in SmartKit, a structured Next.js boilerplate that provides the necessary enforcement mechanisms and the evaluation target codebase.

Three objectives structure the research:
{\sloppy
\begin{itemize}
    \item \textbf{Design a three-dimensional evaluation framework.}
    Construct a framework that scores AI-generated Next.js boilerplate
    code along three dimensions: Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness, so that convention adherence becomes a quantitative,
    comparable property of generated code.
    \item \textbf{Implement SmartKit as a structured architecture.}
    The thesis releases SmartKit, an open-source Next.js boilerplate
    that demonstrates feature-based modularity, explicit Server/Client
    boundaries, and type-safe contracts, providing both the enforcement
    mechanisms and the target codebase for the framework.
    \item \textbf{Demonstrate framework applicability through a bounded
    feasibility run.} The thesis applies the framework to a representative
    feature generated by Cursor under Condition~A to verify that
    the framework can produce scores on real AI-generated code.
\end{itemize}
}

Two research questions follow:
\begin{enumerate}
    \item How can an evaluation framework be consistently designed to
    measure AI coding assistant adherence to Next.js App Router boilerplate conventions along the Structural Integrity, Type \& Contract Safety, and
    Coverage \& Completeness dimensions?
    \item Can the resulting framework be operationalized into measurable
    metrics, and does it demonstrate applicability when applied to
    representative AI-generated Next.js features?
\end{enumerate}

These objectives and questions yield two classes of claims, both
documented as design-level pre-registrations to be exercised by the
pilot section.

\begin{description}
  \item[Framework properties (FP)] describe what the framework can
    measure. Each property claims that a dimension can be operationalised
    on a real artifact and produce a per-run score. The pilot can only
    support or fail to support these claims; it cannot refute them.
  \item[Directional predictions (DP)] are falsifiable hypotheses about
    Condition~A versus Condition~B. Each prediction states which
    condition is expected to score higher on a given dimension. The
    pilot assigns each prediction a binary verdict of
    \emph{confirmed}, \emph{refuted}, or \emph{inconclusive}.
\end{description}

\paragraph{Framework properties (descriptive).} The pilot demonstrates
that the framework operates on a real artifact:
\begin{itemize}
    \item \textbf{FP1 (Structural Integrity).} The framework can measure
    the dimension it targets---file placement, Server/Client boundary
    usage, and naming patterns---on AI-generated Next.js code, yielding
    a per-run score on a representative feature.
    \item \textbf{FP2 (Type \& Contract Safety).} The framework can measure
    the dimension it targets on AI-generated Next.js code, yielding a
    per-run score on a representative feature by combining Type-Safety
    and Contract-Safety sub-scores under the framework's weakest-link
    combination rule. The pilot validates measurement at ecosystem level
    (bundled conventions); component-level attribution requires follow-up
    decomposition studies (\autoref{sec:future-work}, item~4).
    \item \textbf{FP3 (Coverage \& Completeness).} The framework can
enumerate AI-generated files against a feature-specific checklist
and yield a per-run score reflecting required-artifact presence.
The pilot validates measurement across the 0--3 range (no-integration
feature by design); levels 4--5 require integration-dependent artifacts
that the pilot feature deliberately excludes to isolate convention
effect (see \autoref{sec:integrations-and-pilot}).
\end{itemize}

\paragraph{Directional predictions (falsifiable hypotheses).} Each
prediction asks whether Condition~A outperforms Condition~B on one
dimension. The pilot uses the \code{isEnabled(flagKey, userId?)}
utility as the representative feature and evaluates the prediction as
\emph{confirmed} (all runs agree with the predicted direction),
\emph{refuted} (no runs agree), or \emph{inconclusive} (mixed),
following the adaptive-$N$ pilot protocol.

\begin{itemize}
    \item \textbf{DP1 (Structural Integrity).} Condition~A is predicted to place the
    utility in the SmartKit feature-based layout in the majority of runs;
    Condition~B is predicted to use a root-level or flat structure.
    \item \textbf{DP2 (Type \& Contract, ecosystem-level test).} The SmartKit ecosystem (AGENTS.md directive + colocated Zod patterns + sibling schema examples) is predicted to drive Zod-typed schema definitions in Condition~A; Condition~B (directive alone, no structural reinforcement) is predicted to produce raw string types or inconsistent Zod adoption.
    \item \textbf{DP3 (Coverage).} Condition~A is predicted to include a
    centralized test file in the majority of runs;
    Condition~B is predicted to omit a test file in the majority of runs.
\end{itemize}

The pilot reports each framework property as \emph{supported} or
\emph{unsupported} and each directional prediction as one of the three
binary verdicts. Full statistical validation, including larger
per-arm samples, cross-tool replication, and developer-participant
studies, remains future empirical work (see \autoref{sec:threats}
for threats to validity).

Designing an evaluation framework for AI-generated Next.js boilerplate encounters three key challenges that distinguish it from existing code generation benchmarks. Framework conventions are implicit and distributed across documentation, error messages, and community patterns, requiring deliberate extraction into enumerable, testable rules rather than relying on predefined quality criteria. Convention violations in Next.js App Router manifest primarily at runtime: Server/Client boundary violations produce errors only when executed, so evaluation must go beyond static analysis to capture dynamic execution behaviour. A single composite score would also hide which quality dimension is actually regressing, so the framework reports its dimensions separately.

This thesis makes one primary contribution and two supporting contributions.

The primary contribution is the design of a three-dimensional evaluation framework, scored on Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness, for measuring how closely AI coding assistants adhere to Next.js App Router conventions. The framework addresses a gap left by existing benchmarks, which score algorithmic correctness rather than framework-specific quality. It is operationalised through an \emph{ecosystem comparison}: Condition~A with AGENTS.md, sibling features, Feature-Sliced Design (FSD) layout, and Zod patterns versus a convention-naive Condition~B scaffold with none of these.

The first supporting contribution is the SmartKit artifact, an open-source Next.js boilerplate demonstrating feature-based modularity, explicit Server/Client boundaries, and type-safe contracts. SmartKit supplies both the conventions the framework measures and the target codebase it measures them on. All four Better Auth tables (user, session, account, verification), the billing feature (SePay integration with HMAC signature verification and idempotent webhook handling), and the email integration (Resend and React Email) are implemented at the current snapshot.

The second supporting contribution is the bounded feasibility pilot protocol, comprising a pre-registration document, a Condition~A versus Condition~B comparison scaffold, a scoring rulebook, and a baseline-bootstrap script. These artifacts are concrete enough that another researcher can replicate the pilot without re-deriving the protocol from the thesis prose. The pilot demonstrates that the framework produces measurable contrast between conditions within the scope defined in \autoref{sec:research-objectives}.

Each of the three dimensions is paired with an automated measurement: Structural Integrity is measured through parsed-AST rule violations, Type \& Contract Safety through TypeScript compiler output, and Coverage through a rule-coverage matrix checked against the convention catalog. Because the dimensions are deliberately independent, no single composite score can substitute for examining all three independently.

\section{Scope and Limitations}

To keep the empirical rigor and feasibility of this research within the resource envelope of a single-author thesis, I bound the scope by the following parameters and limitations:

\begin{enumerate}
    \item \textbf{Framework scope:} Next.js App Router only. No comparison with Nuxt, Remix, or other meta-frameworks.
    \item \textbf{AI assistants:} Cursor used for the bounded feasibility demonstration. Broader AI assistant evaluation (GitHub Copilot, Claude Code) is future work.
    \item \textbf{Project type:} Single representative Next.js project demonstrating SaaS patterns.
    \item \textbf{Pilot study limitation:} The feasibility demonstration runs one representative task (\code{isEnabled(flagKey, userId?)}) with five independent runs per condition, yielding ten runs total. The demonstration uses a pre-registered rule: five passing runs confirms a prediction, zero passing runs refutes it, and one to four passing runs marks it inconclusive. Findings are bounded by the small per-arm sample; a population-level estimate would require approximately 30 runs per condition. Cross-tool replication and larger-$N$ studies remain future work.
\end{enumerate}

These four boundaries are deliberate. Fixing them isolates the SmartKit effect from confounding variance.


\chapter{Background}
\label{sec:background}

Understanding the intersection of AI coding assistants and Next.js development requires grounding in three domains: AI coding tool capabilities and limitations, Next.js architectural patterns, and SaaS boilerplate design principles.

\section{AI Coding Assistants}

GitHub Copilot, Anthropic's Claude, and Cursor all use transformer-based LLMs fine-tuned for code understanding and generation. GitHub Copilot provides inline code completions and entire function generation within supported editors, using OpenAI's GPT series and Anthropic's Claude series models (specific versions vary over time). Anthropic's Claude offers conversational code assistance through the Claude Code CLI and IDE integrations. Cursor combines Claude with a custom codebase indexing system that enables context-aware suggestions across entire projects.

These assistants are context-aware: completions draw on surrounding code, comments, and project-wide signals such as the codebase index used by Cursor \parencite[code quality evaluation study]{yetistiren2023evaluating}.

The research literature documents both strengths and limitations. Dakhel et al.\ found that AI assistance benefits expert developers who can filter suboptimal suggestions but may harm novice developers who lack the expertise to identify incorrect or inefficient code \parencite{dakhel2023github}. Liu et al.\ documented that ChatGPT performs better on older problems (pre-2021) than newer ones, with a 48.14\% advantage on the Accepted rate, yet it struggles with complex algorithms and domain-specific code, frequently generating solutions with security vulnerabilities and inefficient implementations \parencite{liu2024chatgpt}.

The task taxonomy for AI suitability places boilerplate generation as a strength area. Zhang et al. mined Stack Overflow and GitHub Discussions and found that developers primarily use Copilot for code generation in general-purpose languages (JavaScript, Python) on VS Code, with data processing as the most common function category and difficulty of integration as the dominant limitation \parencite{zhang2023practices}. Pandey et al. documented Copilot time savings of up to 50\% in code documentation and autocompletion, and 30--40\% in repetitive coding, unit-test generation, debugging, and pair programming. The tool struggled with complex tasks, large functions, multiple files, proprietary contexts, and C/C++ code \parencite{pandey2024transforming}. These findings focus the study on boilerplate interaction as an appropriate domain for AI enhancement.

\section{Next.js Framework Architecture}

Next.js is a React meta-framework that provides server-side rendering, static site generation, and API capabilities within a unified application model. Version 13 introduced the App Router paradigm, fundamentally changing how React applications structure pages, layouts, and data fetching. Developers who learned the Pages Router encounter several App Router concepts that the older model did not surface, including Server/Client boundaries and file-system conventions for special files.

React Server Components are a core innovation in Next.js App Router. They execute exclusively on the server, which lets them access databases and sensitive operations directly without exposing logic to the client. The distinction between Server and Client components requires explicit marking through the \usec{} directive, creating a boundary that developers must manage carefully. Incorrect placement across this boundary produces runtime errors and performance degradation.

The App Router organises applications through a file-system-based routing mechanism. Each folder within the \filename{app/} directory corresponds to a route segment, with \filename{page.tsx} files defining the content for each route. Special files such as \filename{layout.tsx}, \filename{loading.tsx}, and \filename{error.tsx} provide shared UI and error handling across route hierarchies. This convention-driven structure enables rapid scaffolding but requires adherence to specific naming and placement patterns.

TypeScript integration in Next.js emphasises type safety throughout the application. The framework provides typed interfaces for page properties, API request and response objects, and data-fetching results. Achieving full type coverage requires consistent use of TypeScript patterns including generics, utility types, and strict mode configuration. AI coding assistants may generate code that compiles but violates framework conventions, producing runtime errors or subtle bugs.

\section{SaaS Boilerplate Patterns}

SaaS applications share common requirements that boilerplate frameworks address: user authentication, database access patterns, multi-tenancy support, and deployment configurations. The economics of SaaS development favour approaches that reduce per-project initialisation effort while maintaining code quality and consistency.

Krüger et al.\ established that platform reuse reduces maintenance effort but involves upfront investment in framework adoption and learning curve \parencite{kruger2020empirical}. The trade-off explains the appeal of well-designed boilerplate templates that amortise initialisation cost across multiple projects. Aleem et al.\ identified customization, scalability, multi-tenancy, security, integration, and fault tolerance as key factors in SaaS architecture decisions \parencite{aleem2019maturity}.

Modern scaffolding approaches build on model-driven architecture principles. Inayatullah and Azam presented a UML-based DSML that automatically generates scaffolding CRUD code for cross-platform (web + mobile) applications from class diagrams, reducing repetitive implementation effort \parencite{inayatullah2019model}. Liu and Sra recently showed that LLMs have potential to automatically generate scaffolded user interfaces, reducing complexity for users in professional creative software \parencite{liu2025auggen}.

Meta-framework evaluation surfaces architectural trade-offs across options. The framework-adoption literature identifies learnability, extensibility, and ease of migration as primary drivers of adoption, while framework lock-in and high configurability are commonly cited as adoption risks \parencite{storey2016frameworkadoption}. Next.js App Router emphasises React Server Components as a first-class primitive while maintaining full compatibility with Client Components for interactive UI. This hybrid model creates specific conventions that boilerplate frameworks should encode.

\chapter{Related Work}
\label{sec:relatedwork}

This section surveys existing research on code generation benchmarks, empirical studies of AI-assisted development, and systematic literature reviews on AI for software engineering. The analysis identifies the specific gap this thesis addresses: the absence of framework-specific evaluation for AI coding assistants operating on Next.js boilerplate conventions.

\section{Code Generation Benchmarks}

The evaluation of AI coding assistants relies heavily on standardised benchmarks that measure code generation capability. Chen et al.\ introduced HumanEval as a foundational benchmark containing 164 hand-written programming problems with function signatures, docstrings, and unit tests \parencite{chen2021evaluating}. The benchmark evaluates models using Pass@1, Pass@10, and Pass@100 metrics. OpenAI's Codex achieved 28.8\% Pass@1 on this benchmark, establishing a baseline for subsequent model development.

HumanEval focuses exclusively on single-function Python code generation with algorithmic and reasoning requirements. The design prioritises general programming capability over domain-specific or framework-aware generation. Yu et al.\ extended the benchmark concept with HumanEval Pro, adding self-invoking code generation tasks that require models to generate functions calling previously defined functions \parencite{yu2025humanevalpro}. Their work found that most LLMs exhibit a 10--15 percentage-point absolute drop on self-invoking tasks compared to standalone tasks (o1-mini falling from 96.2\% to 76.2\% Pass@1 on HumanEval Pro). This drop indicates that current benchmarks underestimate real-world code generation complexity.

SWE-bench marks a substantial advance in benchmark realism by evaluating AI models on real GitHub issues from popular Python repositories \parencite{jimenez2024swebench}. Each task requires understanding the issue description, locating relevant code, implementing a fix, and passing unit tests. Jimenez et al.\ found that state-of-the-art models resolved only a small fraction of issues: Claude 2 solved approximately 1.96\% with BM25 retrieval and 4.8\% with oracle retrieval, while GPT-4 scored 1.74\% with oracle retrieval and 0\% with BM25. The gap between benchmark performance and practical software engineering capability is substantial.

Language-specific benchmarks surface further evaluation limitations. Petrukha et al.\ developed SwiftEval for Swift programming, finding that general-purpose benchmarks overestimated Swift code generation capability \parencite{petrukha2025swifteval}. Their language-specific benchmark documented substantial score drops (up to roughly 60 points for the smallest open-source models, with smaller drops for frontier models) when evaluating the same models on Swift versus HumanEval-style Python problems.

No existing benchmark evaluates framework convention adherence, boilerplate structure quality, TypeScript or Next.js-specific patterns, or multi-file scaffolding tasks. The benchmarks measure whether AI assistants can solve algorithmic problems or fix bugs in existing codebases, not whether they can generate framework-compliant boilerplate from scratch.

Several extensions and alternatives warrant mention. Liu et al.\ developed HumanEval+ and MBPP+ as rigorous extensions of the original benchmarks, finding that pass rates drop by 19.3--28.9\% on average across 26 evaluated LLMs when evaluated against additional auto-generated high-quality tests per problem \parencite{liu2024correct}. Zhuo et al.\ introduced BigCodeBench, which evaluates 1,140 fine-grained tasks combining diverse function calls with complex natural-language instructions \parencite{zhuo2024bigcodebench}. Hendrycks et al.\ proposed APPS, a 10{,}000-problem benchmark spanning introductory, interview, and competition-level coding challenges \parencite{hendrycks2021apps}. Jain et al.\ addressed the critical contamination problem through LiveCodeBench, which sources problems from recent competitive programming contests published after model training cutoffs \parencite{jain2024livecodebench}. Li et al.\ developed CodeReviewer for code review automation, an adjacent evaluation direction that assesses code quality dimensions relevant to AI-assisted development workflows \parencite{li2022codereviewer}. Each of these benchmarks measures distinct aspects of code generation or code quality capability, yet none evaluates the framework-specific convention adherence that the SmartKit framework targets.

\section{Empirical Studies on Developer Productivity}

Several empirical studies examine how AI assistance affects real developer workflows. Peng et al.\ conducted the seminal controlled experiment on GitHub Copilot with 95 recruited developers implementing an HTTP server in JavaScript \parencite{peng2023impact}. Their methodology used a treatment-control design with matched tasks, finding the 55.8\% completion time improvement cited earlier. Heterogeneous effects showed that less experienced developers benefited most from AI assistance. A large-scale survey by Liang et al.\ examined the usability of AI programming assistants and documented both successful use cases and recurring usability challenges in developer workflows \parencite{liang2024survey}.

Tariq et al.\ (preprint) reported an exploratory SSRN study describing an enterprise-level study with 60 developers and 960 task observations across eight .NET development tasks \parencite{tariq2026enterprise}. They measured task completion time, implementation errors, cyclomatic complexity, maintainability index, code smells, and NASA-TLX cognitive load scores. The preprint reports lower task completion time, fewer errors and code smells, lower cognitive workload, and improved maintainability under AI assistance, alongside redundant abstractions and increased code verbosity. Because the study is a preprint and its findings are specific to .NET development, it is treated here as contextual evidence rather than as a methodological basis or a directly transferable result for Next.js or JavaScript-based AI tool evaluation.

Liu et al.\ assessed ChatGPT code generation quality across multiple languages and task types \parencite{liu2024chatgpt}. ChatGPT performs better on pre-2021 problems with a 48.14-percentage-point advantage on Accepted rate (68.41\% versus 20.27\%), yet its ability to directly fix erroneous code through multi-round dialogue is relatively weak. Generated code often contained security vulnerabilities and inefficient implementations requiring human verification, although ChatGPT could resolve over 89\% of identified vulnerabilities through multi-round fixing. In a separate comparison, the same authors found that across 728 LeetCode problems in five languages, AI-generated Python3 solutions had an 8 percentage-point lower share of low-cognitive-complexity submissions than human-written solutions, while cyclomatic complexity distributions closely resembled the human baseline for Python3 (with a 5 percentage-point offset in C++ for cyclomatic) \parencite{liu2024chatgpt}. Yetiştiren et al.\ separately found, in their code quality evaluation study, that ChatGPT, Copilot, and CodeWhisperer all generated code with maintainability issues, particularly improper naming and high cognitive complexity, at technical-debt averages of 8.9, 9.1, and 5.6 minutes respectively \parencite{yetistiren2023evaluating}.

AlOmar et al.\ examined developer-ChatGPT refactoring conversations and found that developers frequently needed multiple iterations to achieve satisfactory refactoring \parencite{alomar2024refactoring}. AI often missed design-level improvements, and common anti-patterns emerged in developer-AI refactoring interactions. AI effectiveness therefore depends on the structure of the interaction and on the developer's ability to guide refinement, not only on the tool itself.

Hou et al.\ conducted a systematic literature review of 395 research articles on LLMs for software engineering from 2017--2024 \parencite{hou2024llmse}. Code generation (118 papers, approximately 30\% of the corpus) and program repair (35 papers, approximately 9\%) are the two most-studied application areas. The review's metric inventory groups evaluation by problem type rather than by benchmark-versus-human split: 338 generation-task studies used 19 metric families (BLEU-4 in 62 studies, Pass@k in 54, Accuracy@k in 39), 147 classification-task studies used nine metric families (Precision in 35, Recall in 34, F1-score in 33), 39 recommendation-task studies used six metric families, and 1 regression-task study used MAE \parencite{hou2024llmse}. Reported effectiveness varies widely by task type. The review identified research gaps in security, requirements engineering, and empirical studies. Framework-specific boilerplate evaluation would begin to address these gaps.

Russo et al.\ developed the Human-AI Collaboration and Adaptation Framework (HACAF), which identifies nine theoretical dimensions across individual (perceived usefulness, ease of use, behavioural intention), technological (compatibility, relative advantage, complexity), and social (social influence, environmental support, self-efficacy) levels \parencite{russo2024navigating}. Technical capability is necessary but insufficient on its own; this thesis reads their analysis as indicating that human factors, including trust, skill, and workflow integration, are necessary alongside technical capability for developer-tool adoption. Evaluating framework-specific boilerplate tools therefore requires attention to how well they integrate with developer workflows and support skill development.

\section{Evaluation Methodology}

The refinement of AI-generated code has received attention as a complementary evaluation dimension. Liu et al. analyzed 4{,}066 ChatGPT-generated programs across 2{,}033 programming tasks in Java and Python \parencite{liu2024refining}. Of these programs, 2{,}756 were deemed correct, 1{,}082 produced wrong outputs, and 177 contained compilation or runtime errors; 1{,}930 additional programs suffered from maintainability issues identified through static analysis. Their automated refinement pipeline using static-analysis feedback improved code quality by more than 20\%. Evaluation frameworks should therefore measure both initial generation quality and the effort required for refinement.

Ouyang et al. studied the non-determinism of ChatGPT in code generation \parencite{ouyang2025nondeterminism}. Across 829 problems in three benchmarks, the ratio of coding tasks with zero equal test output across different requests ranged from 47.56\% (HumanEval) to 75.76\% (CodeContests). Setting the temperature to 0 does not guarantee determinism, despite being a common practice. Reliable assessment therefore requires multiple runs with confidence intervals rather than single-point measurements.

Beller et al. proposed the DAT framework for measuring software development productivity, developed by the Developer Insights team at Meta \parencite{beller2026dat}. The approach combines diff authoring time, survey-based metrics, and AI tool-specific productivity measures. The DAT framework models a path for evaluating AI-boilerplate interaction that balances quantitative performance metrics with qualitative developer experience assessment.

Nguyen-Duc et al. distilled a research agenda of 78 open RQs across 11 software-engineering areas --- including requirements engineering, design, construction, testing, maintenance, and education --- where the current literature is comparatively sparse \parencite{nguyenduc2025genai}. The agenda explicitly calls for standardised evaluation and longitudinal studies, requirements that framework-specific evaluation frameworks can begin to satisfy.

Sauvola et al.\ projected four primary future scenarios for generative AI in software development, ranging from legacy integration to clean-slate and networked development, with software production shifting toward higher-level design and oversight roles as routine coding tasks become increasingly automated \parencite{sauvola2024future}. Research on optimising AI interaction patterns, including framework-specific boilerplate conventions that reduce the cognitive overhead of AI-assisted development, follows from this projection.

\section{Research Gap Summary}

The reviewed literature establishes three findings: AI coding assistants improve developer productivity on repetitive tasks; boilerplate generation is an AI strength area; and existing benchmarks measure algorithmic capability rather than framework convention adherence. To my knowledge, given the structured-but-non-exhaustive literature search described in the next section, I am aware of no published benchmark that systematically measures framework-convention adherence across multiple Next.js App Router conventions on a controlled corpus. A separate systematic search of framework-adjacent code-generation studies (e.g.\ on Angular/Vue/React-adjacent benchmarks) was not conducted. This gap is independently supported by Hou et al.\ (2024)'s systematic review of 395 LLM-SE articles, which does not list framework-specific convention adherence as a separately tracked evaluation category \parencite{hou2024llmse}; the review's research gaps (security, requirements engineering, empirical studies) likewise do not overlap with framework-specific boilerplate evaluation. This thesis proposes a Next.js boilerplate framework engineered for AI interaction and an evaluation methodology that measures framework-specific quality dimensions, reporting both as design-stage contributions.

\section{Alternative Approaches to AI-Codebase Alignment}

The structural approach taken by SmartKit is one of several strategies that researchers and practitioners have explored to improve AI-codebase alignment. This section reviews these alternatives and explains why the structural approach was selected.

Linter and formatter configurations (ESLint, Prettier, TypeScript compiler) can catch some convention violations but operate after code generation rather than before it. These tools validate style and type-correctness, not semantic feature boundaries; they cannot enforce Server/Client component conventions that require architectural awareness at the structure level. Linters operate alongside SmartKit's structural conventions rather than substituting for them: Biome 2.5.6 is included in SmartKit as a post-hoc consistency check on top of the convention envelope.

The structural approach taken by SmartKit addresses these limitations by encoding conventions at the project structure level. Conventions become discoverable by AI systems through file location and naming patterns, are enforced through project structure rather than developer vigilance, and provide reusable templates that scale across features. The structural approach works alongside prompting and documentation, not as a replacement.

\chapter{Proposed Solution}
\label{sec:solution}

This section presents the design of SmartKit, a Next.js boilerplate framework engineered to optimize interaction with AI coding assistants. The design synthesizes empirical findings from the literature with domain-specific analysis of Next.js conventions to produce a codebase structure that improves AI comprehension and output quality.

This thesis uses three related but distinct terms. \textbf{SmartKit} refers to the artefact released on GitHub, a Next.js App Router boilerplate containing six convention-encoding components (AGENTS.md, FSD directory structure, sibling feature examples, Zod schema patterns, ESLint configuration, and tsconfig path aliases). \textbf{SmartKit-style structuring condition} (abbreviated as Cond~A) is the specific experimental condition used in the pilot, comprising AGENTS.md plus one FSD-aligned sibling feature plus one colocated Zod schema. \textbf{SmartKit ecosystem} is the bundle-as-a-whole, the unit of measurement in the pilot. Findings in Chapter~6 are reported at the ecosystem level because the pilot was designed to measure the joint effect of the SmartKit convention envelope rather than to isolate any single component.

\section{Design Rationale}

Zhang et al.\ surveyed developers and found that Copilot is primarily used for code generation in general-purpose languages (JavaScript, Python) on VS Code, with data processing as the most common function category and integration difficulty as the dominant limitation \parencite{zhang2023practices}. This finding motivates the focus on boilerplate interaction as an appropriate domain for AI enhancement. Barke et al.\ observed that programmers interact with Copilot in two modes: acceleration (Copilot executes a known plan) and exploration (Copilot helps discover APIs). They documented four prompting strategies in their codebook: code prompts (71.4\% in acceleration) and context prompts (15.2\% in acceleration) as unintentional strategies, comment prompts (57.2\% in exploration versus 13.1\% in acceleration), and the multi-suggestions pane as the remaining intentional strategy \parencite{barke2022grounded}. These findings motivate three architectural decisions in the SmartKit design: encode conventions explicitly, group related code narrowly, and define type-safe contracts.

\textbf{Feature-based modularity over layer-based organisation.} Many Next.js projects organise code by technical layer (\filename{components/}, \filename{lib/}, \filename{hooks/}) or by page. Layer-based organisation creates wide import graphs: a single component may transitively import from dozens of files, so an AI system generating a new component receives a large, undifferentiated context. Feature-based modularity confines all code for one feature (schemas, actions, components, emails, types) within a single directory, giving the AI a narrow, self-contained context window. The trade-off is that cross-cutting concerns (shared utilities, types, or components) require deliberate extraction to a shared layer. This overhead is acceptable for SaaS boilerplate where the feature boundary is the primary decomposition axis.

\textbf{Drizzle ORM over Prisma.} Prisma uses a schema-first DSL (\filename{.prisma} file) that generates a client. Drizzle uses a TypeScript-first schema directly in \filename{.ts} files, colocated with the application code. I considered Prisma first because the schema-first DSL is easier to onboard onto. Then I read three RealWorld-tier codebases that mixed Prisma schemas with TypeScript business code, and the boundary confused the AI in every case. Drizzle's TypeScript-first approach won out for this thesis despite the steeper SQL learning curve: with Drizzle the AI reads and extends the schema using the same language model it uses for the rest of the codebase, and schema changes propagate through TypeScript's own type inference without a separate code-generation step.

\textbf{Explicit Server/Client boundaries over tRPC-based type sharing.} tRPC provides end-to-end type inference across the Server/Client boundary by sharing a single TypeScript interface definition. This eliminates a class of type errors but requires a separate router definition and does not enforce the architectural boundary at the file level. SmartKit instead uses Next.js's native \usec{} directive for Client Components and the \pkg{server-only} import for server-only utilities, supplemented by Zod schemas shared across the boundary. The native mechanism is framework-default rather than library-specific, which means the conventions survive beyond the SmartKit codebase and transfer to plain Next.js projects; tRPC conventions do not. The trade-off is that the native mechanism requires explicit developer discipline; tRPC enforces the boundary automatically through its type system. Per-feature Zod schemas are colocated under \filename{features/<name>/types/} so the same definition is the source of truth for both runtime validation (server action) and TypeScript inference (client component props); this location convention is described in \S4.5 (Type-Safe API Contracts).

\textbf{Zod schemas as the single source of truth across the Server/Client boundary.} React Server Components and Client Components communicate through typed props, but there is no built-in mechanism to ensure that the type on the server matches the type on the client. SmartKit uses Zod schemas, defined once in \filename{features/<name>/types/}, parsed at the server action boundary, and reused on the client via \pkg{z.infer}. A single schema definition is the source of truth for both runtime validation (server action) and TypeScript type inference (client component props), and the AI can read and extend the schema using the same Zod syntax it encounters in existing features. The trade-off is that Zod adds a runtime dependency and a learning curve for developers unfamiliar with schema-first validation.

\subsection{Intended Users and Adoption Path}

SmartKit targets solo developers and small teams (two to five members) who build Next.js projects with AI coding assistants. These developers already understand React and TypeScript fundamentals. They want to reduce boilerplate setup time and keep AI-generated code consistent with project conventions.

The framework supports incremental adoption. A team can adopt the feature-based folder structure and the Server/Client boundary conventions without committing to the full SmartKit stack. This lower adoption cost lets teams validate the conventions in an existing codebase before they pick up billing, authentication, or email integrations.

\section{Feature-Based Modular Architecture}

Many Next.js projects organize code by technical layer (components/, lib/, hooks/) or by page structure. SmartKit instead uses feature-based modularity, where each feature contains everything needed for its functionality: an authentication feature, for instance, holds database schemas, API routes, React components, form validation schemas, and email templates inside one directory.

This organization improves AI comprehension by narrowing the search space for relevant context when code is generated for one feature. The scope of any change becomes explicit, which lowers the risk of AI-generated code violating feature encapsulation. The directory boundary is also a natural test and deployment unit that matches developer mental models.

The feature directory structure follows a consistent pattern across all features:

\section{Server/Client Boundary Conventions}

React Server Components introduce an explicit boundary between server-only and client-accessible code, and \autoref{sec:stack-rationale} motivates why SmartKit relies on Next.js's native mechanism (the \usec{} directive and the \pkg{server-only} import) rather than a library such as tRPC. This section focuses on how those two primitives are applied in practice: where they live in the source tree, and what data-flow shape they impose on AI-generated code.

The boundary shapes data-flow design. Server Components can read databases and environment variables directly, while Client Components receive data through props or invoke server actions. AI systems can therefore call type-safe server actions from a Client Component, which keeps the data path consistent as new components are generated.

\section{Database Schema Patterns}

SmartKit uses Drizzle ORM with PostgreSQL to provide type-safe database access across the application. The schema design follows conventions that AI systems can learn from existing tables and reproduce for new ones: each table declares columns with explicit types, relations through foreign keys, and indexes for query optimisation.

The Drizzle query pattern lets AI-generated code read and write the database through type-safe query builders. AI systems can examine an existing schema to infer a join or insert shape and produce code that preserves type safety end-to-end. Ad-hoc queries that bypass type checking or violate the file-level conventions are discouraged.

Better~Auth supplies the shared identity tables (\code{user}, \code{session}, \code{account}, \code{verification}) used by every feature that signs users in, while \filename{features/billing/} owns its own \code{billing} and \code{payment\_transactions} tables. All four Better~Auth tables and the billing tables live in \filename{src/database/schema/}, one infrastructure directory outside the FSD hierarchy, with relations declared in \filename{src/database/schema/relations.ts}. The single-directory placement lets \pkg{drizzle-kit} scan every schema in one pass and lets any feature import shared row types (\filename{database/schema/index.ts}) without depending on a sibling feature. The placement keeps database patterns centralised while still being directly importable from any feature module.

\section{Type-Safe API Contracts}

API routes in SmartKit use Zod schemas for request and response validation. Schemas are defined once per feature (in \filename{features/<name>/types/}, as introduced in \autoref{sec:stack-rationale}) and \pkg{z.infer} derives the matching TypeScript type, so the same definition is the source of truth for both runtime validation and TypeScript inference. AI systems can examine a Zod schema to understand the contract on both sides of the boundary and generate code that respects it without separate type annotations.

Because the schemas are shared, the validation logic on the client and the server stays in lockstep. The same Zod object validates a client-submitted form before submission and a server-handled request inside a route handler or action. The match closes the gap between AI-generated client-side and server-side code, producing more coherent implementations across the boundary.

\subsection{Stack Selection Rationale}
\label{sec:stack-rationale}

Each component of the SmartKit stack reinforces one of the three evaluation dimensions. The comparison with alternative choices (tRPC versus native Server/Client boundary, Prisma versus Drizzle, raw types versus Zod) is given in \autoref{sec:stack-rationale}. Three guiding principles follow from that comparison:

\begin{enumerate}
  \item \textbf{App Router as the structural surface.} Next.js~16's App Router exposes the conventions Structural Integrity measures: Server/Client boundaries, file-system routing, and the \usec/\pkg{server-only} primitives are framework defaults. These rules therefore transfer to plain Next.js projects rather than coupling the rubric to SmartKit-specific library conventions.
  \item \textbf{Zod schemas at the Server/Client boundary.} TypeScript~5.7.3 strict mode provides the compile-time signal that Type~\&~Contract Safety reads from \code{tsc --noEmit}. Zod~4 schemas, colocated in \filename{features/<name>/types/}, are parsed at the Server Action boundary and reused on the client via \pkg{z.infer}; one schema is the source of truth on both sides, and Coverage~\&~Completeness checks for its presence at the expected path. AI tooling can read and extend the same Zod syntax it encounters in existing features.
  \item \textbf{Server/Client boundary errors surface as build-time failures.} Server Components fetch data directly through Drizzle, Server Actions in \filename{features/<name>/actions/} call \code{revalidatePath} after writes, and Client Components receive typed props without an intermediate client-side data layer. These failures are the signal Structural Integrity reads; a tRPC-style shared router would hide the boundary inside library types and remove that signal, which is why SmartKit uses the framework-native primitives instead.
\end{enumerate}

\subsection{Feature Flag Resolution}
\label{sec:feature-flag-resolution}

The feature flag system resolves override sources in priority order: per-user overrides, then environment variables, then a static default. The implementation lives in \filename{features/flags/lib/is-enabled.ts}, which is marked \pkg{server-only} so that Next.js fails the build if a Client Component imports it.

The Zod schema that defines the allowed \code{FlagKey} values is colocated in \filename{features/flags/types/flags.ts}:

\begin{lstlisting}[
  language=TypeScript,
  caption={Zod schema for feature flag keys.},
  label={lst:flag-key-schema},
  basicstyle=\ttfamily\scriptsize,
]
import { z } from "zod";

export const FlagKeySchema = z.enum([
  "FEATURE_NEW_DASHBOARD",
  "FEATURE_BILLING_ENABLED",
  "FEATURE_DARK_MODE",
]);

export type FlagKey = z.infer<typeof FlagKeySchema>;
\end{lstlisting}

The \code{isEnabled} function implements the three-tier resolution with in-memory caching:

\begin{lstlisting}[
  language=TypeScript,
  caption={The isEnabled utility with three-tier resolution and 5-minute TTL cache.},
  label={lst:is-enabled-impl},
  basicstyle=\ttfamily\scriptsize,
]
import "server-only";
import { FlagKeySchema, type FlagKey } from "../types/flags";

const TTL_MS = 5 * 60 * 1000;

// Two parallel maps -- values holds the resolved boolean, expirations
// holds the wall-clock timestamp at which the entry expires.
const values = new Map<string, boolean>();
const expirations = new Map<string, number>();

const buildCacheKey = (flag: FlagKey, userId?: string): string =>
  userId ? `${flag}__${userId}` : `${flag}___`;

const readUserOverride = (
  _userId: string | undefined,
  _flag: FlagKey,
): boolean | undefined => {
  // Per-user DB override is not wired in this pilot.
  return undefined; // signals "no override, fall through"
};

const readEnvOverride = (flag: FlagKey): boolean | undefined => {
  const raw = process.env[`FLAG_${flag}`];
  if (raw === "true") return true;
  if (raw === "false") return false;
  return undefined;
};

export function isEnabled(
  flag: unknown,
  fallback: boolean = false,
  userId?: string,
): boolean {
  const parsed = FlagKeySchema.safeParse(flag);
  if (!parsed.success) {
    throw new Error(
      `Invalid flag key: ${JSON.stringify(flag)}. ` +
        `Allowed: ${FlagKeySchema.options.join(", ")}`,
    );
  }
  const key = buildCacheKey(parsed.data, userId);
  const now = Date.now();

  const expires = expirations.get(key);
  if (expires !== undefined && expires > now) {
    const cached = values.get(key);
    if (cached !== undefined) return cached;
  }

  let resolved: boolean | undefined =
    readUserOverride(userId, parsed.data) ??
    readEnvOverride(parsed.data) ??
    fallback;

  values.set(key, resolved);
  expirations.set(key, now + TTL_MS);
  return resolved;
}
\end{lstlisting}

\bigskip\noindent\textbf{Design rationale.}
The tiered design supports gradual rollouts via environment variables before per-user targeting. The 5-minute TTL bounds memory growth while keeping flag values fresh for environment-driven rollouts. The server-side boundary rationale, why the function lives behind \pkg{server-only} rather than crossing the Server/Client boundary, is given in \autoref{sec:server-client-boundary}.

\subsection{Server/Client Boundary Enforcement}
\label{sec:server-client-boundary}

Server/Client boundary errors are the failure mode Structural Integrity reads: event handlers crossing the boundary, and server-only imports leaking to the client. Next.js surfaces both as build-time errors. Server Components fetch data directly through Drizzle, Server Actions in \filename{features/<name>/actions/} call \code{revalidatePath} after writes, and Client Components receive typed props without an intermediate client-side data layer.

To prevent accidental client bundling of server-only code, the framework uses the \pkg{server-only} package~\parencite{server-only-npm}:

\begin{lstlisting}[
  language=TypeScript,
  caption={Using server-only to prevent client bundling.},
  label={lst:server-only-usage},
  basicstyle=\ttfamily\scriptsize,
]
import "server-only";

// This module cannot be imported into Client Components.
// Next.js will throw a build-time error if attempted.
export async function getServerData() {
  // server-side only logic
}
\end{lstlisting}

\bigskip\noindent The rationale for using \pkg{server-only} and \usec{} as the boundary primitives is given in \autoref{sec:server-client-boundary}; the listing above shows the import statement and the build-time error that Next.js produces when a Client Component attempts to import this module.

\subsection{Evaluation Infrastructure}
\label{sec:eval-infrastructure}

To run the three evaluation dimensions, the framework includes an automated scoring script (\filename{scripts/score-flag.ts}) that reads source files and computes a 0--5 score per dimension. The script is read-only: it does not mutate the run directory and does not call any AI or LLM for scoring.

The structural integrity scoring logic detects server/client boundary violations:

\begin{lstlisting}[
  language=TypeScript,
  caption={The structural integrity scoring logic from score-flag.ts.},
  label={lst:scoring-logic},
  basicstyle=\ttfamily\scriptsize,
]
/** Score Structural Integrity dimension (0-5) */
async function scoreStructural(runDir: string): Promise<DimScore> {
  const details: Record<string, unknown> = {};

  // Locate the main utility file (any name, look for isEnabled function)
  const tsFiles = await findTsFiles(runDir);
  let isEnabledPath: string | null = null;
  let hasServerOnly = false;
  let hasUseClient = false;
  let hasIsEnabledExport = false;

  for (const f of tsFiles) {
    const content = await readFile(f, 'utf-8');
    const hasExport =
      /export\s+(?:async\s+)?function\s+isEnabled/.test(content) ||
      /export\s+const\s+isEnabled/.test(content) ||
      /export\s+default\s+(?:async\s+)?function\s+isEnabled/.test(content) ||
      /export\s+default\s+isEnabled/.test(content);

    if (hasExport) {
      isEnabledPath = f;
      hasIsEnabledExport = true;
      hasServerOnly = /import\s+["']server-only["']/.test(content) || /from\s+["']server-only["']/.test(content);
      hasUseClient = content.includes("'use client'") || content.includes('"use client"');
    }
  }

  // Normalize path separators to forward-slash for cross-platform path detection
  // (relative() on Windows returns backslashes; downstream checks use forward-slash)
  const relPath = isEnabledPath
    ? relative(runDir, isEnabledPath).replace(/\\/g, '/')
    : '(not found)';
  details.is_enabled_file = relPath;
  details.has_is_enabled_export = hasIsEnabledExport;
  details.uses_server_only_import = hasServerOnly;
  details.has_use_client_in_util = hasUseClient;

  // Split scoring: path_match (0/0.5/1) and feature_complete (0/0.5/1)
  let pathMatch = 0;
  let featureComplete = 0;

  if (!isEnabledPath) {
    pathMatch = 0;
    featureComplete = 0;
    details.failure_reason = 'No file with isEnabled function found';
  } else {
    const inFeatures =
      relPath.includes('features/flags/lib/') ||
      (relPath.includes('src/features/') && relPath.endsWith('/lib/is-enabled.ts'));
    const inRoot = relPath.startsWith('lib/') || relPath.startsWith('src/lib/') || !relPath.includes('features/');
    const inApp = relPath.includes('app/');

    // Path matching score
    if (inApp || inRoot) {
      pathMatch = 0; // Severe: wrong location
    } else if (!inFeatures && relPath.includes('features/')) {
      pathMatch = 0.5; // Partial: in features/ but wrong subfolder
    } else if (inFeatures) {
      pathMatch = 1; // Correct: features/flags/lib/
    }

    // Feature completeness score
    if (!hasIsEnabledExport) {
      featureComplete = 0; // Missing export
    } else if (hasUseClient) {
      featureComplete = 0.5; // Has export but uses 'use client' (wrong)
    } else if (hasServerOnly) {
      featureComplete = 1; // Has export + server-only
      // Check barrel re-export for full completeness
      if (relPath.includes('features/flags/lib/')) {
        const barrel = join(dirname(isEnabledPath), '..', 'index.ts');
        if (existsSync(barrel)) {
          const barrelContent = await readFile(barrel, 'utf-8');
          if (!barrelContent.includes('isEnabled')) {
            featureComplete = 0.9; // Almost complete but missing barrel
          }
        }
      }
    } else {
      featureComplete = 0.7; // Has export but no server-only
    }
  }

  details.path_match = pathMatch;
  details.feature_complete = featureComplete;

  // Overall score (0-5) = weighted combination
  const score = Math.round((pathMatch + featureComplete) * 2.5);
  details.score = score;
  return { score, details };
}
\end{lstlisting}

\bigskip\noindent\textbf{How the rubric maps to code.}
Each scoring function returns 0 (violation), 3 (partial), or 5 (pass) per sub-criterion; these are combined into a 0--5 dimension score. Type \& Contract Safety runs \code{tsc --noEmit} and counts \code{: any} occurrences; Coverage \& Completeness enumerates required files (\code{is-enabled.ts}, \code{is-enabled.test.ts}, \code{flags.ts}, \code{index.ts}) against a reference checklist. The complete rubric implementation is in \filename{smartkit/scripts/score-flag.ts}.

\bigskip\noindent\textit{Scoring vs.\ rubric note.} The automated script combines two sub-criteria into a 0--5 score by the formula $\mathrm{round}((\mathit{pathMatch} + \mathit{featureComplete}) \times 2.5)$. The sub-criteria take values in $\{0, 0.5, 1\}$ for path placement and $\{0, 0.5, 0.7, 0.9, 1\}$ for feature completeness. A wrong-subfolder placement ($\mathit{pathMatch} = 0.5$) with a complete feature body ($\mathit{featureComplete} = 1$) gives $(0.5 + 1) \times 2.5 = 3.75$, which rounds to 4. Table~\ref{tab:rubric-structural} caps wrong-subfolder placement at Level 2 (\emph{Partial}). The script therefore diverges from the rubric prose on this edge case. The executed pilot placed every file at \filename{features/flags/lib/}, so the divergence did not change any reported score; it is documented here so future replications at off-canonical paths read the script output against the rubric prose, not the arithmetic alone.

\section{Evaluation Framework}
\label{sec:evaluation-framework}

The remainder of this chapter reports the locked protocol used to produce the empirical data, and then reports the data itself.

\subsection{Three Dimensions}
\label{sec:dimensions}

The evaluation uses a multi-dimensional quality framework that captures different aspects of boilerplate quality. The framework extends existing benchmark methodology to address framework-specific concerns that existing evaluations overlook; the specific literature gap that motivates this framework is documented in the Related Work chapter. SmartKit's contribution is to instantiate the missing framework-specific convention-adherence measurement dimension for Next.js App Router.

The three dimensions capture distinct, non-overlapping aspects of boilerplate quality that affect real-world usability. Rather than measuring only output correctness, the framework assesses whether generated code can be integrated into production codebases without convention violations or type safety issues. Each dimension maps to an automated measurement approach and corresponds to a specific failure mode observed in AI-generated Next.js code.

\textbf{Unit of analysis.} Scoring is performed per generated file: each file receives one score per dimension, and feature-level scores are computed as the median across constituent files. The median is used rather than the mean because individual files within a feature may exhibit extreme outlier scores due to edge-case generation failures (e.g., a single malformed file), and the median is robust to such outliers.

\textbf{Structural Integrity} assesses whether generated code follows Next.js conventions for file location, naming, Server/Client component boundaries, and App Router patterns. Automated checking uses the \filename{score-flag.ts} script. The dimension captures violations such as incorrect file placement in the \filename{features/} directory, missing \usec directives on client components, and non-standard naming patterns that break routing.

\textbf{Type \& Contract Safety} combines two sub-scores on the 0--5 rubric. The Type Safety sub-score reads \code{tsc --noEmit} error counts and \pkg{@typescript-eslint/}\pkg{no-explicit-any} occurrences; these indicate whether generated code introduces type regressions. The Contract Safety sub-score reads the proportion of API route handlers that include Zod schemas for request/response validation. The two sub-scores combine under the lower-of rule: the dimension score equals the smaller of the two sub-scores.

\textbf{Coverage \& Completeness} evaluates whether generated boilerplate includes all necessary artifacts for a functional feature. \autoref{tbl:coverage-checklist} shows the reference checklist for the \code{isEnabled} feature flag utility used in the pilot. Completeness is measured by enumerating generated files against the checklist and computing a coverage ratio.

\subsubsection{Relationship between SmartKit Integrations and the Pilot Feature}
\label{sec:integrations-and-pilot}

SmartKit instantiates the framework conventions across multiple feature areas, including billing (SePay integration), authentication (Better~Auth), and email (Resend). These integrations exist because the artifact is a usable SaaS boilerplate. The pilot deliberately selects a feature, the feature-flag check utility, that uses \emph{none} of the integrated services, in order to isolate the effect of convention encoding from the effect of having integrated services available. If the pilot used a feature that integrates SePay or Resend, any observed difference between Condition~A and Condition~B would conflate convention encoding with integration availability. The integrations remain first-class in the artifact; their relation to the pilot evaluation is summarised in the scope note at the start of this chapter. This separation is what allows the framework to remain generalisable beyond SmartKit: a developer using a different stack can encode the same conventions without SePay, Resend, or Better~Auth, and the framework still measures the same three dimensions on any generated feature.

A second, related point concerns the role of the integrations during the AI session. In Condition~A, the AI sees the full SmartKit file tree, including \filename{features/billing/} (SePay HMAC, idempotency), \filename{features/auth/} (Better~Auth schemas and server actions), and the Resend email templates under \filename{features/auth/emails/}. These files belong to SmartKit's second role as a usable SaaS boilerplate (see the scope note at the start of this chapter); they encode the SmartKit convention envelope: feature-based folder structure, colocated server actions, Zod schemas in \filename{types/}, \pkg{server-only} boundaries, and \code{revalidatePath} after mutations. The AI in Condition~A pattern-matches this envelope when generating the pilot feature, even though the pilot feature itself does not call any of the integrated services. In Condition~B, none of these pattern sources are available, so the AI must invent both the utility and its surrounding convention. The score difference between conditions therefore measures the convention envelope, not the integration surface. The convention envelope is what the framework is designed to capture; the integration surface is what makes SmartKit a usable SaaS boilerplate. Both are required for the thesis, but they play distinct roles. The integration surface contributes to the second thesis contribution---the SmartKit artifact as a working SaaS boilerplate---rather than to the pilot; the pilot is the instrument that exercises the framework on AI-generated code, while the integrations are the evidence that the framework conventions are usable in production code. This bundled-effect limitation is analyzed in \autoref{sec:dp2-results}.

\subsection{Rubric Interpretation}
\label{sec:rubric-interpretation}

The three rubric dimensions introduced and detailed in this chapter carry different epistemic statuses with respect to the underlying constructs they are taken to represent. This subsection makes those statuses explicit so that pilot results are read within the framework's validated scope, and not beyond it.

\paragraph{Three dimensions, three epistemic statuses.} Each dimension is grounded in a distinct form of evidence, and the strength of the inference from a score to a substantive claim differs accordingly.

Structural Integrity: \emph{directly measured}. The score counts the presence or absence of artifacts at expected paths in the SmartKit feature-sliced layout (file placement, \code{server-only} import detection, \usec{} directive checks, barrel-file verification). Differences between conditions reflect observed counts across runs (e.g.\ on the central artifact path, Cond~A confirmed with all 5 runs passing and Cond~B refuted with 0 out of 5 runs passing), not estimates or judgements, so the dimension-level score is reproducible from the run artefacts without calibration against an external construct.

For Type \& Contract Safety, the score is a \emph{justified proxy for production quality}. The sub-scores combine \code{tsc --noEmit} error counts and Zod-schema coverage at API boundaries; these signals are well-motivated indicators of compile-time and contract-level safety. The cutoffs are asserted design choices; Security review, load testing, observability, and runtime hardening remain outside this dimension's scope.

Coverage \& Completeness reads as an \emph{aspirational developer-experience proxy}. The pilot validates the dimension's measurement capability across the 0--3 range (file-presence and basic artifact structure). Levels 4--5 (DB-backed integrations, deployed instances) require a pilot feature that exercises SmartKit's existing integrations; the current pilot deliberately excludes integrations to isolate structural convention effect (\autoref{sec:integrations-and-pilot}).

\subsection{Evaluation Design: Rationale and Trade-offs}
\label{sec:design-rationale}

The evaluation framework design involves several deliberate choices that balance scope with feasibility. Prior work on tool-assisted coding includes rule-based static analysis (ESLint, TypeScript) and LLM-based code generation (GitHub Copilot, Claude Code). SmartKit takes a third path by encoding framework conventions at the project-structure level rather than relying on post-hoc validation or prompt engineering.

\textbf{Dimension selection.} The three dimensions were designed to address the gap between output-oriented benchmarks (algorithmic correctness) and the framework-specific quality dimension that existing benchmarks do not measure. Each SmartKit dimension targets a distinct failure mode observed in AI-generated Next.js code: structural violations (file placement, Server/Client boundaries), type safety gaps, and missing boilerplate artifacts.

\textbf{Automated over manual evaluation.} The framework prioritises automated metrics to enable reproducibility and scale. Expert review provides richer qualitative assessment, but automated checking ensures consistent evaluation across the large number of code samples required for meaningful comparison. Where qualitative judgement is necessary (e.g., structure quality assessment), LLM-as-judge with majority voting is a future option that was not exercised in the executed pilot; the pilot uses automated-only scoring.

\textbf{6-level rubric across dimensions.} Each of the three~dimensions is scored on a 0--5 rubric (six integer levels). The per-dimension cell descriptions are detailed in the rubric table; the rough mapping is: $0$ = missing artefact, $1$ = severe violation, $2$ = partial (in the right neighbourhood but wrong sub-detail), $3$ = acceptable, $4$ = good (level 3 + a specific bonus criterion, e.g.\ \code{server-only} for Structural), $5$ = excellent (level 4 + a second bonus criterion, e.g.\ barrel re-export). The exact level descriptions are dimension-specific and were inferred from related literature on code quality rubrics \parencite{li2022codereviewer}; per-level cutoffs have not been calibrated against developer-experience data.

\textbf{Rubric scope, not calibration gap.} The Coverage ceiling and its measurement correction are documented in \autoref{sec:measurement-validity}; rubric calibration remains future work.

\textbf{Single-framework focus.} The evaluation focuses exclusively on Next.js to maintain depth over breadth. Future work should extend the framework to Nuxt and Remix to assess generalizability of the approach.

\textbf{Confound control between conditions.} The no-integration pilot feature removes service-specific patterns from the comparison (see \autoref{sec:integrations-and-pilot}). Three confounds persist: ecosystem-level reinforcement through sibling features; run-order between Condition~B (Runs 1--5) and Condition~A (Runs 6--10); and tool-snapshot drift across Condition~A.

The control artifact is the control condition and provides a baseline that isolates SmartKit's convention encoding from the underlying technology stack.

Quantitative metrics derive from automated analysis of generated code. \textit{Structural Integrity} uses Biome custom rules to check Next.js-specific file placement, naming, and Server/Client boundary conventions. \textit{Type \& Contract Safety} uses \code{tsc --noEmit} output to identify type violations and custom Biome rules for \emph{any}-type detection and Zod coverage. \textit{Coverage \& Completeness} uses file enumeration against a reference checklist per feature type.

The pilot uses automated-only scoring (Biome, \code{tsc --noEmit}, file enumeration via \filename{score-flag.ts}).

Productivity metrics such as diff authoring time and developer-reported productivity \parencite{beller2026dat} are not collected in the current pilot and remain future work; the executed pilot reports only per-run time-to-correct (ttc, in minutes) as a coarse timing signal. Task completion time, cyclomatic complexity, maintainability index, and code smell density are documented as design-stage metrics for a future developer-participant study.

\section{Pilot Methodology}
\label{sec:pilot}
\label{sec:pilot-protocol}

This section describes the pilot design: the two conditions being compared, the standardised task, the scoring rubric, and the decision rule for interpreting results.

\subsection{Pilot Design Overview}
\label{sec:pilot-overview}

The demonstration runs one task (generating a feature-flag utility) across two conditions, with five independent runs per condition. Each run produces a score on the 0--5 rubric. The verdict rule classifies the outcome as follows:

\begin{itemize}
    \item \textbf{Confirmed}: all five runs in a condition score $\geq 3/5$.
    \item \textbf{Refuted}: none of the five runs score $\geq 3/5$.
    \item \textbf{Inconclusive}: one to four runs score $\geq 3/5$.
\end{itemize}

This binary verdict answers a feasibility question: can the framework detect a difference between the convention envelope and the convention-naive baseline? It does \emph{not} measure how large that difference is. The limits of this verdict are discussed in \autoref{sec:conclusion-validity}.

The representative feature (\code{isEnabled(flagKey, userId?)}) was selected because it exercises none of SmartKit's integrated services; this choice isolates the convention-encoding effect from service-specific patterns (see \autoref{sec:integrations-and-pilot}). The evaluation scenario measures AI-generated boilerplate quality directly: AI systems receive task descriptions, and the generated code is measured against the framework dimensions. The demonstration focuses on Cursor as the primary case study, consistent with the scope defined in the introduction. All evaluations use multiple runs to address non-determinism concerns raised by Ouyang et al.\ \parencite{ouyang2025nondeterminism}; the Cursor tool does not expose user-settable temperature (the snapshot used in the demonstration does not surface this control), so multi-run evaluation substitutes for temperature variation as the determinism-handling mechanism. Results report per-condition medians and ranges, plus Wilson 95\% confidence intervals on the binary pass rate ($\geq 3/5$).

The prompt intentionally avoids referencing SmartKit-specific conventions (\emph{do not} say ``for SmartKit'', ``follow the feature-based layout'', ``use \filename{.server} naming'', or ``refer to AGENTS.md''). The full pre-registration record, including the frozen prompt hash, is reproduced in the pilot protocol.

The same per-run pipeline was applied to all ten runs, with per-run scores plotted in \autoref{fig:pilot-scores} and per-condition aggregates reported in \autoref{tbl:pilot-aggregate}:
\begin{enumerate}
    \item Initialize a fresh copy of the codebase with the pre-registered tooling verified against a run-day checklist.
    \item Invoke Cursor with the standardized prompt; start the time-to-correct clock.
    \item Collect generated files, Biome violations, \code{tsc --noEmit} output, and artifact enumeration; snapshot the run in \filename{runs/cond-<a,b>/run-<NN>/}.
    \item Score each run on the three-dimension rubric; record per-run JSON; commit before the next run.
\end{enumerate}

\subsection{Run Schedule and Verdict Rule}
\label{sec:pilot-schedule}

The pilot followed a pre-registered adaptive schedule: five runs in Condition~B (Runs~1--5) and five runs in Condition~A (Runs~6--10). Both arms reached adaptive-$N=5$ to satisfy the binary verdict rule and open the comparative-CI gate. The verdict rule in force: 5 out of 5 passing runs resolves as confirmed; 0 out of 5 resolves as refuted; 1 to 4 out of 5 resolves as inconclusive. The full schedule with tool snapshots, verdict counts, and timestamps is in the pilot audit trail released in the thesis GitHub repository.

For each run treated as a binary outcome (pass = score $\geq 3/5$; fail = score $< 3/5$), the Wilson 95\% confidence interval on the proportion of passing runs is computed by:
\begin{equation}
\frac{k + \frac{z^2}{2}}{n + z^2} \pm \frac{z}{n + z^2} \sqrt{\frac{k(n-k)}{n} + \frac{z^2}{4}}
\label{eq:wilson}
\end{equation}
where $k$ is the number of passing runs, $n=5$, and $z = 1.96$ for 95\% confidence. The Wilson interval is preferred over the normal approximation (Wald interval) for small $n$ because it never produces bounds outside $[0, 1]$ and has better coverage properties when the true proportion is near 0 or 1. At $n=5$ the 95\% CI half-width is approximately $0.21$, so the binary verdict rule (5/5 vs 0/5) is the only inferentially safe read at this sample size; per-arm rates between these extremes are not distinguishable from chance fluctuation. Results are reported as median [min, max] with Wilson 95\% confidence interval (CI) for the pass rate. The formula is in \autoref{eq:wilson}.

A pre-registered plan called for a second rater to independently score 2 runs (1 per condition) using the same rubric, with Cohen's $\kappa \geq 0.7$ as the threshold for rubric revision. The pilot executed with automated-only scoring; the IRR pass was therefore not run, and the rubric has not been empirically cross-checked against a human rater. Re-executing the IRR pass on a representative slice of runs is documented as future-work item~3 (\autoref{sec:future-work}).
\label{sec:pilot-irr}

\section{Results}
\label{sec:pilot-results}

The pilot applied the three-dimensional framework to one representative task: generating the \seqsplit{isEnabled(flagKey, userId?)} utility using Cursor. The demonstration ran five times under Condition~A and five times under Condition~B. Of the three directional predictions, two confirmed outright, one confirmed as an instruction-following asymmetry, and one clause refuted.

\textbf{What the reader should expect.}
The pilot's directional predictions anticipate a clear contrast on two of three dimensions. Cond~A is predicted to score at or near the rubric ceiling because its convention envelope (AGENTS.md, sibling features, FSD layout, Zod patterns) is designed to produce exactly those outputs. Cond~B is predicted to score at or near the floor because its scaffold lacks every convention-encoding signal the framework measures. The binary verdict rule classifies a 5/5 pass rate as confirmed, a 0/5 pass rate as refuted, and 1--4 out of 5 as inconclusive.

\textbf{How to read the ceiling--floor pattern.}
Cond~A's medians sit at rubric ceiling on Structural Integrity (5) and near the ceiling on Type \& Contract Safety (4); Coverage is reported at its pilot-feature ceiling of 3 (see \autoref{sec:measurement-validity}). Cond~B's medians sit near the floor: Structural Integrity 2, Type \& Contract Safety 3 (raw values: 0, 3, 3, 3, 3), and Coverage 0. The interpretation of this contrast is bounded by \autoref{sec:threats}.

\textbf{Scoring.} \textit{Structural Integrity} was scored by running the \filename{score-flag.ts} script against the generated files, counting violations per category. \textit{Type \& Contract Safety} was scored by running \code{tsc --noEmit} on the generated code and counting type errors and \emph{any}-type occurrences. \textit{Coverage \& Completeness} was scored by enumerating generated files against a reference checklist. Each dimension is reported on the 0--5 rubric described earlier in this chapter.

\subsection{Pilot Scores}

\textbf{Score pattern.} Cond~A scored Structural Integrity 5 and Type \& Contract Safety 4 in all 5 runs; Coverage scored 3 in all 5 runs, its pilot-feature ceiling (see \autoref{sec:measurement-validity}). \section{Discussion}
\label{sec:discussion}

This section reads the executed scores against the rubric mechanics and issues three directional-prediction verdicts: confirmed, refuted, or inconclusive based on whether all, none, or some runs met the passing threshold.

\subsection{DP1 -- Structural Integrity Placement}
\label{sec:dp1-results}

\textbf{Confirmed.} Cond~A placed the utility at the predicted path \filename{features/flags/lib/is-enabled.ts} in all five runs. Cond~B placed it at root \filename{lib/} in all five runs. The pattern is consistent with an ecosystem-level mechanism: the SmartKit codebase exposes \filename{AGENTS.md}, sibling features under \filename{features/}, and the established placement in adjacent features; the convention-naive scaffold exposes none of these, so generated output falls back to root-level placement.

\subsection{DP2 -- Type \& Contract Safety (Zod-derived FlagKey)}
\label{sec:dp2-results}

\textbf{Confirmed as instruction-following asymmetry}. Cond~A produced a Zod-derived \code{FlagKey} enum in all 5 runs and Cond~B produced a raw \code{string} type alias in all 5 runs.
The standardized prompt, the dependency surface, and the explicit
Zod directive (``use a Zod schema to derive'') were identical
across conditions, so the asymmetry is not attributable to a
missing-package effect on Cond~B. The attribution question that
remains is whether the asymmetry reflects the SmartKit
convention-encoding effect or instruction-following reinforcement
that the ecosystem incidentally enables: Cond~A's prompt bundles
the directive with three ecosystem-level reinforcement signals
absent from Cond~B (AGENTS.md, colocated Zod schemas in
\filename{features/auth/} and \filename{features/billing/}, and
the Zod patterns in \filename{src/database/schema/}), and a
compliant Cond~A run cannot be attributed to the directive, the
ecosystem, or the dependency in isolation. Adjudicating between
the two explanations requires the bundled-effect isolation
experiment (future-work item~4), which re-runs DP2 with the
Cond~B prompt removing the shared Zod directive.

\textbf{What this verdict means.} The framework detected a difference between
conditions on Type \& Contract Safety: Condition~A consistently produced Zod-derived
types while Condition~B produced raw string types. The pilot cannot
determine whether this outcome stems from convention encoding in the SmartKit
ecosystem or from instruction-following reinforcement that the ecosystem
incidentally provides. Resolving this attribution requires isolating the
Zod directive from the ecosystem effect, which is the purpose of the
bundled-effect experiment planned as Future Work item 4.

\subsection{DP3 -- Coverage \& Completeness (Centralized Test Path)}
\label{sec:dp3-results}

\textbf{DP3-A: confirmed.} Condition~A placed a test file at the predicted centralised path in all five runs.
\textbf{DP3-B: refuted.} The convention-naive scaffold placed a test file at the repository root in all five runs, the opposite of the prediction.

\subsection{Synthesis}
\label{sec:discussion-synthesis}

Two findings are consistent across predictions. DP1 and DP3-A both show Cond~A placements matching the predicted FSD paths in all 5 runs, indicating that structural-convention signals (AGENTS.md, sibling features, FSD layout) orient placement when present. DP2's confirmed-asymmetry verdict and DP3-B's refutation show different outcomes: Cond~A reinforces the Zod directive (DP2) and produces consistent placement (DP1, DP3-A), whereas Cond~B places tests at the repository root (DP3-B). I read the DP3-B refutation as a positive finding about the framework's discriminative capacity rather than as a contradiction of the DP1/DP2 outcomes.

\paragraph{Scope of these verdicts.} The binary rule and confidence interval are defined in \autoref{sec:pilot-schedule}. Attribution and measurement limits are assessed in \autoref{sec:threats}; the Coverage cap does not change the DP1 and DP3-A placement verdicts.

\subsubsection*{Analytical Discussion}
The four subsections below analyse the pilot results beyond the verdict descriptions in \autoref{sec:pilot-results}. Each subsection addresses one analytical question: mechanism (which convention-encoding effect did the pilot actually exercise), alternative explanations (which the pilot cannot rule out), comparison to the AI-code-generation literature (what the results add on top of HumanEval and SWE-bench), and implications (what the framework tells practitioners and researchers to do next).

\subsection{Mechanism and Alternative Explanations}
\label{sec:mechanism-and-alternatives}

Three mechanisms are consistent with the observed ceiling--floor pattern (\autoref{fig:pilot-scores} shows the numbers; \autoref{sec:pilot-results} explains how to read them), and the pilot design separates which mechanisms it can and cannot test.

\textbf{Structural-convention signals orient placement when they are present.} DP1 (Structural Integrity placement) and DP3-A (Coverage \& Completeness, centralized test path) both show Cond~A placements matching the predicted FSD paths in all five runs. Cond~B places these at root-level paths. AGENTS.md, sibling features, and the FSD layout are visible in Cond~A and absent in Cond~B. The consistent 5/5 contrast on placement dimensions indicates that the visible codebase structure does orient AI-generated file placement.

\textbf{The ecosystem reinforces directives that match its existing patterns.} DP2 (Zod-derived FlagKey) produced the predicted contrast (Cond~A Zod, Cond~B raw string). This thesis deliberately tests convention encoding at the ecosystem level (bundled effect by design). The ecosystem-level question—\emph{whether} the full SmartKit convention envelope drives adherence—is answered affirmatively by DP1, DP2, and DP3-A. The component-level question—\emph{which} mechanism (AGENTS.md, FSD layout, or sibling patterns) contributes most—is explicitly future work (item~4). The Cond~A prompt bundles the Zod directive with three reinforcing signals: the AGENTS.md directive, the colocated Zod schemas in sibling features, and the Zod patterns in the database schema. This design choice reflects two research priorities: (1) SmartKit is deployed as a whole, so ecosystem-level effect is the pragmatically relevant question for practitioners; (2) Component isolation requires controlled ablation experiments, which are deferred to Future Work item~4.

\textbf{The ecosystem does not suppress default generation behaviour on dimensions it does not prime.} DP3-B (Cond~B test placement) was refuted: Cond~B placed tests at the repository root in all five runs, opposite of the prediction. This result is consistent with DP1 and DP2: the convention envelope's observed effect is bounded to conventions that are explicitly encoded or pattern-matched. It does not actively redirect AI default generation behaviour on dimensions where the AI has not been primed.

Three alternative explanations for the ceiling--floor pattern are worth stating explicitly so the reader can see which the pilot rules out and which it leaves open.

\textbf{Alternative A (instruction-following reinforcement):} Cond~A's advantage could reflect explicit directives rather than structural encoding alone. Future work item~4 removes the shared Zod directive from the Cond~B prompt to isolate this effect (see \autoref{sec:internal-validity}).

\textbf{Alternative B (tool-specific behaviour):} The ceiling--floor pattern could be specific to Cursor's context-awareness features (AGENTS.md parsing, codebase indexing) rather than a generalizable convention-encoding effect. Under this explanation, GitHub Copilot and Claude Code would not reproduce the pattern. Cross-tool replication (Future Work item~1) is the minimum experiment that can rule out tool specificity.

\textbf{Alternative C (coincidental alignment):} Cond~B's consistent floor scores could be an unlucky draw from a wider distribution rather than a systematic convention-naive scaffold effect. The binary rule (5/5 vs.\ 0/5) mitigates this concern on the two dimensions where the verdict was extreme. Population-level inference still requires the larger-$N$ replication in Future Work item~2, because the binary rule at $n=5$ cannot distinguish a true proportion of 0.50 from 0.80 within Wilson 95\% confidence intervals.

\subsection{Comparison to AI-Code-Generation Literature}
\label{sec:literature-comparison}

The pilot results map onto the broader AI-code-generation literature in two ways.

HumanEval and SWE-bench measure problem-solving and bug-fixing capability; neither assesses whether AI-generated code adheres to framework conventions. The ceiling--floor pattern (\autoref{fig:pilot-scores}) shows that convention adherence is a distinct dimension from algorithmic correctness: a benchmark assessing only algorithmic correctness would not detect the contrast, since both conditions produce correctly implemented utility functions. The three-dimensional rubric captures a quality dimension that existing benchmarks do not.

Yeti\c{s}tiren et al.\ report that GitHub Copilot generated valid code for 91.5\% of HumanEval problems ($n=164$), with 28.7\% fully correct and 20.1\% incorrect~\parencite{yetistiren2022assessing}. Their failure mode concerns functional correctness on algorithmic tasks. The SmartKit framework addresses structural correctness and convention adherence on boilerplate-generation tasks. Both failure modes apply to production-ready AI-assisted development. The framework complements functional-correctness benchmarks rather than replacing them.

\subsection{Implications}
\label{sec:implications}

\textbf{For practitioners.} Developers using AI coding assistants with Next.js App Router should expect that framework conventions (Server/Client boundaries, file placement, Zod typing) are not automatically followed by AI assistants unless the conventions are explicitly encoded in the project structure. A boilerplate that encodes conventions at the file-system level (SmartKit's approach) produces measurable convention adherence in AI output. A bare scaffold does not. Teams adopting AI-assisted Next.js development should consider structural convention encoding (AGENTS.md, FSD layout, colocated type patterns) as part of their AI-tooling setup.

\textbf{For researchers.} The ceiling--floor pattern across five runs per condition provides preliminary evidence that framework-convention adherence is measurable with a rubric that operates on real generated artifacts. The bundled-effect limitation means that the mechanism (AGENTS.md, FSD layout, Zod patterns, or their combination) cannot be isolated from the current pilot design. Future research on AI-framework alignment should design experiments that isolate individual convention-encoding mechanisms. The bundled-effect isolation experiment in Future Work item~4 is the minimum next step.

The following section consolidates the pilot's limitations under a four-category threats-to-validity taxonomy, followed by a summary of contributions and future work directions.

\section{Threats to Validity}
\label{sec:threats}

The threats-to-validity taxonomy below organises the limitations of the pilot under four categories.
\begin{itemize}
    \item \textbf{External Validity} covers transfer across frameworks.
    \item \textbf{Measurement Validity} covers rubric cutoffs and scoring reliability.
    \item \textbf{Internal Validity} covers rubric-calibration consequences and protocol deviations.
    \item \textbf{Conclusion Validity} covers alternative explanations.
\end{itemize}
This section is the analytical taxonomy, with each category discussed against the executed pilot rather than the pre-registered design.

\subsection{External Validity}
\label{sec:external-validity}

\textbf{Generalizability.} The pilot produced directional predictions about AI-generated Next.js App Router boilerplate, bounded to that framework. Whether they hold for Nuxt (Vue) or Remix is unverified. The framework's three dimensions are designed for portability, but cross-framework claims require framework-specific instantiation first; the cross-framework extension to Nuxt and Remix is future work (item~5).

\subsection{Measurement Validity}
\label{sec:measurement-validity}

\textbf{Rubric cutoffs and scoring protocol.} The pilot's three rubric dimensions produce ordinal, reproducible scores on the framework's Structural Integrity, Type \& Contract Safety, and Coverage \& Completeness dimensions. The cutoffs (0--1: serious violations, 1--2: minor, 2--3: acceptable, 3--4: good, 4--5: excellent) are design choices; the mapping from rubric levels to developer-relevant outcomes is not empirically calibrated. Rubric calibration against developer experience is future work (\autoref{sec:future-work}).

\textbf{Coverage dimension: design-stage limitation and a measurement correction.}
Two distinct issues affect the Coverage \& Completeness dimension, and they are reported separately to avoid conflating a known design constraint with a scoring defect.

\textit{Design-stage limitation.} The pilot feature was deliberately selected to exercise no SmartKit-integrated service (\autoref{sec:integrations-and-pilot}); that choice structurally excludes the per-user database override path required by the rubric's Levels 4--5 (\autoref{sec:pilot-rubric}). The Levels are not exercisable by this pilot feature, independent of any scoring implementation. The limitation is scope-bound, not an error.

\textit{Measurement correction.} An earlier version of the automated Coverage scorer measured file presence only and did not check the Level 4 prerequisite, which allowed Cond~A to register at the automated file-presence ceiling despite the prerequisite being unmet. The current scorer, \texttt{score-flag.ts}, detects a stubbed per-user override by a deterministic regex on the utility's body and caps the Coverage score at the level supported by the verified run artifacts. The correction is documented in the score JSON: every Cond~A run reports \texttt{coverage\_cap\_applied: true}, the underlying raw file-presence score in \texttt{raw\_uncapped\_score\_if\_capped: 5}, and the cap reason as a string pointer to \autoref{sec:integrations-and-pilot}. The correction does not alter the pre-registered rubric definitions (\autoref{sec:pilot-rubric}), the verdict thresholds (\autoref{sec:pilot-overview}), or the binary DP3 verdict, since the corrected scores remain $\geq 3$ and the Cond~B / Cond~A contrast on test colocation (DP3-A, DP3-B) is unchanged.

\subsection{Internal Validity}
\label{sec:internal-validity}

\textbf{Coverage ceiling.} The feature does not implement a database-backed per-user override, so it cannot reach Coverage \& Completeness levels 4--5. The corrected scorer caps Condition~A at level 3; this limits claims about full-range Coverage, while DP1, DP2, and the test-placement verdict DP3-A use evidence independent of that prerequisite. The correction and its recorded artifacts are detailed in \autoref{sec:measurement-validity}; the feature boundary is explained in \autoref{sec:integrations-and-pilot}.

\textbf{Ecosystem-level measurement.} Condition~A combines AGENTS.md directives, FSD layout, and sibling Zod patterns. The confirmed DP1, DP2, and DP3-A verdicts describe the contrast for that combined convention envelope; they cannot assign the difference to one component. A component-level ablation is proposed in \autoref{sec:future-work} (item~4).

\textbf{Run-order confound.} All five Condition~B runs preceded the five Condition~A runs. Time-of-day or experimenter familiarity could therefore contribute to the observed contrast, and two tool snapshots within the Condition~A block complicate attribution further. The locked schedule is described in \autoref{sec:pilot-overview}; a randomised replication is needed to separate these effects.

\subsection{Conclusion Validity}
\label{sec:conclusion-validity}

\textbf{Alternative explanations.} The confirmed DP1 and DP2 verdicts cannot distinguish ``structural convention-encoding benefit'' from ``instruction-following asymmetry that the structural convention incidentally enables'', because Condition~A bundles both AGENTS.md directives and Zod prompts. Future work item 4 isolates the Zod contribution. Whether the same verdicts would hold under prompting-only, linter-based enforcement, or enhanced documentation remains unverified.

\textbf{Single-tool limitation.} The pilot used Cursor for every generation run. The results therefore establish the framework's behaviour with this tool and do not establish tool-independent effects; different context handling or instruction-following could change the scores. Cross-tool replication with GitHub Copilot and Claude Code is specified in \autoref{sec:future-work} (item~1).

\textbf{Small sample size.} Each condition contains five runs, which supports the pre-registered binary feasibility verdict but provides limited precision for population-level proportions or effect sizes. The observed contrast could be less stable in a larger run set, particularly for outcomes near the decision boundary. Validation-stage replication at approximately 30 runs per arm is specified in \autoref{sec:future-work} (item~2).

\chapter{Conclusion and Future Work}
\label{sec:conclusion}

\section{Summary}

\textbf{Research Question 1} asks how the evaluation framework can be consistently designed to measure AI assistant adherence to Next.js App Router conventions. The framework properties (FP1--FP3) in Chapters 4 and 5 demonstrate that the three-dimensional rubric (Structural Integrity, Type \& Contract Safety, Coverage \& Completeness) can be operationalised on real AI-generated code.

\textbf{Research Question 2} asks whether the framework demonstrates applicability. The directional prediction verdicts (DP1--DP3) in \autoref{sec:dp1-results}, \autoref{sec:dp2-results}, and \autoref{sec:dp3-results} show that the framework produces measurable contrast between the SmartKit and convention-naive conditions: DP1 (structural placement) and DP3-A (centralized test path) are confirmed; DP2 (Zod-derived FlagKey) is confirmed as ecosystem-level convention reinforcement (bundled AGENTS.md directive + structural Zod patterns drive adoption in Cond~A; directive alone in Cond~B produces mixed results); DP3-B is refuted.

\textbf{Coverage dimension scope.} This pilot exercises Coverage \& Completeness levels 0--3. The higher levels require a different feature; the design constraint and scoring correction are described in \autoref{sec:measurement-validity}.

The primary contribution is a three-dimensional framework for assessing AI-generated Next.js boilerplate convention adherence. SmartKit implements the conventions, and the five-run-per-condition pilot demonstrates that the framework produces scores on generated code. The verdicts and protocol adaptations are reported in \autoref{sec:discussion}; their limits are assessed in \autoref{sec:threats}. Larger-sample replication, cross-tool validation, and developer-participant studies are described in \autoref{sec:future-work}.

\medskip\noindent\textbf{Ceiling--floor pattern.} Cond~A medians were $5$ for Structural Integrity, $4$ for Type \& Contract Safety, and $3$ for Coverage \& Completeness. Cond~B medians were $2$, $3$, and $0$, respectively. One Cond~B run produced no Zod schema and scored $0$ on Type \& Contract Safety; the other four scored $3$. The Coverage ceiling and its effect on interpretation are assessed in \autoref{sec:measurement-validity}.

\section{Future Work}
\label{sec:future-work}

\textbf{(1)~Cross-tool replication.} Replicate the pilot using alternative AI coding assistants (GitHub Copilot, Claude Code) to assess whether the framework's dimensional scores are tool-specific or generalize across AI tools. The directional predictions (DP1--DP3) can be tested on each tool, producing a per-tool verdict table. This addresses the single-tool evaluation limitation disclosed in the abstract.

\textbf{(2)~Validation-stage replication at $n \approx 30$ per arm.} Increase per-arm sample size to a validation-stage quantity (effect size $h = 0.5$, $\alpha = 0.05$, power $0.8$, two-proportion chi-squared approximation) so that the comparative Bonferroni 99\% CI on the $A-B$ difference provides inferential leverage rather than collapsing to a single point at the binary-rule stage.

\textbf{(3)~Execute the IRR pass.} Re-execute the pre-registered second-rater IRR pass (Cohen's $\kappa \geq 0.7$) over a representative slice of runs once a second rater becomes available. The current pilot uses automated-only scoring; IRR validation is required before rubric scores can be claimed to track developer-relevant quality grades.

\textbf{(4)~Component-level decomposition experiment.} Re-run DP2 with three conditions: (A) full ecosystem, (B1) directive alone (no AGENTS.md, no sibling patterns), (B2) no directive (ecosystem structure only). This experiment isolates individual mechanism contributions, extending the ecosystem-level findings from the current pilot.

\textbf{(5)~Cross-framework extension (Nuxt, Remix).} Instantiate the framework in Nuxt (Vue) and Remix environments to assess whether the directional predictions hold outside Next.js App Router. The three dimensions are designed for portability but require framework-specific instantiation (Nuxt file-based routing via \filename{/pages/}, \code{useAsyncData()}, \code{.client.vue} suffix; Remix flat routes via \filename{/routes/}, \code{loader}/\code{action} functions, \code{ErrorBoundary} components).

\textbf{(6)~Developer-participant study.} Pair SmartKit-generated and
unstructured Next.js codebases with recruited developers and measure task
completion time, code quality, and developer-reported productivity, following
the methodology of Peng et al.\ \parencite{peng2023impact}. This validates
whether the structural-convention effect observed
in the pilot extends to real developer workflows.

\textbf{(7)~Rubric calibration against developer-experience evidence.} The Coverage \& Completeness dimension is interpreted as an aspirational developer-experience proxy; a developer-participant study that pairs each rubric level (0, 1, 2, 3) with developer-reported time-to-integrate and onboarding-friction ratings is needed before the Coverage score can be claimed to track a developer-relevant construct. Error handling, security review, and performance are also candidates for additional dimensions in a future revision of the rubric.
